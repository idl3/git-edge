# Review: crdt-branches (idea #31)

## Scores
- Feasibility 3/5. Every primitive named is GA (DO SQLite + `transactionSync`, `setAlarm`, R2 put/get, `crypto.subtle` SHA-1, `CompressionStream`). Limits are the problem: `materialize` loads every path of the branch into JS memory and `writeTree` re-hashes and re-PUTs *every* directory on every materialization (the "O(changed directories + 1)" claim is false; content-addressing makes the PUTs idempotent, not free). A 1M-path branch is ~100 MB of row objects, over the 128 MB DO ceiling, and one R2 Class-A op per directory per 1.5 s debounce window. `setAlarm` overwrites the pending alarm, so a writer stream faster than 1.5 s starves materialization indefinitely. Also, DO input gates open on R2 `await`s, which the design relies on not happening (see Concurrency).
- Reliability 2/5. Three lost-update paths: (a) concurrent `materialize` calls on one branch interleave across R2 awaits and one call's `DELETE FROM crdt_ops WHERE branch=?` drops ops the other never applied; (b) `INSERT OR REPLACE INTO crdt_state` never compares lamports, so a replayed older op after compaction clobbers a newer register; (c) `crdt_state` mutations at line 90 run outside the transaction, so a crash mid-loop commits half-applied state.
- Correctness 2/5. Not a CRDT (application order is arrival order, not `(lamport, actor)`; retries are not no-ops after compaction). For plain git clients the multi-writer path is unreachable: the client rejects a divergent push locally before the server sees it, and the only way past that (`--force`) makes `treeDiff(oldOid, newOid)` compute reverts of every other writer's work (see Interop). The agent JSON path is a serialized server-side merge with LWW, which is a defensible weaker feature.
- Effort: weeks for the agent-POST variant with the three fixes (per-branch mutex, lamport compare + per-actor high-water mark, base = pushed commit's parent); the git-client half needs a different design, not a patch.

## Crash walk-through
Push from A appends ops (durable, `transactionSync`), then `materialize` runs: reads ops, `INSERT OR REPLACE` into `crdt_state` per op (each auto-committed at the next await), awaits `diff3Blob` R2 GETs, PUTs trees, PUTs the commit, then the ref-flip transaction. Crash after the commit PUT and before the transaction: ref unchanged, ops and `dirty` retained, tree/commit objects orphaned in R2 (content-addressed, harmless, needs the sweeper from #6). The alarm was armed, so it re-runs `materialize`; ops re-apply onto the already-mutated `crdt_state`. For plain LWW ops this is idempotent; for a diff3 path the second pass sees `cur.blob` = the merged blob != `o.base` and runs diff3 again with "theirs" already inside "ours", which yields either a clean no-op or a spurious conflict that then silently LWW-clobbers the merge. No ref split-brain (single DO, single `refs` row), but the client that got a 5xx retries: `lamport = Date.now()` differs, so the PK does not dedupe, a second batch of identical ops is appended, and a second merge commit with the same parent set is minted. "Replaying a retried push is a no-op" is false.

## Concurrency walk-through
A and B push to `live/foo` within 100 ms. A: `appendOps`, `materialize` -> `SELECT * FROM crdt_ops` (sees A's ops), `await diff3Blob(...)`. Input gate opens (R2 is not storage). B: `appendOps` (B's ops now in table), `materialize` -> SELECT sees A's and B's ops, applies both to `crdt_state`, awaits R2. A resumes, `SELECT path, blob FROM crdt_state` may or may not include B's rows depending on await ordering, builds tree T_A, PUTs commit M_A (parents: prev, P_A), runs the transaction: ref = M_A, `DELETE FROM crdt_ops WHERE branch='foo'` -- deleting B's ops. B resumes, PUTs M_B (parents: prev, P_A, P_B), ref = M_B. Final ref = whichever transaction runs last. If A's runs last: tip = M_A, whose tree may lack B's edits, B's ops are gone from the log, and M_B (the only commit containing B's edit in a tree) is unreachable from any ref. B's client was told `new-oid M_B` and will pull a tip that does not contain its change. That is silent data loss under ordinary two-writer load, and the same race exists between `alarm()` and a push-triggered `materialize`. Second path: agent A posts `{lamport:5, path:f, blob:X}`, compaction runs, B posts `{lamport:9, blob:Y}`, compaction runs, A's HTTP retry re-posts lamport 5: `INSERT OR IGNORE` succeeds (log is empty), `INSERT OR REPLACE` writes X over Y. LWW violated by design, not by race.

## Interop check
1. Client-side rejection, `remote.c:set_ref_status_for_push()`. The receive-pack advertisement (v0; there is no v2 push) tells the client `refs/heads/live/foo = M_k+2`. A client whose branch is `P` (parent `M_k`) either lacks `M_k+2` -> `REF_STATUS_REJECT_FETCH_FIRST` ("! [rejected] ... (fetch first)"), or has fetched it and `ref_newer(P, M_k+2)` is false -> `REF_STATUS_REJECT_NONFASTFORWARD`. The pack is never sent; "`git-receive-pack` never rejects a non-fast-forward" is moot because the client does. After a fetch the user merges/rebases locally, pushes a commit whose parent is the tip, and the CRDT path is never exercised -- that is ordinary git.
2. With `--force`, the command line is `<M_k+2> <P> refs/heads/live/foo` where old-oid is the *advertised* tip, not "the tip it was based on". `treeDiff(M_k+2, P)` therefore emits an op for every file other writers changed since `M_k`, with `blob` = the stale `M_k` content and `base` = the current state blob, so `cur.blob === o.base` skips diff3 and LWW reverts everyone else's work. The base must be `P`'s parent (or `merge-base(P, tip)`) read from the commit object, never old-oid.
3. `report-status-v2 ... option new-oid <M>` is parsed by `send-pack.c:receive_status()` and applied in `transport_update_tracking_ref()`, but `refs/files-backend.c:write_ref_to_lockfile()` calls `parse_object()` on the new oid and the client does not have `M` -> "error: trying to write ref 'refs/remotes/origin/live/foo' with nonexistent object <M>". Push exits 0, tracking ref is not updated; the next `git pull` is a fast-forward as claimed (P is a parent of M), so this is noise, not loss.
4. `treeDiff` with `oldOid = 0{40}` (branch creation) and `newOid = 0{40}` (deletion) is unhandled; deletion of a live branch falls through to op generation.
5. `writeTree` hard-codes `100644`; `treeDiff` carries no mode, so executables (`100755`), symlinks (`120000`) and gitlinks (`160000`) are silently rewritten to regular files. `git fsck` passes; the checkout is wrong.

## Blockers
- Plain `git push` of a divergent commit never reaches the server (client-side non-ff check); with `--force` the old-oid base turns other writers' edits into reverts. The git-client half of the idea has no correct wire path as designed.
- Concurrent `materialize` on one branch (push vs push, push vs alarm) deletes unapplied ops and can leave the tip without a writer's change. Needs a per-branch mutex or `blockConcurrencyWhile`, and `DELETE ... WHERE rowid <= max_seen`.
- `crdt_state` replace ignores lamport; post-compaction replay of an older op overwrites newer state. Needs `WHERE (lamport, actor) < (?, ?)` plus a per-actor high-water mark so the "idempotent" claim survives compaction.

## Caveats
- `Date.now()` lamports plus `ORDER BY lamport, actor` make ordering wall-clock dependent; the proof admits it, but the fix (per-actor `max+1`) changes the PK semantics and the idempotency story.
- Full-tree re-hash per materialization: memory O(paths), R2 PUT O(directories); needs cached subtree shas keyed by directory.
- Debounce alarm is starvable under continuous writes; use "no earlier than first dirty + 1.5 s", not "now + 1.5 s".
- One merge commit per debounce window per branch; commit-graph and negotiation cost grow unboundedly on a hot branch.
- diff3 conflict falls back to LWW with the loser preserved only as an unreachable-ish parent; users get no conflict signal at all.
- Partial `crdt_state` writes outside the transaction; wrap the whole apply loop, which forces the diff3 blob reads to happen before the transaction.

## Verdict
does-not-land as written. The primitives are fine and an agent-only "server-side LWW merge with debounced materialization" is buildable in weeks once the three blockers are fixed, but that is a sequential merge service, not a CRDT, and the headline claim that plain git clients participate as concurrent writers is contradicted by git's client-side fast-forward check and by the old-oid-as-base diff, which actively destroys other writers' changes under `--force`.

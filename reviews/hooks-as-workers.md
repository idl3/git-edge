# Review: hooks-as-workers (idea #23)

## Scores
- Feasibility: 4/5. DO SQLite + `transactionSync`, alarms, service bindings on a DO's `env`, dispatch namespaces (`env.HOOKS.get`), `AbortSignal.timeout`, HMAC via `crypto.subtle` are all GA; Worker Loaders are correctly flagged beta and unused. Limits are fine: payload is ref lines, fan-out is sequential, 1000-subrequest cap and 128 MB are nowhere near. Docked because the headline "register a Worker" is, by the proof's own admission, only reachable through Workers for Platforms (paid add-on) or an HTTPS webhook; `service:` targets are deploy-time only. Also `x-git-edge-json` carries every command in a header: Cloudflare caps a single header at 16 KB (32 KB total), so a `--mirror` push with a few hundred refs gets the hook call rejected before the hook runs — put it in the body.
- Reliability: 2/5. The core shape (pre-receive outside the transaction, CAS re-check inside, post-receive outbox row committed with the ref flip) is right. But the proof shares one DO with two-phase-push and a DO has exactly one alarm: `commit()` calls `setAlarm(Date.now())`, and this `alarm()` only drains the outbox and re-arms for `MIN(outbox.next_at)`. The janitor alarm two-phase-push armed in `begin()` (guarded by `getAlarm() === null`) is silently overwritten, and future `begin()` calls see an alarm already set and never re-arm it. Net: orphan sweeping stops the first time a repo has a post-receive hook. Fixable in an hour with a single dispatcher alarm, but as written it is a correctness regression in a dependency.
- Correctness: 3/5. Delivers a pre-receive *gate* and an at-least-once post-receive *notification* with git-shaped stdin. It is not a git hook: no `git rev-list`, no quarantine env (`GIT_QUARANTINE_PATH`), no `update` per-ref semantics, no push-options; `isFastForward` (the canonical use) is hand-waved and would cost one R2 read per commit walked. The "hook fetches pending objects via upload-pack + token" path needs upload-pack to serve SHAs that are in `pending/<pushId>/manifest.json` but not yet in the `objects` index — not shown anywhere.
- Effort: weeks. The DO code is days; the token-scoped upload-pack for pending objects, the alarm dispatcher, HMAC/secret storage, and a WfP dispatch namespace (or webhook fallback) are the rest.

## Crash walk-through
Push P: objects in R2, `commit()` runs pre-receive (hook says ok), `transactionSync` flips `main` and inserts an outbox row. Case A: isolate dies after the transaction commits but before line 85's `setAlarm` reaches storage. SQLite writes and alarm writes share the output gate and there is no `await` between them, so in practice they flush together (PLAUSIBLE; docs describe alarm state as part of the same storage, not verified for SQLite-backed DOs). If they did not, the row sits in `outbox` with no alarm until the next push with a post hook — no data loss, delayed delivery. Case B: `alarm()` delivers to the hook, the hook returns 200, isolate dies before `DELETE FROM outbox`. Redelivery on the next alarm: at-least-once as claimed; the hook has `pushId` to dedupe. Case C (the real one): any repo that has a post-receive hook. `commit()` sets the alarm to now, `alarm()` drains and re-arms only for the outbox, and the two-phase-push janitor alarm is gone; a later push that crashes between phase one and phase two leaves `pending/<id>` and orphan `objects/<sha>` keys forever, and `begin()`'s `getAlarm() === null` guard means it is never re-armed. Retry window is also short: `2^0..2^8` seconds sums to ~8.5 minutes, then the row is dropped — a user Worker mid-deploy or a webhook target in a 10-minute outage loses the event permanently, which contradicts "strictly better than git".

## Concurrency walk-through
Pushes A and B both move `main` from X. A enters `commit()`, awaits its pre-receive hook (input gate opens). B enters `commit()`, awaits its hook. Both hooks accept. A's `transactionSync` sees `main == X`, flips to A, enqueues post-receive. B's transaction sees `main == A != X` → `ng refs/heads/main fetch first`. Correct, and identical to git's ref-lock race; the hook saw an `old` that was still true at flip time. Post-receive rows are drained in insertion order by a single DO, so per-repo ordering holds. Two subtle points: (1) the `hooks` table is read at two different times with awaits between (lines 59 and 70), so a hook registered mid-push gets post-receive but was not consulted for pre-receive — benign but document it. (2) A hook that pushes back into the same repo re-enters the DO while the outer `commit()` is awaiting; that is allowed (input gate is open during a non-storage await) and the CAS makes it safe, but the `x-git-edge-depth` recursion stop is asserted, never enforced by any endpoint in the proof. `alarm()` awaiting hook fetches while `commit()` calls `setAlarm(Date.now())` again is fine: the runtime does not run two `alarm()` invocations concurrently and the re-set fires after the current one returns (PLAUSIBLE).

## Interop check
Push is protocol v0/v1 (v2 has no receive-pack); git 2.4x sends `report-status side-band-64k` (and `report-status-v2` when it understands it). The client prints `! [remote rejected] main -> main (pre-receive hook declined: <msg>)` from an `ng <ref> <reason>` line, so the mapping is sound, and real `git-receive-pack` also rejects *every* ref on a non-zero pre-receive. The wire detail that breaks: `reason` is the rest of the pkt-line. The proof takes `res.text().trim().slice(0,200)` and interpolates it — a hook body with an embedded newline splits into a second pkt-line that starts with neither `ok ` nor `ng `, and `receive_status()` in the client fails with `invalid ref status from remote`. Strip `\n` from the reason, and send the long free text as band-2 `remote:` lines (which is what git does with hook stderr). Also: with side-band-64k every report-status line must be wrapped in band 1 — that is the receive-pack slug's job but this proof's return value is consumed there. `report-status-v2` (`ok <ref>` may be followed by `option ...` lines) is not addressed; harmless as long as the server only advertises `report-status`.

## Blockers
- Single-alarm collision with two-phase-push's janitor (and gc-and-repack-alarm, which also owns `setAlarm`): needs one dispatcher `alarm()` that computes the earliest of `pending` sweep, `outbox.next_at`, gc, and re-arms from all tables.
- Hook rejection message can contain `\n` and corrupt report-status; must be sanitised or moved to band 2.
- Upload-pack serving not-yet-committed objects under a `pushId` token is required for any real pre-receive policy and is not designed.

## Caveats
- "Users deploy a Worker and register it" is only true with Workers for Platforms; otherwise it is a webhook with HMAC, whose secret storage/rotation is absent.
- Commands in a request header hit the 16 KB per-header limit on large or `--mirror` pushes.
- Retry budget of ~8.5 min then drop makes post-receive lossy for any realistic outage.
- Hooks receive stdin lines but nothing else git provides (`update` hook, push-options, `GIT_PUSH_OPTION_*`, quarantine); non-fast-forward checks cost R2 reads per commit.

## Verdict
risky. The transaction-plus-outbox design and the pre-receive-outside/CAS-inside ordering are the right skeleton and run on GA primitives, but the proof as written breaks the orphan janitor it depends on, can corrupt the push report with an ordinary hook message, and leaves the one thing hooks are for — inspecting the pushed history — undesigned. Fix the alarm dispatcher and reason sanitising and this drops to lands-with-caveats.

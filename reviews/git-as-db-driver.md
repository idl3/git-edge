# Review: git-as-db-driver (idea #42)

## Scores
- Feasibility 4/5. Every primitive is GA: DO SQLite (`ctx.storage.sql`, needs `new_sqlite_classes` migration), `setAlarm`/`alarm()`, R2 `put`/`get`, `CompressionStream("deflate")` (zlib framing, correct for loose objects), `crypto.subtle.digest("SHA-1")`, DO RPC. Limits: `treeFromRows` re-hashes every table on every save; a 1M-row table is a ~38 MB tree object copied 3x (`cat`, `Blob`, `arrayBuffer`) and SHA-1'd per write, which brushes the 128 MB DO heap and burns CPU on each save (proof admits this). `migrate` is one unbounded await loop. Deduction for a RPC bug: `find(tbl, pred)` takes a function; over DO RPC the function arrives as a stub whose call returns a Promise, so `.filter(pred)` sees a truthy promise and returns every row. Same for `migrate(fn)`: a stub cannot be re-invoked after eviction or from `alarm()`.
- Reliability 2/5. "Serialized without locks" is false. DO input gates open on every R2 await, and `save()` reads `prev = head()` before ~3 R2 puts and writes `refs` after them. Two saves in flight both see parent H, both commit, the second `INSERT OR REPLACE refs` wins, the first commit is dangling and the `expectHead` "CAS" passes for both (see Concurrency). The sibling `repo-do-ref-authority` does it right (`UPDATE ... WHERE sha=?` synchronously); this proof does check-then-act across awaits. Migration state is in-memory and `migrate` only sets `main` and the alarm at the very end, so a mid-migration crash leaves a half-rewritten `rows` mirror that later saves silently commit to `main` (see Crash).
- Correctness 2/5. Loose blob/commit bytes are right. Tree sort is wrong for git: JS `<` compares plain names, git compares with a `/` appended to directory names, so sibling tables `users` and `users-old` sort `users-old` first in git (`/`=0x2f > `-`=0x2d) but `users` first here; `git fsck` reports "not properly sorted" and `git checkout` index lookups fail. Bigger: the mirror is the source of truth in practice. An external `git push` (allowed by the design, same DO) moves `main` but never touches `rows`; the next ORM save rebuilds the tree from `rows` and reverts the pushed content (and drops every non-`tables/` path, since the root tree only ever contains `tables`). "Every query a tree walk" is a SQLite scan of JSON text; "migrations are rebases" is rewrite-then-replay of journaled writes that never were commits. Working document store with git-shaped history, not the stated thing.
- Effort: weeks. DO plus JS adapter is days; per-subtree tree caching, a real synchronous CAS (`blockConcurrencyWhile` or an in-DO promise queue), persisted migration journal with named migration fns, mirror rebuild on external push, git-order tree sort, and packing via siblings is the bulk. ActiveRecord adapter is months and never drop-in.

## Crash walk-through
`migrate("v2","users",fn)` on 50k rows: `migrating=true`, loop awaits one R2 put per row and updates `rows` in place. The isolate dies at row 20k. SQLite writes made before each await are already durable, so `rows` holds 20k v2 rows and 30k v1 rows; `migrating` is gone with the isolate; no alarm was set (it is armed last); `refs/heads/migrate/v2` and `main` are untouched. Next `save()` sees `migrating=false`, builds the tree from the mixed mirror and commits it on `main` as `save users/7`. The half-migration is now permanent history on `main` with no commit naming it, and re-running `migrate` applies `fn` twice to 20k rows. No ref split-brain, but silent data corruption. The plain `save()` crash is milder: blob put and `rows` insert are durable, `refs` never moves, the caller gets a 5xx and retries; the mirror is one row ahead of HEAD until the next successful save sweeps it in, and 1-3 R2 objects are orphaned per crash with no GC.

## Concurrency walk-through
Clients A and B both read `main=H` and call `save("users","1",{x:1},H)` / `save("users","2",{y:2},H)`. A awaits its blob put; B enters, awaits its blob put. A resumes: inserts row 1, `prev=H`, expectHead passes, starts `treeFromRows` (awaits tree puts). B resumes: inserts row 2, `prev=H`, expectHead passes too (nothing has moved), starts its own `treeFromRows`, which now includes row 1. A's trees were hashed before row 2 landed, so A's commit lacks row 2; B's commit has both. Both have parent H. If B's final `refs` write lands last: `main=B`, A's commit is dangling, `git log` shows one commit for two saves, but content is complete. If A's write lands last (its commit put was slower): `main=A`, whose tree lacks row 2, while `rows` has it; B was told `sha=B` for a commit not on `main`. The mirror and HEAD now disagree until the next save, and "re-materialize from HEAD" would lose row 2. Two concurrent `migrate` calls interleave the same way and produce a tree that is a blend of both rewrites.

## Interop check
- Right: `<type> <len>\0` header, SHA-1 over header+body, zlib via `CompressionStream("deflate")`, `100644`/`40000` modes, 20-byte binary shas, commit layout with author/committer and blank line. A stock git 2.4x `clone` through the sibling upload-pack would accept these objects.
- Breaks: tree entry order for names where one is a byte-prefix of another under a directory (`users` vs `users-old`, `a` vs `a.json` if a table were ever named with a dot). Git's `base_name_compare` treats dir names as `name/`; `git fsck` flags the tree, and `git ls-tree`/`checkout` binary-search the entries and miss them. Also JS string `<` orders by UTF-16 code unit, git by byte; ids outside the BMP sort differently.
- Encoding contract: this proof writes zlib'd bodies at `objects/<sha>`, but `content-addressed-r2-keys` stores uncompressed and `refs-sqlite-objects-r2` uses `objects/<prefix>/`; until siblings agree, the fetch path may not serve these objects at all. Nothing here speaks pkt-line; interop is entirely inherited.

## Blockers
- Ref update is check-then-act across R2 awaits: concurrent saves produce dangling commits, HEAD/mirror divergence, and a no-op `expectHead` lock. Needs a synchronous conditional `UPDATE refs ... WHERE sha=?` (or `blockConcurrencyWhile`/queue) with a retry loop.
- Migration state (`migrating`, base, fn name, progress) lives in memory and `main`/alarm are set only at the end; any crash mid-loop commits a half-migrated table on `main`.
- `rows` mirror is never updated from `git push`; the next ORM save reverts pushed content and drops all non-`tables/` paths.
- Tree sort does not match git's directory-as-`name/` ordering; `git fsck` fails for prefix-named sibling tables.

## Caveats
- `find`/`migrate` predicates over DO RPC become stub promises; `filter` returns everything. Pass a serializable query or a named function.
- O(rows) tree rehash and ~4 Class A puts per save; expect 50-100 saves/s per DO and a 128 MB wall near 1M rows in one directory. Shard `tables/<tbl>/<a>/<b>/` and cache subtree shas in SQLite.
- Alarm replay is not idempotent: a retried `alarm()` re-commits already replayed writes with fresh timestamps (duplicate commits, orphan objects).
- Journaled writes are replayed un-migrated; the proof admits this. Store the migration name and apply `fn` on replay.
- Loose objects only; clone after N saves is N R2 GETs until the pack siblings exist. Orphaned objects from crashes/races have no GC.

## Verdict
risky. The object encoding is close enough that a stock git could read the history, and one-writer-per-DO makes a single-client version work on day one. But the proof's central claim, "serialized without locks", is wrong under DO input-gate semantics: concurrent saves race across R2 awaits, the optimistic lock is a no-op, and a mid-migration crash bakes a half-rewritten table into `main`. Add a synchronous CAS, persisted migration state, git-order tree sorting, and mirror refresh on push, and it lands as a git-backed document store; weeks, not days.

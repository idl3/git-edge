# Review: server-side-rebase (idea #18)

## Scores
- Feasibility 4/5. Every primitive is GA: DO SQLite (`sql.exec`, `rowsWritten` on the cursor), `setAlarm`/`alarm()`, DO RPC methods, R2 `put`/`get`, `CompressionStream("deflate")` (emits a zlib wrapper, which is what a loose object needs), `crypto.subtle.digest("SHA-1")`. CPU: 40 replays per step with tens of R2 round trips each is wall-clock, not CPU, so the 30 s CPU limit is safe; memory: trees are small, but `mergeTrees` on a blob pair and the `commits.raw BLOB` column (2 MB/value cap) are unbounded by the code. Deduction: "the DO serializes the operation with every push" is overstated. DO input gates release on non-storage awaits, so pushes interleave with every R2 `get`/`put` inside `step()`; only the final CAS makes that safe, and it does (see Concurrency).
- Reliability 2/5. No ref loss or split-brain (single DO, CAS on `expect`), but the job machine has three real holes: a crash between the `INSERT INTO rebase_jobs` commit and the first `setAlarm` leaves a `done=0` job that nothing ever resumes; `alarm()` takes `LIMIT 1` and re-arms only from inside the job it stepped, so a second pending job starves the moment the first one finishes; `writeCommit` stamps `Date.now()`, so a retried step mints a different oid and the earlier commit/tree objects are orphaned in R2 with no GC (content-addressed, harmless, but billed and never reclaimed). Jobs are never deleted either.
- Correctness 2/5. The protocol half is right (see Interop). The rebase half is a stub: `squash` is stored as `[{squashOf, msg}]` and then fed to `parentTree(c)`/`tree(c)` in `step()` as if it were a commit oid, so the squash path throws on its first iteration; `command=rebase-status` is advertised but has no handler, so a `pending` reply is a dead end; `mergeTrees` is a comment, and without diff3 every same-file edit on both sides is a "conflict", which in practice is most rebases onto a moved `main`; author/date are replaced by `git-edge`, which `git rebase` never does; merge commits in `revList` are cherry-picked against `parentTree(c)` (first parent implied) with no stated policy. What lands is "server-side tree-level cherry-pick loop with CAS", a real but weaker thing.
- Effort: weeks. Protocol/DO scaffolding is days; a JS diff3 (pure-JS ports exist, no Wasm needed), a real `mergeTrees` with tree-object writing, job GC/re-arm, the `rebase-status` handler, and a pkt-line HTTP client are the bulk. Months only if the Wasm git core is made a hard dependency.

## Crash walk-through
Client sends `command=rebase onto=main branch=feat expect=E`. `rebase()` inserts the job, `step()` replays commits 1..17, each `writeCommit` doing an R2 `put` then an `INSERT OR IGNORE INTO commits`, then the isolate dies at commit 18 before the `UPDATE rebase_jobs SET head,todo`. DO storage writes are committed only when the output gate opens, so on restart the `commits` rows and the job row are rolled back to whatever the previous event committed. If the crash was in the first request, the job row itself never committed and the client gets a 5xx: clean, retry works. If it was in an alarm step, the last checkpoint (`head`,`todo`) is intact, the alarm is at-least-once and re-fires, and the step resumes from the checkpoint. The 17 R2 objects written in the dead step are orphans forever (new timestamps produce new oids on redo). No ref was touched, so nothing is lost or split. The truly bad case is subtler: `rebase()` commits the row and `step()` returns `pending` after `setAlarm`, both in the same event, so they commit together; but a crash after the row commits and before `setAlarm` runs in a later alarm step (e.g. `step` throws on a malformed tree) leaves `done=0` with no alarm armed and no `rebase-status` handler to nudge it. Stuck forever until another rebase on the same repo happens to arm an alarm and `LIMIT 1` picks it.

## Concurrency walk-through
Two clients both read `feat=E` and both send `rebase ... expect=E`. Both jobs are inserted (the `tip(branch) !== expect` guard passes for both since neither has flipped yet); both replay in interleaved alarm steps against the same `onto` tip. Job A finishes first: `UPDATE refs SET oid=A' WHERE name=feat AND oid=E` writes 1 row. Job B finishes: its CAS finds `oid=A'`, writes 0 rows, reports `stale`. Correct, no split-brain, but B's entire replay is wasted work and its objects are orphaned. Now a `git push feat` arrives mid-replay of A: the push's own CAS moves `feat` to P; A's final CAS fails with `stale`. Also correct. ABA: push moves `feat` E -> P -> E (force push back); A's CAS succeeds. Since the oid is the content, the result is still a valid rebase of E onto `onto`, fine. Weakest point: `onto` is read once (`head = tip(onto)`) at job creation, so a rebase that spans several alarm steps while `main` advances lands on a stale `main`; `git` would call that a successful but non-fast-forward-relative rebase, and the client's subsequent `fetch`+`reset --hard` hides it. Not a data-loss bug, but the "moving `onto` tip" wording in the mechanism is not what the code does.

## Interop check
- What is right: git >= 2.18 `remote-curl.c` `check_smart_http` accepts an `x-git-upload-pack-advertisement` body whose first pkt is either `# service=git-upload-pack` or bare `version 2`, so the proof's omission of the `# service=` prelude is legal. Unknown capability lines (`rebase=squash`, `rebase-status`) are parsed into the server-capabilities list and ignored by `ls-refs`/`fetch`; verified that git 2.4x `git ls-remote` and `git fetch` with `-c protocol.version=2` do not error on extra `key=value` lines. `fetch=shallow wait-for-done` and `object-info` are real values. So the headline claim ("advertised, invisible to old clients") holds.
- What would break, exactly: a stock client sends `Git-Protocol: version=2` on `info/refs` only when `protocol.version=2` (the default since 2.26), so a v0/v1 client hits the `version=2` header check, falls through to 404, and cannot clone at all; that is the sibling `protocol-v2-only` decision, not this idea, but this proof's `fetch` has no v0 fallback. For the new command, the git-edge client must send `Content-Type: application/x-git-upload-pack-request` and `Git-Protocol: version=2` on the POST; the proof's dispatcher ignores both headers, so a wrong-typed POST from a proxy would still be parsed. The `conflict` response reuses `0001` as a section delimiter, which is legal v2 framing. The `args` parser splits on the first space and `"squash" in args` works for a bare `squash` line. Nothing in the rebase wire format would confuse a stock client because a stock client never sends it.
- Objects: the loose-object header, zlib wrapper and SHA-1 over `"commit <len>\0"+body` are byte-correct, so a later stock `fetch` can serve rebased commits, provided the sibling pack builder inflates R2 loose objects (the `in-do-object-cache` review already flags that the siblings disagree on whether R2 bodies are zlib'd; this proof writes zlib'd bodies at `repos/<doId>/objects/<oid>` while `content-addressed-r2-keys` writes uncompressed at a different key layout, so rebased commits may be unreadable by the fetch path until that contract is settled).

## Blockers
- Squash path throws: `step()` treats `{squashOf, msg}` as a commit oid. Needs a separate branch: `mergeTrees(tree(base), tree(onto), tree(tip))` then one commit.
- `rebase-status` is advertised but unimplemented, so every multi-step (`pending`) rebase is unobservable by the client.
- `alarm()` `LIMIT 1` without re-arming when other `done=0` rows exist starves concurrent jobs; a thrown `step()` leaves a job stuck with no alarm.
- R2 key layout and body encoding (`repos/<doId>/objects/`, zlib'd) diverge from `content-addressed-r2-keys` (`objects/<sha>`, uncompressed), so the fetch path may not serve the rebased commits.

## Caveats
- No file-level merge until diff3 lands; until then most real rebases report `conflict`. Use `node-diff3`-style pure JS rather than waiting on the Wasm core.
- Original author/date/signature are discarded; pass `author` through as a command argument and copy it from the source commit by default.
- `onto` is pinned at job creation; a long replay lands on a stale base. Either re-read `tip(onto)` per step and restart, or document it.
- Orphaned R2 objects from retried/lost jobs need a GC hook (mark objects reachable from refs, sweep `objects/` older than N days).
- Hot-branch push latency degrades while a job runs on the same DO; the 40-commit step budget should be time-based (e.g. 5 s wall clock), not count-based.

## Verdict
risky. The v2 capability advertisement and CAS-guarded ref flip are correct and a stock git 2.4x client is provably unaffected, so the idea's protocol claim lands. But the rebase engine in the proof is a sketch with a crashing squash path, an unimplemented status command, a starvable job queue and no file-level merge; it is a tree-level cherry-pick loop, not a rebase. Weeks to a version that actually rebases a branch whose files were touched on both sides.

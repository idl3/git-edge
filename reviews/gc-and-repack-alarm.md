# Review: gc-and-repack-alarm (idea #55)

## Scores
- Feasibility 3/5. Every primitive named is GA (SQLite DO, `setAlarm`/`alarm()` with ~6 retries and per-invocation write rollback on throw, R2 `delete(string[])` ≤1000, R2 multipart with `resumeMultipartUpload`, `CompressionStream("deflate")` = zlib). The resumable state-machine shape is the right one for a 30 s CPU cap. Deductions are for code that cannot run as written: (a) `gc.buf.push(...(await this.packEntry(o)))` spreads a whole object's bytes as call arguments, which throws `RangeError: Maximum call stack size exceeded` for any blob over roughly 100 KB; (b) `this.meta("gc", JSON.stringify(gc))` persists up to 5 MiB of `number[]` as one SQLite TEXT value, past the 2 MB per-row limit (and ~40 MB of heap for the array); (c) a DO has exactly one alarm and `setAlarm(Date.now())` in a tight chain clobbers the alarms `two-phase-push` (janitor), `precomputed-clone-pack` (30 s rebuild), `in-do-object-cache` and `ephemeral-repos` all assume they own. The proof admits (b); (a) and (c) it does not.
- Reliability 2/5. One dangling-ref path and two permanent-stall paths (below). No corruption of committed bytes, because R2 keys are content-addressed and reachable loose objects are never touched, but a stall silently disables GC forever.
- Correctness 2/5. Against the sibling contracts this proof consumes, nothing lines up: `two-phase-push` creates `objects (sha TEXT PRIMARY KEY)` with no `type/size/links/created_at`, so the mark walk's `JSON.parse(row.links)` throws on the first ref; `content-addressed-r2-keys` stores the loose form UNCOMPRESSED at `objects/<owner>/<repo>/<aa>/<rest>`, so `BUCKET.get("objects/<sha>")` is null (`obj!.body` TypeError) and, key fixed, `DecompressionStream` dies on a non-zlib body; `precomputed-clone-pack` keys packs by `<owner>/<repo>` and needs `pack_slices` (blob-boundary offset + a second trailer) plus covered tips; this proof writes neither, so the built pack is never served. The "repack" is also a lookalike: no deltas, and reachable loose objects are kept, so storage doubles rather than shrinks.
- Effort: weeks. Fixing the buffer (Uint8Array chunks in SQLite BLOBs or an R2 scratch key), the serialisable SHA-1, an alarm multiplexer shared by all sibling alarms, the sweep ordering, tip snapshotting and slice recording is each small, but all of it needs an end-to-end test with real `git clone` before the pack can be trusted.

## Crash walk-through
Pack phase, final batch: `mpu.complete(parts)` succeeds, then the isolate dies before the handler returns. SQLite writes for the invocation roll back, so `gc.count` and `gc.phase` revert; alarm retries; `batch.length === 0` again; `mpu.complete` is called on an upload that no longer exists → R2 throws NoSuchUpload; every retry throws; after the retry budget the alarm is dropped. `meta.gc` still exists, so `onRefsChanged` never re-arms (`if (!this.meta("gc"))`) — GC is off for this repo forever and a complete pack sits orphaned in R2 with no `pack_builds` row. Same terminal state from any deterministic throw (a >100 KB blob in `packEntry`, a missing `objects` row in mark). Mid-batch crashes are fine: part numbers are re-used and `CompressionStream` is deterministic, so re-uploading part N overwrites identical bytes; R2 `delete` before row `DELETE` is idempotent on retry. First-invocation crash after `createMultipartUpload` orphans an MPU until R2's 7-day auto-abort; harmless.

## Concurrency walk-through
Sweep invocation checks `refs_version`, then `await BUCKET.delete(dead)`. That await is external I/O, so the DO input gate opens and a `commit()` for a push that resurrects orphan commit X (in `dead`) runs: the Worker's HEAD on `objects/X` returned found so no bytes were re-uploaded, `known(X)` passes because the `objects` row still exists, refs move to X, `refs_version` bumps. Sweep resumes, R2 delete of X completes, `DELETE FROM objects` removes X's row. Result: `refs/heads/foo → X` with no bytes and no index row; the next clone gets a pack missing X and `git fsck`/checkout fails. The proof's `refs_version` guard runs before the delete, not atomically with it — it does not close the race it claims to. Fix: delete the SQLite rows first (so `known()` fails and the push is rejected/re-uploaded), then the R2 keys; or have commit not trust HEAD-found without a row. Separate liveness issue: any push during mark/pack invalidates the whole run at sweep time, so a repo that is pushed to more often than a full repack takes never finishes GC (starvation, not corruption).

## Interop check
- Byte layout that is right: `PACK`, v2, big-endian count, type/size varint (verified: `(type<<4)|(size&15)`, then 7-bit groups with 0x80 continuation), zlib bodies via `CompressionStream("deflate")`, non-delta only, commits→tags→trees→blobs; SHA-1 trailer over everything before it. A git 2.4x `index-pack` accepts this once served with the trailer appended.
- Exact wire break: the header count is `COUNT(*) FROM marked`, the entry loop is `marked JOIN objects`. Any marked sha without an index row (exactly the state a resurrected-then-swept object or a link to a not-yet-committed object leaves) yields fewer entries than the header promises; `index-pack` reads the trailer bytes as the next object header and dies with `fatal: pack has bad object at offset N`. Second break: the object stored in R2 has no trailer, so the "same R2 object is a well-formed .pack" claim of `precomputed-clone-pack`/`bundle-uri` is false for packs from this builder. Third: covered tips are the refs at `startGc()` but are never recorded; if the consumer uses refs-at-completion, a clone whose wants moved during the build receives a pack missing those commits (`fatal: bad object` on checkout), and if it uses nothing the fast path never hits.

## Blockers
1. Schema/key/encoding contract mismatch with `two-phase-push`, `content-addressed-r2-keys` and `precomputed-clone-pack` — mark, pack and serve each fail on the sibling-built repo.
2. Sweep race: refs_version check is not atomic with the R2 delete; a resurrecting push during the delete leaves a dangling ref.
3. Stall-to-death: `mpu.complete` re-run after rollback, spread-args RangeError, or a missing row exhausts alarm retries and `meta.gc` then suppresses re-arming forever; no watchdog.
4. Single DO alarm shared with at least four sibling ideas; `setAlarm(Date.now())` chaining silently cancels theirs.

## Caveats
- `gc.buf` as `number[]` in JSON exceeds the 2 MB SQLite row limit and costs ~8× the bytes in heap; must become BLOB chunks or an R2 scratch key.
- No delta compression and loose objects retained after repack: R2 storage roughly doubles; the pack is a clone accelerator, not a space reclaimer, until a second sweep learns "covered by pack".
- Cost/throughput: one Class B GET plus an inflate+deflate per reachable object per build; 1M-object repos need churn gating and take hours of alarm slices during which every `commit()` queues behind mark batches.
- `resumeMultipartUpload` uploads expire after 7 days; state must detect NoSuchUpload and restart the pack phase.
- Pure-JS serialisable SHA-1 is asserted, not shown; `crypto.subtle` cannot checkpoint.

## Verdict
risky. The architecture (index-only mark, resumable phased alarm, timestamp grace period, content-addressed sweep) is the correct design for a serverless git GC, but the proof as written cannot execute against the repos its dependencies build, has a real dangling-ref race in sweep, and has three ways to wedge itself permanently. All fixes are known and bounded; none are done.

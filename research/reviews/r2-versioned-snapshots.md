# Second-pass review: Snapshots via R2 object versioning of ref state

# Review v2: r2-versioned-snapshots (idea #21)

## Scores
- Feasibility 4/5 (was 4). The R2 surface is real in `worker` 0.8.5: `ListOptionsBuilder::{prefix, limit, start_after, execute}`, `Objects::{objects, truncated, cursor}`, `Object::{key, size}`, `Bucket::{put, get}` and multi-key `delete_multiple` all exist (docs.rs/source; `delete_multiple` per the two-phase-push review). `SqlStorage::exec`/`changes()` are measured (platform-facts #1, #4) and `gix_pack::data::header::decode` is verified in 0.74.2. The misses are all compile-level: `gix_zlib::Inflate::feed` does not exist — in 0.1.0 `Inflate` is the one-shot helper (`once(input, &mut [u8]) -> Result<(Status, usize, usize)>`, `reset`); the incremental consumed-count API the code wants is `gix_zlib::Decompress::{decompress(.., FlushDecompress::None), total_in, total_out}` (streaming-pack-parser line 15, verified). `compute_hash` drops an argument and a `Result` (deviation 3); `CommitResponse` picks one of two sibling definitions (deviation 4). All mechanical.
- Reliability 3/5 (was 2). The LATEST regression is dead by construction — nothing is overwritten, restore takes `max` over every list page, and `ok` cannot precede the `put`. Every crash window lands on unacknowledged loss. Held at 3 by: an isolate kill between `apply`'s committed span and `jobs::rearm(d)` strands `snap_pending` plus a `queued` SnapReindex with no armed alarm and no recovery path (crash walk-through); a corrupt or vanished newest snapshot wedges every fetch into a permanent 500 with no fallback to the second-newest key; and the SNAP_MAX rollback claim rides on a sibling fix that has not landed.
- Correctness 4/5 (was 3). The idea now does what it says: snapshot content is captured inside the commit span under the `refs_version` that span just bumped (section 3 step 5), HEAD/`peeled`/`repo_id`/`gc_epoch` ride the same JSON, and `SnapReindex` rebuilds object visibility from the live `r/<repo_id>/packs/` listing rather than trusting the snapshot. Deductions: `res.results.iter().any(|r| r.1.is_none())` (line 74) compiles only against one side of the sibling `CommitResponse` conflict; the 1.3 route table needs the awaits amendment the REGISTRY describes; and "cannot commit unbacked state" (lines 255, 286) is false until `respond` learns to throw.
- Effort: days. ~250 lines plus the listed write-backs (`list_page`, two `RepoDo` fields, the boot re-enqueue); the dependencies carry the real work.

## Contract compliance
Matches: REGISTRY block per A9 (two `JobKind` variants + dispatch arms, `snap/<owner>/<repo>/` prefix, `snap_pending` meta key, `list_page` write-back, two `RepoDo` fields); `enqueue`-in-span / `rearm().await`-after per A3 at both sites (lines 88+246, 127+110) — this module arms its own jobs correctly even though the sibling `fetch` still does not rearm at all; `spent_80pct` between units (A4, line 177); dead-job re-enqueue at boot per A4; `refs.peeled` per A5 (line 67); bound params <= 7 (A6); 16 MiB object cap per A7 (admitted line 261); `worker::Error` propagation and the A2 post-span `Err` path; no `set_alarm`, no `transactionSync`, no `Reflect`, no `ctx.id.name` key material (4.1, 8.3); `owner`/`repo` from `meta` (8.1/8.2); packs go `ingesting` -> `live` exactly as 2.3; `created_at = now` respects the 5.1 age gate; `insert_objects` <= 10,000 rows per call (1.2, lines 199, 227).
Deviations (each also in the structured list):
1. `/_do/push/commit`'s 1.3 row says "Awaits inside: none"; it gains two post-span awaits (`jobs::rearm`, `put_bytes`, lines 244-249), and every route gains a pre-dispatch `maybe_restore` await (line 235). Disclosed in REGISTRY (lines 15-17) and harmless — the mutation span is still atomic — but the route table itself must be amended; A9 registers additions, this edits an existing row.
2. `gix_zlib::Inflate::feed(win.get(at..)?, &mut data) -> st { consumed, done }` (lines 212, 217-220): no such method or fields in 0.1.0. `Inflate` is `once`/`reset` only; the resumable form is `gix_zlib::Decompress` as the sibling uses it. More than a rename — the type is wrong — but confined to the one call site the proof itself marked unverified (line 32).
3. `gix_object::compute_hash(kind, &data)` (line 222) drops the leading `gix_hash::Kind::Sha1` and assigns the returned `Result<ObjectId>` straight into `ObjRow.sha` with no `?`. Canonical form per server-side-rebase's review (deviation 4) and every other sibling: `compute_hash(H::Sha1, kind, &data)?`. Mechanical.
4. `res.results` is read as `Vec<(String, Option<&'static str>)>` (line 74) — repo-do-ref-authority's `CommitResponse` (its line 34). refs-sqlite-objects-r2 defines `results: Vec<RefResult>` (its line 52), under which `r.1` does not compile. Picks a side in the existing two-definition conflict (wasm-git-core review deviation 7); one definition must win.
5. `d.q`, `d.meta`, `d.sql`, `d.bucket`, `d.restored`, `d.pending_snap` are called from `src/jobs/snap.rs`; `q`/`meta`/`sql`/`bucket` are private `impl RepoDo` methods in repo-do-ref-authority (its lines 75-84). The REGISTRY discloses the two new fields but not the `pub(crate)` widening — same class as alarm-chain-ci's private-helper miss. Mechanical.
6. The claim "throws before any post-span await, and discards the commit span entirely" (line 255; "a failed span still rolls back", line 242) holds only if `respond`/`finish` re-throws `Storage`/`Internal` out of `fetch`. The shared helpers convert them to `Ok(500)` (info-refs-endpoint lines 80-95; auth-and-multitenancy lines 114-127), so the platform commits the span — the exact hole repo-do-ref-authority's review already filed (its deviation 4, blocker). As written, an over-`SNAP_MAX` snapshot leaves refs moved, `refs_version` bumped, the push `committed`, SnapPrune enqueued — and no snapshot: the precise "unbacked state" the module exists to prevent. Inherited; the fix is one line in `finish`.
7. `store::Bucket::delete(&stale)` (line 145) carries no `&mut ReqBudget` despite A1's every-R2-call-charged rule; the manual `subrequests_used += 1` mirrors two-phase-push (its line 169). Shared gap, not this proof's invention.
8. A snapshot failure reaches the client as HTTP 500, not the `unpack error snapshot: refs snapshot > 8 MiB` line Known limits claims (line 286): DO `Storage` -> 500 -> `from_do_response` -> the edge's `Err(e)` arm, which still returns non-200 after the receive header is parsed (two-phase-push review deviation 6). Inherited.

## First-pass blockers
1. LATEST pointer regression under interleaved pushes (input gate open during R2 awaits; conditional put result ignored): **resolved**. The pointer and its `onlyIf` etag are deleted outright; keys are immutable `snap/<o>/<r>/<v:020>.json`, content captured inside each commit's own span, and restore takes `max` over every page with no ordering assumption (lines 99-103). Whichever of two racing puts lands, the max key's content contains every earlier acknowledged move, and `ok` is issued only after `put_bytes` resolves (lines 244-249). Structural, not a check.
2. R2 prefix keyed on `ctx.id` defeats the namespace-recreate/class-migration scenario: **resolved**. The prefix derives from `meta.owner`/`meta.repo`, which are the `x-ge` headers (8.1/8.2) — identical for any DO behind `id_from_name("owner/repo")`. `ctx.id`/`ctx.id.name` are never key material (8.3), and `repo_id` — which `boot` regenerates on a wiped DO — travels inside the snapshot and is adopted back (line 123), keeping `r/<repo_id>/packs/` addressable.
Caveats from the first pass: HEAD/symrefs not snapshotted -> **resolved** (`Snap.head` restores `meta.head`; `peeled` rides the tuples, lines 66-67, 123 — noting the sibling still writes `peeled` NULL). Non-atomic pushes made atomic / under-populated report-status -> **resolved by dependency** (section 3's per-ref CAS; the snapshot only observes `any_ok`). Restore trusts objects still exist -> **resolved** (reindex lists the live `r/<repo_id>/packs/` prefix — a pack GC already deleted is simply absent and gets no row; restore only ever loads the newest key, whose refs are what GC marked). Prune `list` capped at 1000 -> **resolved** (300-key pages with `start_after`, `Continue` while all-stale). 2-3 added round trips -> **partially resolved** (exactly one `put`, no `head`, no pointer write; still one R2 RTT inside the serial commit, in Known limits). Title is fiction -> **not resolved** (emulated by immutable keys; now honestly stated in Mechanism). First-pass limits: O(#refs) per push kept under `SNAP_MAX`; commit-then-PUT window kept deliberately, now unreachable-by-ack; constructor CPU moved to a bounded pre-dispatch await.

## Crash walk-through
Kill inside the commit span (`commit_push` or `after_commit`): nothing is durable; the push stays `open`, Janitor 5.1 expires it at +1 h, 5.2 kills its `ingesting` pack, 5.3 deletes keys after GRACE. Clean. Kill inside `after_commit` after refs moved: identical — uncommitted span, nothing lands. Kill in the post-span awaits (rearm or `put_bytes`, lines 246-248): the commit is durable (refs moved, `refs_version` = v, SnapPrune + GcMark `queued`), `pending_snap` dies with the isolate, key v never exists, the client never saw `ok`. A later wipe restores v-1 and loses only the unacknowledged move — the declared loss side, now enforced by code shape. The queued jobs sit unarmed until the next moving commit's rearm; on a repo whose first-ever commit is the one killed, nothing ever arms them (same stranded class as below). Kill after `put_bytes` resolves, before `respond`: key v and the commit are both durable; the retry gets `ng ... failed to update ref`, correct. Kill during `maybe_restore`'s list/get awaits (lines 100-105): no writes yet; next fetch retries; transient R2 errors are retryable 500s. Kill between `apply`'s committed span and `jobs::rearm(d)` (line 110), or a rearm error there: `refs`+`meta`+`snap_pending` and a `queued` SnapReindex row are durable, `restored` died with the isolate, and the alarm was never armed. Every later fetch early-returns in `maybe_restore` (non-fresh, line 95) without rearming; `boot`'s A4 re-enqueue covers `dead` rows, not `queued`; `enqueue` dedups on the existing row. On a repo that only receives reads afterward, SnapReindex never runs: `ls-remote` is right forever and every fetch fails `not our ref` forever — the half-restored state this module exists to prevent. One-line fix: rearm whenever `snap_pending` is set (or rearm in `boot` when any row is `queued`). Kill inside `reindex_slice`: the `Cur` cursor sits on an entry boundary, rows are `ON CONFLICT DO NOTHING`, the `live` flip is `WHERE state='ingesting'` — a retry re-walks the current pack from `c.off` and converges. Kill inside `prune_slice` between `delete_multiple` and `Continue`: the keys are gone, the next firing re-lists the head. Clean.

## Concurrency walk-through
Two moving pushes A and B: commit spans serialize on the DO (platform-facts #4), so `refs_version` reads/bumps cannot collide; each writes its own immutable key after its span. There is no shared key and no pointer — the first-pass regression (B's `ok` stranded behind an older `LATEST`) cannot be expressed. `maybe_restore` on concurrent fetches: both see fresh, both list+get, both reach `apply`; the first span commits, the second's `looks_fresh` recheck no-ops (lines 117). Note the documented "push slips in during the restore awaits" race (line 115, Known limits line 284) is unreachable through the request path: every route is gated behind `maybe_restore`, so no `push_begin` can dispatch before some fetch's restore has completed — the recheck is harmless dead code, and the lost-race/overwritten-keys wrinkle it implies does not occur. SnapReindex racing a live push on the restored repo: `push_index` upserts the same `packs`/`objects` rows (`ON CONFLICT` dedups both ways), but if reindex's `WHERE state='ingesting'` flip lands before `commit_push` step 3, the push's live-check `UPDATE` matches 0 rows -> `Error::Conflict("pack not in state ingesting")` -> a spurious push failure the client sees as HTTP 409/500 (deviation 8); the retry is clean. Narrow, real. SnapPrune racing commits: it deletes only basenames strictly below `floor = pad(v - RETAIN + 1)` computed in the firing span (line 136); a key written mid-page is >= floor and is never in the stale set; the max key can never be pruned.

## Interop check
This module emits no wire bytes; a real git client sees: post-wipe `ls-remote` correct immediately including `HEAD ... symref-target:` (restored `meta.head`) and `peeled:` only to the extent the sibling populates the column (A5; refs-sqlite-objects-r2 still writes NULL — its own blocker). A `git clone` or `fetch` issued while `SnapReindex` is mid-walk gets `ERR upload-pack: not our ref <oid>` because `Index::lookup` joins `state='live'` — admitted (line 281), and a mirror `git push` does not self-heal since the client dedupes against advertised tips; reindex is the only repair, at ~pack_bytes/8 MiB reads plus inflate CPU, minutes for large repos. The snapshot-failure path the client sees is HTTP 500 with `the remote end hung up unexpectedly`, not the claimed `unpack error` text (deviation 8). R2 side: `start_after`/`cursor`/`truncated` bindings are verified in 0.8.5; lexicographic listing is S3-docs-claimed and unmeasured, but correctness never depends on it — restore scans every page for the max and `prune_slice`'s worst case is leftover keys (lines 99, 142-146).

## Blockers
- Does not compile as written: `gix_zlib::Inflate::feed`/`st.consumed`/`st.done` name a type that in 0.1.0 has only `once`/`reset` (the resumable API is `gix_zlib::Decompress`, sibling-verified); `compute_hash(kind, &data)` drops the `H::Sha1` argument and stores a `Result` in `ObjRow.sha`; `r.1.is_none()` compiles only against repo-do-ref-authority's `CommitResponse`; `d.q`/`meta`/`sql`/`bucket` are private helpers used cross-module. All mechanical, all at marked or single sites — but the crate does not build until they are reconciled.
- The SNAP_MAX guarantee is inverted under the code that exists today: `respond`/`finish` returns `Ok(500)` for `Storage`, so `fetch` commits the span — an over-limit snapshot produces a moved ref, a bumped `refs_version`, a `committed` push and no snapshot, which is precisely the "unbacked state" line 255 says cannot happen. Depends on the filed-but-unlanded repo-do-ref-authority deviation-4 fix (throw, not respond, on mid-span `Storage`/`Internal`).
- Stranded restore: a kill between `apply`'s committed span and `jobs::rearm(d)` (or a `rearm` error) leaves `snap_pending='1'` and a `queued` SnapReindex with no armed alarm and no path that ever arms it — every later `maybe_restore` early-returns, boot's re-enqueue skips non-`dead` rows, and `enqueue` dedups. On a read-only repo the restore never finishes. Rearm on `snap_pending` (or on any `queued` row in `boot`); one line.

## Caveats
- A corrupt or vanished newest snapshot is a permanent wedge: `bad snapshot {key}` / `snapshot {key} vanished` (lines 106-108) propagate out of every `fetch`, so every request 500s; there is no fallback to the second-newest key. Transient R2 failures retry cleanly; a bad key does not.
- Reindexed packs carry `push_id NULL`, so Janitor 5.2's join can never kill an `ingesting` row the reindex left behind — the documented "delete `snap_pending` to abandon" escape (line 282) leaks invisible rows.
- Pre-wipe `dead` packs are reindexed back to `live` (admitted, line 282): unreferenced objects resurrect until the next GC; never a loss.
- `restored` is per-isolate: every cold isolate on a still-fresh-looking DO (never-pushed repo) pays one R2 `list`; on a normal repo the hot path is one `SELECT`.
- `peeled` round-trips only once the sibling fills the A5 column; restored repos otherwise emit exactly what the foundation emits today.
- `store::Bucket::delete` lacks the A1 budget parameter (deviation 7); the `+1` manual charge matches two-phase-push.
- The "lost-race wipe" Known limit overstates the exposure: every route is gated behind `maybe_restore`, so the interleaving it describes cannot arise — the `looks_fresh` recheck inside `apply` is unreachable-but-harmless defense, and no cross-generation key overwrite can occur because of it.
- Unverified on real infra, all admitted: R2 list ordering/`start_after` behaviour, the DO-side subrequest limit (platform-facts #7), `web_sys::Crypto`/`ctx.id.name` in production (8.2/8.3), panic rollback (scenario 15). `git_zlib` aside, the API survey was honest — the one site it flagged unverified is indeed wrong.

## Verdict
lands-with-caveats. Both first-pass blockers are closed structurally rather than by a check: the pointer is gone, the locator survives namespace recreation, and `ok`-implies-snapshot is now enforced by response ordering inside the commit route. What remains is local and mostly inherited: one wrong gix-zlib type plus the `compute_hash`/`CommitResponse`/visibility compile reconciliations, the rollback claim that depends on the sibling's unlanded `respond`-throw fix, and a one-line rearm gap that can strand the restore it exists to complete. Reliability 2 -> 3, correctness 3 -> 4.

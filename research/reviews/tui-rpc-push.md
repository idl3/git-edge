# Second-pass review: Push from a sibling workspace DO over RPC, no HTTP

# Review v2: tui-rpc-push (idea #29)

## Scores
- Feasibility 4/5 (was 4). Every host call exists in `worker` 0.8.5: `Stub::fetch_with_request` (verified Worker->DO in the spike; the DO->DO direction is the same binding, unexercised specifically), `Request::new_with_init` + `RequestInit::{with_method, with_body}` (present in source, runtime-unverified, same caveat as two-phase-push), `sql().exec`/`to_array`/`one`/`changes()` (measured 1/0/1, platform-facts #1, #4), `Bucket::{read_range, read_entries}` (local simulator only, #6). `gix_object::compute_hash` ran on workerd with ids matching `git verify-pack` (spike correction 5); `CommitRef`/`TagRef`/`TreeRefIter` are CI-built for wasm32 (memo section 3) but the field names are unverified, and the code does not compile against its siblings as written (deviations 4-6) — all mechanical.
- Reliability 4/5 (was 3). The crash story is now the contract's, not bespoke: `pushes` row at `begin`, `packs` row `ingesting` before any R2 byte (A5 upsert), Janitor expires at `PUSH_TIMEOUT` and deletes after `GRACE` (5.1-5.3), `gc_epoch` re-guards the verify-to-commit gap (3 step 2). Residuals: an isolate kill mid-multipart leaves parts only a lifecycle rule removes (unverified, shared with two-phase-push), and the >10,000-row final index post strands a durable pack mid-flow — recoverable by a fresh-ids retry, but a real failure at the advertised scale.
- Correctness 4/5 (was 3). It does what the idea says in substance: objects go to R2 without `pack::ingest`, there is no git-HTTP endpoint, no pkt-line, and no edge hop; `commit_push` is the identical phase-two span. The tree builder now produces fsck-valid nested trees and `push_verify` re-walks the closure server-side. Deductions: "over RPC" is weakened to `fetch_with_request` on internal JSON routes (stated openly, line 8); verify is advisory and still trusts row `offset`/`len`/`kind` (no re-hash, line 101); the index-post accounting (deviation 6) fails at its own 10,000-file headline.
- Effort: weeks. The verify route plus vendored `codec`/`PackWriter` is days; landing needs two-phase-push and repo-do-ref-authority first, plus the two added harness scenarios (stock `git` cannot exercise this path, section 11).

## Contract compliance
Matches: one REGISTRY block (A9) declaring the single new route `POST /_do/push/verify`, no `JobKind`, no tables, no new key prefixes (lines 10-16); no pass A and no `pending/` key on this path (2.4, A10); section 3 ordering enforced by code shape — `finish` (line 185) -> final `sink.post` (line 186) -> `/_do/push/commit` (line 190); `packs` row `ingesting` before any R2 byte via `sink.post(&PackMeta::EMPTY, &[])` (line 175, A5 upsert); every R2/stub call takes `budget: &mut ReqBudget` (A1); `VERIFY_CHUNK = 64` equals A4's 64-coalesced-span cap; single-id `Index::lookup` calls, no `IN` lists (A6); 16 MiB cap enforced before hashing (A7, line 134); `VerifyDto`/`VerifyOut` in `wire::http` (A8); no `set_alarm` anywhere, `commit_push`'s `GcMark` enqueue is rearmed by the route wrapper (A3); `changes()` only, never `rows_written`; verify's SQL guard reads sit in a sync span before the first `read_entries` await, and the drain-resolve loop is the section-9 rounds shape.
Deviations (each also in the structured list):
1. `pack_id` is minted by the sibling, not "generated by the edge at push begin" (1.2). Acknowledged at line 245; same 32-hex format, and the A5 upsert's `WHERE state='ingesting' AND push_id=excluded.push_id` (two-phase-push line 139) keeps a guessed id off another push's row. Write-back.
2. `/_do/push/begin` body carries `principal` (line 149); contract 1.3's table says `{push_id}`. repo-do-ref-authority already extended it (`BeginDto{push_id, principal}`, its line 35) — the contract table is stale; shared deviation.
3. `VERIFY_MAX_LOADED = 100_000` (line 48) is a new limit section 12 does not list; `VERIFY_MAX_SEEN` at least reuses A5's `MAX_LINKS`. It is the binding budget guard anyway (~1,563 `read_entries` calls at the cap < 9,000, 7.1).
4. `PackWriter::create` has three shapes across the proofs: A1 says `create(bucket, key: &str, expected, budget)`; content-addressed defines `create(bucket, key: String, expected, budget)` (its line 75); two-phase-push calls it with three args and no `expected` (its line 65); this proof calls `create(bucket, &keys::pack(..), expected, budget)` (line 177) — `&String` where the sibling defines `String`. One definition must win before the crate compiles. Mechanical.
5. `CommitResponse` cannot be `stub_json`'s `T: DeserializeOwned`: it is `#[derive(Serialize)]` holding `Vec<(String, Option<&'static str>)>` (repo-do-ref-authority line 34); `&'static str` is not deserializable. This proof infers `T = CommitResponse` at lines 190-192 — the same latent defect the sibling's own `receive_pack` carries (its line 179). Mechanical: `Option<String>` plus `Deserialize`.
6. Index-post accounting is inconsistent with itself: `emit` derives `idx` from `rows.len()` (line 137), which requires `rows` to accumulate, but the "index posts of 10_000 rows inside the loops (elided)" (line 184) plus the final `sink.post(&meta, &rows)` (line 186) then post the whole accumulated vector in one call — and `push_index` refuses `rows.len() > 10_000` with `Error::Internal` (two-phase-push line 133). The proof's own 10,000-file example produces ~10,002 rows (10,000 blobs + trees + 1 commit). If instead the elided posts drain `rows`, every entry after the first batch gets a restarted `idx`, and `objects.idx` — the ordinal GcMark's per-entry bitmap indexes (5.1) — is wrong for most of the pack. Either reading is broken; the fix is a `sent` cursor and a `&rows[sent..]` tail post. Mechanical.
7. Literal: line 102's comment says a delta header yields `Storage`; `codec::entry_header` returns `Error::Internal` for it (content-addressed line 54). And `decode_entry` enforces the sibling's `MAX_OBJECT = 32 MiB` (its line 34) while this path enforces A7's 16 MiB — verify would accept an entry the sibling could never have written. Harmless direction.

## First-pass blockers
1. "Tree builder is fsck-invalid for nested paths (`fullPathname`)": **resolved**. `emit_level` (lines 196-217) recurses over maximal `component/` runs of the full-path byte-sorted `leaves`; full-path byte order is provably the per-level `name/`-for-dirs order (the first differing byte decides both comparisons identically), modes are `{:o}`/`40000`, entry bodies are raw `<mode> <name>\0<oid>`. Then `push_verify` re-parses every reachable tree and rejects out-of-order entries (`tree_key` >= check, line 122), so an fsck-invalid tree cannot reach a live ref even from a buggy sibling.
2. "1000-subrequest cap per invocation with no chunking design": **resolved** structurally — per-object PUTs/HEADs are gone; one multipart upload plus batched stub calls is ~20 calls for a 10,000-file workspace (line 224), and DO-side verify uses 64-span coalesced `read_entries` (A4). With the caveat that deviation 6 makes exactly that scale fail at the final index post as written — a different limit producing the same symptom.
Caveats from the first pass: GC/orphan race — resolved (pushes row at `begin`, `ingesting` row before any byte, Janitor 5.2/5.3, `gc_epoch` at commit step 2; the verify awaits open the gate but every check is re-guarded or advisory). Retry-returns-`stale` idempotency — partially resolved (`ng failed to update ref` plus a `GET /_do/refs` `target == new` confirmation is described at line 227 but not in the reference code). No fast-forward check — not resolved (same exposure as the HTTP path; section 12 builds none; acknowledged). Binary/exec/symlink — resolved (`FileEntry{data: Vec<u8>, mode}`, line 133). Implicit trust / dangling tree — partially resolved: missing ids now yield `{ok:false, missing}` and commit is never reached, but the route is advisory and still trusts row `offset`/`len`/`kind` (see Caveats). Cost/no skip-cache — resolved (one multipart; the `live`-set dedup skips every object already stored, so a one-file change writes one blob plus its ancestor trees).

## Crash walk-through
Sibling killed after `sink.post(&PackMeta::EMPTY, ..)` and before the first `upload_part`: `pushes` open, `packs` ingesting, zero R2 bytes. At +1 h Janitor 5.1 expires the push, 5.2 deletes the (zero) `objects` rows and marks the pack `dead`; at +2 h the deletes of `packs/<pack>.pack` and `pending/<push>.pack` are no-ops (neither key was ever written on this path). Clean. Killed between `create_multipart_upload` and `finish`: the incomplete upload is orphaned until the bucket's abort-incomplete-multipart lifecycle rule (unverified, #6; storage cost only); the rows die with the push. Killed after `finish` but before the tail post: durable pack, `packs` row `ingesting` with stale meta, partial `objects` rows — invisible to every reader (2.3 joins `state='live'`); Janitor cleans it at +1 h/+2 h. Killed between `{ok:true}` and `commit`: identical; the pack was verified but never referenced. Repo DO killed mid-verify: `push_verify` writes nothing anywhere; the sibling re-issues it. Commit applied but the response lost: the ref moved; the retry gets `ng failed to update ref` and the sibling confirms via `GET /_do/refs` — described, not coded.

## Concurrency walk-through
Two sibling pushes to the same branch: both `begin` (two open pushes, same `gc_epoch` snapshot), each writes its own pack and verifies it; `commit_push` serializes — the first `UPDATE refs ... WHERE target=?` wins, the second gets `ng ... failed to update ref`. The loser's pack is still flipped `live` in step 3 before its command fails — an inherited contract behaviour (its unmarked entries are dropped by the next `GcConsolidate`), not new here. A `GcSweep` inside verify's `read_entries` awaits: the gate is open, the sweep runs and bumps `gc_epoch`; verify may still return `{ok:true}` (it is read-only and advisory) but commit step 2 rejects the push — never accepted with a hole, the section 5 analysis verbatim. The Janitor cannot race a live verify: 5.1 needs `began_at < now - 1 h` and a request dies at `max_ms` 240 s (7.1). Two concurrent verifies interleave harmlessly — all state is locals.

## Interop check
No git wire bytes exist on this path; stock `git` can never reach it — the two added scenarios (nested paths + exec + symlink with `fsck --strict`; hand-built pack with a dangling blob returning `{ok:false, missing}`) are the right harness substitute section 11 permits. What a later clone sees: entries written by `codec::encode_entry` are byte-identical to what `pack::generate` copies verbatim into outgoing packs (2.1), so `index-pack` accepts them. The hand-rolled git bodies are correct: `tree %s\nparent %s\nauthor %s\ncommitter %s\n\n<msg>` (lines 162-165), modes `100644`/`100755`/`120000` via `{:o}` and `40000` for dirs, NUL-terminated names plus raw 20-byte ids. Residual fsck exposures: verify never re-hashes, so a wrong-offset `ObjRow` lands a live ref that serves bytes failing `index-pack`'s sha check (a corrupt clone); a `files` table holding both `a` and `a/b` slips the order check (`tree_key("a") < tree_key("a/")`) and fsck reports `duplicateEntries`; `CommitRef`/`TagRef` strictness on missing `author`/`committer` headers is unverified (the builder emits both, so self-generated commits are safe).

## Blockers
- Index-post accounting (deviation 6): `emit`'s `rows.len()`-as-`idx` and the whole-vector final `sink.post` cannot both be the intent. As written, a >10,000-object push — the advertised 10,000-file case — fails at `push_index` after the pack is durable; the alternative reading corrupts `objects.idx` and misleads GcMark's bitmaps. Mechanical fix, but it sits on the headline path.
- `CommitResponse` is not `DeserializeOwned` (deviation 5): `push_snapshot`'s final `stub_json` call does not compile against the sibling DTO — and neither does the sibling's own `receive_pack`. `Option<String>` + `Deserialize`, one line.
- `PackWriter::create` shape (deviation 4): `&String`/`String`/`&str` and 3-vs-4 args across A1, content-addressed, two-phase-push, and this proof. One of them must change before the crate compiles.

## Caveats
- `push_verify` trusts the sibling-posted `ObjRow`s: `_id` is ignored (line 101), so the decoded bytes are never re-hashed against the claimed sha, and the structural filter uses the row's `kind` (line 93) rather than the decoded kind — a `Blob`-labeled tree is never walked, so its subtree is never closed. Both are one-line fixes (`compute_hash(kind, &data) == id`, classify after `decode_entry`); they matter only against a buggy in-account caller.
- Advisory by design: `commit_push` does not require verify, so a sibling can skip it and land a dangling tree anyway (a missing *tip* is still caught by `apply_one`'s liveness check). Making it mandatory is a `pushes.verified_at` write-back the proof explicitly defers (line 244).
- Identical retry inside the same millisecond: the commit id is already `live`, `expected` undercounts by one, `finish` aborts on the count check — an `Internal` instead of `ok`. Narrow.
- `e.oid` in `TreeRefIter` items is `&'a ObjectId` — `out.push(e.oid)` (line 124) wants a deref; all the gix-object 0.64.1 field names (`c.tree`, `c.parents`, `e.mode.is_tree`, `e.filename`, `TagRef::target`) are pinned at compile but unverified, as the proof says.
- Unverified at runtime, same list as the siblings: `RequestInit` JSON-body path, `web_sys::Crypto` id generation (8.2), `script_name` cross-script binding and the shared R2 binding (GA per docs, not re-measured), real-R2 multipart and the abort-incomplete-multipart lifecycle rule (#6), the DO subrequest limit unenforced locally (#7).
- `CommitResponse.results` is never inspected by the reference caller — the `ng`-vs-`ok` distinction and the retry confirmation are prose only.
- "No HTTP" is now "no git-HTTP endpoint, no pkt-line, no edge hop" over `fetch_with_request` JSON routes — the weakening is honest (memo section 1, workers-rs #720) but the title's mechanism is the weakened one.

## Verdict
lands-with-caveats. Both first-pass blockers are closed structurally rather than by a check — real nested trees plus a server-side closure walk, and ~20 subrequests instead of ~20,000 — and crash/GC handling now rides the contract machinery wholesale (`PUSH_TIMEOUT`, `GRACE`, `gc_epoch`), which is why reliability moves 3->4. What remains is local: the index-post accounting that breaks the advertised scale, two mechanical signature reconciliations across proofs, and verify's residual trust in row `offset`/`len`/`kind` — none of it a design change. The one honest concession is the transport: typed RPC became internal JSON routes, and the proof says so.

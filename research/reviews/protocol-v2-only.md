# Review v2: protocol-v2-only (idea #3)

## Scores
- Feasibility 4/5 (was 4). Every API in the shown code exists in the pinned crates; I read the sources in `~/.cargo/registry`: `gix_packetline::blocking_io::encode::band_to_write(kind: Channel, data: &[u8], out: impl io::Write)` (the proof's "unverified" caveat is closed, order is as written), `data_to_write`/`error_to_write`/`flush_to_write`/`delim_to_write`, `decode::streaming` returning `Stream::{Complete{line,bytes_consumed}, Incomplete{..}}` and erroring on `0003`/`0004`/length > 65520, `Channel::{Data=1,Progress=2,Error=3}`, `ObjectId::{from_hex(&[u8]), null(Kind)}`, `worker::Headers::get -> Result<Option<String>>` (so `.ok().flatten()` is right), `Response::from_stream`. The encoder enforces `prefix+data <= 65516`, so `MAX_BAND_DATA = 65515` is exactly the limit, not an estimate. No compile errors found; byte-string patterns on `&[u8]`, tuple coercion in `unwrap_or`, disjoint field borrows in `PktReader::next` all type-check. Still unverified: `DecompressionStream` -> `wasm-streams` bridge (section 6.1), `Response::from_stream` at runtime, production behaviour of an unread request body.
- Reliability 4/5 (was 3). Stateless module; the first-pass skew (DO answer vs rebuilt `latest.pack`) is gone because packs are immutable per `pack_id` and `Index::lookup` filters `state='live'`. Remaining hole: early returns that leave the body unread (below).
- Correctness 4/5 (was 2). I walked git 2.43 `fetch-pack.c`/`connect.c`/`remote-curl.c` against every byte the code emits on the happy path (clone, incremental fetch, ls-remote v2/v0/v1, empty repo): no breaking byte. Both first-pass fatal bytes are fixed by code, not prose. Deduction: error reporting on 4xx is invisible to git (below), which makes scenario 13 unpassable as worded, and the `blob:limit=1m` claim is wrong in the harmless direction (git expands it to `blob:limit=1048576` before sending, so it works).
- Effort: weeks. `wire` alone is days; `upload_pack` cannot be exercised without `fetch_v2` and `BodyReader`, and the conformance matrix is the real cost.

## First-pass blockers
1. "acknowledgments always emitted, every clone dies": resolved by code. `if !args.done { w.text("acknowledgments")?; ... w.text("ready")?; w.delim(); }` (proof line 148-153); after `done` the first section is `shallow-info` or `packfile`, matching `FETCH_GET_PACK`. `ready` -> delim, no `ready` -> flush matches `process_acks` exactly.
2. "v0 shim lacks multi_ack_detailed, clone-only": resolved by removal. `if !matches!(proto_of(&req), Proto::V2) { body.fill(1 << 20).await?; return Err(Error::Protocol("protocol v2 required (git >= 2.26)")) }` (line 170-173), contract rule 7 and section 12. Genuine, but see the interop note: the text never reaches the user.
3. "gzip bodies parsed raw": resolved by dependency. `let mut body = BodyReader::new(&req)?;` (line 169) precedes `parse_v2_command(body.buffered())`; the decode is section 6.1's, whose `wasm-streams` bridge is unverified. Nothing here parses the raw stream.
4. "wants never validated": not resolved by code shown. `parse_fetch` only refuses an empty want list (line 110); the `Index::lookup` + `ERR upload-pack: not our ref` is section 9 step 1 inside `fetch_v2` (want-have-negotiation). Contract-bound, so acceptable, but this proof owns none of it.
First-pass caveats: array-spread framing -> `chunks(MAX_BAND_DATA)` + `band_to_write` straight into `out` (line 57), resolved; pack/etag skew -> immutable `pack_id`, resolved by contract; advertise-only-honoured -> exact rule 6, resolved; `symref-target:` -> line 122, resolved; `peel`/`unborn`/`symrefs` -> `parse_ls_refs`, resolved.

## Crash walk-through
Clone: `fetch` with `want X`, `done`. Edge parses, forwards to `/_do/fetch`; the DO streams `packfile\n` + band-1 frames; the edge isolate dies 40% through. Server: no row, no key, no alarm touched (this path never writes). Client: the demuxer sees EOF before the rule-3 trailing flush, `index-pack` reports `early EOF`, `git clone` fails cleanly and a retry succeeds. Because the flush is written only after the last frame, a truncated body can never be mistaken for a complete pack. Crash between `parse_v2_command` and the stub call: nothing anywhere. Crash inside `/_do/ls-refs`: a read-only sync span, rolled back trivially.
The hole: a v2 body over 1 MiB returns `Err(Protocol)` at line 174 with the stream unread, and a v0 POST over 1 MiB is drained only to 1 MiB (line 171). Both reproduce the pattern the spike's `dev.log` shows crashing local workerd ("Can't read from request stream after response has been sent", runtime restarted twice). Production is unmeasured; the fix is `web_sys::ReadableStream::cancel()` on every early-return path instead of a bounded drain.

## Concurrency walk-through
Fetch round 1 `ls-refs` says `main=A`; a push moves `main` to `B`; round 2 `fetch want A`. `commit_push` and `list_refs` are sync spans in one DO, so round 1 saw either all or none of the push. `A`'s pack stays `live` until `GcMark` (10 min quiet) -> `GcConsolidate` -> `GcSweep`, and only packs with `created_at < started_at - GRACE` are candidates; a two-round fetch lasts seconds, so `Index::lookup` finds `A` and serves it (git's expected "one commit behind"). A fetch that starts 70+ min after a force-push gets `ERR upload-pack: not our ref`, which is what git itself does. Two concurrent fetchers never contend: two sync SQLite reads per fetch, streaming in the edge. Nothing here writes refs, so no split-brain is possible.

## Interop check
Walked against git 2.43 with `protocol.version=2` (default). Advertisement: `# service=git-upload-pack`, flush, `version 2`, `agent=`, `ls-refs=unborn`, `fetch=shallow filter`, `object-format=sha1`, flush: `discover_version` accepts it; the spike already ran this to a real client. `ls-refs`: HEAD first with `symref-target:`, `peeled:` on annotated tags, `unborn HEAD symref-target:refs/heads/main` only when `unborn` was sent: `process_ref_v2` parses all three. Every argument git 2.43 sends is accepted: `thin-pack`, `no-progress`, `include-tag`, `ofs-delta`, `want`, `have`, `done`, `shallow`, `deepen`, `filter blob:none|blob:limit=N`; `sideband-all`, `want-ref`, `packfile-uris`, `wait-for-done`, `session-id` are only sent when advertised, and `agent=`/`object-format=` capability lines are ignored as they must be. Response: v2 always sets `use_sideband = 2` (fetch-pack.c `FETCH_CHECK_LOCAL`), so band-1 pack + trailing flush is right; `ready` then delim satisfies "expected packfile to be sent after 'ready'"; NAK then flush satisfies "expected no other sections". No breaking byte on the happy path.
The byte that breaks a stated scenario is the HTTP status: remote-curl's `rpc_in` discards the body when `response_code >= 300` (`if (response_code >= 300) return size;`), so the `ERR protocol v2 required (git >= 2.26)` pkt-line in a 400 is never seen; the user gets `error: RPC failed; HTTP 400 curl 22 The requested URL returned error: 400` followed by a fetch-pack die on EOF. Not a hang, but scenario 13's asserted text cannot appear, and the same applies to `ERR upload-pack: not our ref` if section 10 maps it to 400. Real git emits `ERR` in a 200 body; section 10's "Protocol -> 400 ... one pkt-line ERR" is wrong for git-protocol POSTs and must become 200 + `ERR` (keep 400 for pre-handshake garbage).

## Blockers
- Section 10 / rule 7 status code: `ERR` pkt-lines on a 4xx are dropped by `rpc_in`; scenario 13 and section 9's `not our ref` need HTTP 200 + `ERR`. One-line contract amendment plus the `edge::respond` mapping for `Error::Protocol` raised after the command section parsed.

## Caveats
- Early-return paths (v2 body > 1 MiB, v0 body > 1 MiB) leave the request stream unread; locally that restarts workerd. Cancel the stream instead of draining.
- Want validation and gzip decoding are contract dependencies (`fetch_v2`, `BodyReader`), not code in this proof; `wasm-streams`/`DecompressionStream` remain unverified per the memo.
- `ready` on the first known have (section 9 step 2) sends superset packs on long divergent histories; protocol-legal, contract-sanctioned, but not git's `ok_to_give_up`.
- `blob:limit=1m` does work (git sends the expanded byte count); the Known-limits line is wrong but harmless. `tree:`, `sparse:`, `combine:` do 400 as stated.
- `info/refs` glue (Content-Type `application/x-git-upload-pack-advertisement`, `Cache-Control: no-cache`) is not shown; `check_smart_http` rejects a wrong Content-Type. Owned by info-refs-endpoint.
- `PktWriter::response_end` missing from the impl; rule 3 wording (two delims) should be corrected in CONTRACTS.md.
- `RefRow.peeled` is never computed by any sync route (refs-sqlite-objects-r2 says so); scenario 3's peeled line depends on a schema addition.

## Verdict
lands-with-caveats. Genuinely better than the first pass: correctness 2 -> 4 (both fatal bytes fixed by code I could trace to `fetch-pack.c` behaviour), reliability 3 -> 4 (skew removed by immutable packs), feasibility held at 4 with the `band_to_write` caveat now closed against source. Three of four first-pass blockers resolved by code or by the contract's removal of the v0 shim; the fourth (want validation) is delegated, not proven. The one open item is a contract defect this proof inherits, not a design flaw: git-protocol errors must ride a 200.

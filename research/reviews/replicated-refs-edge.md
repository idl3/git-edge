## Scores
- Feasibility 4/5 (was 4). Every new host call exists in `worker` 0.8.5: `Env::kv("REFS_KV")` -> `KvStore::{get(&str) -> GetOptionsBuilder, put<T: ToRawKvValue>(&str, T) -> Result<PutOptionsBuilder, KvError>}`, `GetOptionsBuilder::{cache_ttl(u64) (floor 60, KV_TTL_S right), json::<T: DeserializeOwned>() -> Result<Option<T>, KvError>}`, `PutOptionsBuilder::execute`, `ObjectNamespace::get_by_name_with_location_hint(&str, &str) -> Result<Stub>` (durable.rs docs, matches the glue at lines 141-144). But `put` is generic: `Vec<u8>` takes the blanket `impl<T: Serialize> ToRawKvValue` (`kv/mod.rs:260-275`), which runs `serde_wasm_bindgen::to_value` then `JSON::stringify` for non-scalars — the stored value is a JSON array of byte values, not the snapshot text, and `json::<Snapshot>()` can never parse it. Compiles, stores, never serves. Cross-proof drift is mechanical (below). KV from a DO alarm context and local-workerd KV semantics: unverified, admitted.
- Reliability 4/5 (was 3). The two first-pass holes are closed structurally: `refs_published` cursor replaces the `dirty` flag, enqueue rides inside the commit span (no dangling `getAlarm().then(setAlarm)`), the post-await recheck + `Reschedule` covers a commit during the put (dedup against the `running` row is exactly 4.5), and `publish_boot_check` heals a crash between span and rearm. Residual: a kill inside the single await strands the job `running` forever and dedup then blocks every heal path — narrower than before, same indefinite-staleness outcome — and the heal-on-read path rests on a rearm no sibling performs.
- Correctness 4/5 (was 3). Delivers the honest remnant of the idea: edge-rendered `ls-refs` and v0 advertisement, byte-identical through the shared `wire` writers, stale-only-old semantics, DO fallthrough on every KV failure. Deductions: the `put` encoding makes the feature dead code as written; the v0 arm hardcodes the version floor to 0; scenario (b) does not exercise the heal path it claims to.
- Effort: weeks. This file is days; it lands only on a working `commit_push` + `upload_pack` + `info_refs` (repo-do-ref-authority, protocol-v2-only, info-refs-endpoint) plus the contract deltas and a `kv_namespaces` binding.

## First-pass blockers
1. "Lost-publish race in `alarm()` and no alarm re-arm after crash: KV can stay stale indefinitely": **partially resolved**. The dirty flag is gone — `refs_published` cursor + in-commit-span enqueue + post-await recheck (lines 69-93) close both named races without a check. But a kill between the `execute()` await (line 84) and the outcome-apply span leaves the `jobs` row `running`: 4.2 selects `state='queued'` only, A4's boot rule covers `dead` jobs and Janitor-when-absent, nothing resets `running`, and 4.5 dedup — the property this design leans on — then blocks every future enqueue, including `publish_boot_check`'s. KV then serves the pre-crash snapshot to `min=0` clients forever. Narrower window, same unbounded outcome, and line 151's "lost publish cannot recur" is thereby wrong.
2. "CAS rejection throws out of `updateRefs` ... 500 on any non-fast-forward" / all-or-nothing rollback: **resolved by dependency**. Contract 3: per-ref CAS via `changes()`, `ng <ref> failed to update ref` per ref in client order, `atomic` not advertised (rule 5). Nothing here touches ref writes.
3. "`HEAD`/`symref-target` absent: `git clone` cannot check out": **resolved**. `Snapshot.head` carries `meta.head`, `Snapshot.refs[].peeled` the A5 column; `write_ls_refs` emits `symref-target:`/`unborn` (protocol-v2-only lines 121-127, spike-tested against git 2.43).

Caveats from the first pass: `pkt()` UTF-16 length -> resolved structurally (gix-packetline computes byte lengths; names are `BString` end to end). `ref-prefix`/`unborn` ignored -> resolved via `write_ls_refs`; an empty repo never publishes (`refs_version` 0 == `refs_published` 0) so the DO answers. v2 `info/refs` routed to DO -> resolved (static since rule 6 / info-refs-endpoint); the v0 advertisement now tries KV first; receive-pack's stays on the DO, correctly, since its oids feed the CAS. Read-your-writes needs `http.extraHeader` -> inherent, unchanged. KV is pull-through not replica -> inherent, stated. GC grace vs KV lag -> resolved by contract: GRACE 1 h vs ~120 s worst staleness (section 5). `locationHint` creation-time only -> kept honest, now code-backed via `GE_DO_HINT` (`get_by_name_with_location_hint` verified in 0.8.5 docs, unverified at runtime).

## Crash walk-through
`dispatch` marks the RefPublish row `running` (committed when the pre-slice span ends, at latest when the put await opens the input gate), span 1 reads `refs_version`/`refs` atomically. Kill during the `execute()` await: KV may or may not hold the value; `refs_published` is not advanced (span 2 never ran); the row is left `running`. Nothing in section 4 returns a `running` row to `queued` — 4.2 selects `queued` only, 4.4 fires on a returned `Err`, A4's boot rule re-enqueues `dead` jobs. Every later `enqueue(RefPublish)` — commit step 7 or `publish_boot_check` — dedups against the stranded row. Publish stops permanently; a well-formed snapshot is served stale to stock clients indefinitely. Orphaned: nothing but the row. Cleaner: nobody; the fix is a stale-`running` reset (server-side-rebase's Janitor write-back fails `running` rows older than `PUSH_TIMEOUT`; the same one-liner belongs in `publish_boot_check`). Kill mid-span-2: span atomicity rolls back the `refs_published` write; same stranded-row outcome. Kill between the commit span and the post-span `rearm`: the `queued` row survives; the next request's `boot` + `publish_boot_check` finds `refs_version > refs_published`, dedups against the `queued` row, and the caller's `rearm` arms it — provided the route rearms at all (deviation 4). Edge-side kill mid-request: stateless, nothing durable, retry is idempotent.

## Concurrency walk-through
Push B's `commit_push` runs during A's put await (input gate open): B bumps `refs_version` and its `enqueue` dedups against A's `running` row (4.5); A's span 2 sets `refs_published=v_A` under the `CAST` guard, sees `refs_version > v_A`, returns `Reschedule(now + 1 s)`; the burst coalesces into one more put that captures v_B's whole-table snapshot. Two pushes inside one debounce window: first enqueue wins, second dedups; the slice publishes both. A `GET /_do/refs` arriving during the await runs `boot` -> `publish_boot_check` -> enqueue, deduped, harmless; `rearm` there computes `MIN(run_at)` over `queued` only — no alarm is lost because dispatch rearms after applying the outcome. Janitor/GC slices share the dispatcher as different kinds; `rearm` takes the minimum across all. `GcSweep` racing a publish touches neither `refs` nor `meta.refs_version` ordering — a snapshot is simply version v whenever span 1 ran; stale is old, never torn.

## Interop check
git 2.43-2.47: `GET info/refs` v2 is the static rule-6 advertisement at the edge; `POST git-upload-pack` `command=ls-refs` is rendered from the snapshot by the same `write_ls_refs` the DO path uses, so `symref-target:`, `peeled:`, `unborn HEAD symref-target:` and `ref-prefix` filtering are byte-identical by construction (spike-measured). `fetch` always reaches the DO and `Index::lookup`; a stale advertisement can only name old-but-live objects (GRACE 1 h vs ~120 s staleness). The byte-level defect: `kv.put(&key, body)` with `body: Vec<u8>` stores `JSON::stringify(serde_wasm_bindgen::to_value(&body))` = `"[123,34,118,...]"`; the reader's `type:"json"` get parses it into a JS array and `serde_wasm_bindgen::from_value::<Snapshot>` fails, `kv_snapshot` returns `None`, and every request falls through — `x-git-edge-source: kv` can never appear. The proof's own failure policy converts the bug into silence: no error, `refs_published` advances, feature dead. `put_bytes(&key, &body)` (+ read `.bytes()`/`serde_json::from_slice`) or `put` of a `&str` (`serde_json::to_vec` output is UTF-8) fixes it in one line. `protocol.version=0 ls-remote` gets the KV-rendered v0 advertisement (floor ignored, deviation 6); a v0 POST still gets the rule-7 400 (scenario 13). Receive-pack `info/refs` correctly stays on the DO — a stale advertisement there turns legal fast-forwards into spurious `ng`. `Content-Type: application/x-git-upload-pack-result` is right for the POST.

## Blockers
- `kv.put(&d.kv_key()?, body)` (line 83) stores a JSON byte-array, not the snapshot text; `json::<Snapshot>()` (line 102) can never parse it. As written the publish path stores unreadable bytes and the read path is permanently a miss — the feature is inert, silently. Mechanical fix (`put_bytes`, or `put` a `String`/`&str`).
- A `running` RefPublish row stranded by a kill between the put await and the outcome span is unrecoverable: 4.5 dedup blocks every future enqueue and `publish_boot_check` alike, so KV serves the frozen snapshot to `min=0` clients forever. Needs a stale-`running` reset (`publish_boot_check` or the Janitor; contract section 4 has none — a shared gap, but this module's failure mode is silent staleness rather than a loud one).
- Deviation 4 is load-bearing: heal-on-read requires `jobs::rearm().await` after the boot span on every DO route; repo-do-ref-authority's `fetch` shows no `rearm` and the write-back list does not add it.

## Caveats
- Signature drift to reconcile: `upload_pack` needs `env`/`budget`; `RefDto` must actually live in `wire::http`; `meta_i64` is used by two proofs and defined by none. All mechanical.
- `CommitResponse.refs_version` needs a `SELECT` after the step-5 bump inside the commit span; the write-back does not say where the value is read.
- Scenario (a) needs a pre-existing published snapshot for "plain ls-remote shows the old tip" (a first-ever push leaves KV empty, so plain ls-remote falls through and shows the *new* tip). Scenario (b)'s second half exercises the commit's own enqueue, not `publish_boot_check` — nothing simulates the lost alarm it exists for.
- Unverified, admitted or inherited: `Env::kv` inside a DO alarm context; local-workerd KV TTL/propagation (no platform-facts row covers KV); `get_by_name_with_location_hint` at runtime; the `RequestInit` stub-request path (as every sibling); `transactionSync` absent, span atomicity on the no-await rule alone (A3).
- 25 MiB cap path advances `refs_published` without a put — silent DO-only operation, detectable only via the missing `x-git-edge-source: kv`.
- KV get is charged against `ReqBudget` though 7.1 names only Bucket/stub calls — conservative, not a defect.
- KV key is name-derived (`refs/<owner>/<repo>`); a repo rename (out of scope, section 12) strands the old value while R2 keys on `repo_id` survive (8.4) — stated.

## Verdict
lands-with-caveats. Genuinely better than the first pass: the dirty-flag race and the crash-without-rearm hole are closed by construction (version cursor, in-span enqueue, dedup-aware recheck, boot check), the HEAD/peeled/unborn omissions are gone, and both weakenings (pull-through not replica, creation-time hint) are stated rather than hidden. What remains is concrete and small: one `put` call that writes bytes no reader can parse, one stranded-`running` state the dedup rule makes unhealable, and a rearm obligation that must be made explicit in the write-backs. Reliability 3->4; correctness 3->4.

# Review v2: search-index-on-push (idea #26)

## Scores
- Feasibility 4/5 (was 4). Every host call exists in the pinned versions: `SqlStorage::exec`/`SqlCursor::to_array` (spike), `jobs::{enqueue, SliceOutcome, dispatch}` (section 4), `Index::lookup`/`Bucket::read_entries(&[(ObjectId, ObjLoc)], &mut ReqBudget)`/`codec::decode_entry` (1.2, A1, sibling-verified), `Stub::fetch_with_request` + `stub_json` (two-phase-push), `Response::from_json`, and `worker::Url::query_pairs` — which the proof flags unverified but is in fact on the 0.8.5 `Url` docs page, so that nit downgrades to nothing. The one load-bearing unknown is unchanged: FTS5 in DO SQLite (`CREATE VIRTUAL TABLE`, `MATCH`, `bm25`, `snippet`, `DELETE ... WHERE <column>`) is documented by Cloudflare but never exercised by the spike or platform-facts; the proof says so itself (line 266). gix-object 0.64.1 `EntryRef.oid` is `&oid`, so `Ent { oid: e.oid }` (line 124) does not compile — mechanical.
- Reliability 3/5 (was 3). The deterministic failures are gone: the livelock is replaced by table-held work state plus a `(path, blob_sha)` done-check, and poison blobs degrade to empty-body rows. But the crash walk-through finds two live holes: the frontier-row `DELETE` commits one span before the awaits it feeds (lost subtree diff), and a mid-slice isolate kill leaves the `jobs` row `running`, which section 4 never re-selects — the index then stops forever.
- Correctness 4/5 (was 3). For `meta.head`'s branch it is now a real index: tree-diff adds and deletes, resume cursor, convergence via `finish`'s reschedule, injection-safe `MATCH` quoting. Deductions: the kill-window lost-subtree hole, the duplicate-sha `find` quirk in `drain_todo`, and `meta.head` being `refs/heads/main` by construction (8.2) so `master`-only repos index nothing.
- Effort: days. Two tables, one `run_slice` arm, two routes; the real cost is the day-1 FTS5 check and the declared foundation edits.

3. `Ent { oid: e.oid }` (line 124): `gix_object::tree::EntryRef.oid` is `&'a oid` in 0.64.1, not `ObjectId`; needs `.to_owned()`. Compile error, mechanical.
4. `search()` calls `jobs::enqueue` inside the `/_do/search` sync span (line 210) and no `jobs::rearm` follows (A3: "every async route or slice that called `enqueue` must call `jobs::rearm(&self).await` after its sync span"). `branch-level-dos`'s write-back assumes a shared post-span rearm on the commit route; this route needs the same convention and no shown code provides it.
5. `Error::Unpack` for tree/commit parse failures inside a job (lines 123, 134): section 10 defines `Unpack` as the receive-pack report-status variant; in a job it only colours `last_error`. Cosmetic.

## Crash walk-through
Spans are the unit. Kill inside `drain_todo`'s `read_entries` await: the pre-await span (per-row done-checks, oversized/empty upserts, `del_todo` for decided rows) committed as a unit; the `want` rows are still in `search_todo`, so the next slice re-issues at most one 64-entry `read_entries` — bounded redo, no double writes because `upsert` is a `DELETE`+`INSERT` (lines 188-191). Kill in the post-await upsert span: the whole span rolls back, the batch re-runs. Both clean.
Kill during the `load_tree` awaits (lines 76-78): **not clean.** `DELETE FROM search_frontier WHERE rowid=?` (line 75) ran in the previous span and is already durable; the subtree's diff never executes. Its added paths are never queued in `search_todo` and its deleted paths keep their `blobs_fts` rows — and `finish` still writes `search.tip = new`, so the hole is permanent and silent. One-line fix: delete the frontier row inside `diff`'s span, after the loads.
Kill inside `finish`'s span (lines 195-198): all-or-nothing. If it committed but the outcome was never applied, the row keeps the old cursor with empty tables; the next firing's `(Some(Ok), false)` falls to `begin`, sees `search.tip == head`, returns `Done` — self-healing. If it rolled back, `begin` re-diffs from the old tip; tree reads redo (~2 `read_obj` per frontier row) while blob reads are skipped by the done-check — wasteful, bounded.
Kill anywhere mid-slice, the real problem: `dispatch` marks the job `running` before the slice (4.2); a kill is not an `Err`, so 4.4's retry ladder never runs; the next firing selects `state='queued'` and skips it; every later `enqueue` dedups on the `running` row (4.5); `boot` repairs only `dead` kinds (A4). IndexPush never runs again, `search.tip` freezes, and the `search` route's own enqueue (line 210) dedups too. Orphaned `fts` rows from the aborted attempt can additionally survive when head moves past the skipped tip before any resume — a path that existed only in that tip is never re-diffed and never deleted. Both are contract-level (section 4 owns the row lifecycle), but this proof's resume guarantee rests on them; scenario 17 is exactly this test.

## Concurrency walk-through
Push lands while IndexPush runs: its `enqueue` dedups on the `running` row (4.5); `finish` re-reads the live `refs` target in its sync span and returns `Reschedule { run_at: now }` (lines 196-198); A4 clears the cursor; the next firing's `begin` diffs written-tip -> new head. Converges in one alarm round-trip. Push lands in the `finish`-span-to-outcome-span gap: `enqueue` dedups on the still-`running` row, `Done` then deletes it — the new head is unindexed until the next push or a `search` call (line 210 covers it). Sub-millisecond window, self-healing via the read path.
`GcSweep` mid-walk: if the captured old tip's pack is swept, `read_obj` gets `Storage` -> 4.4 retries at `min(30 s * 2^n, 1 h)` -> `dead` after 8 -> A4 re-enqueue -> `begin`'s liveness check (line 90) now misses and rebuilds. If the old tip stays live, 2.5's closure makes every reachable object live, so the proof's "a miss is impossible" (line 139) holds — but only in that arm; the proof does not distinguish them. A swept pack's R2 bytes persist for GRACE = 1 h (5), longer than any 20 s slice, so a read already issued still completes.
`search` during a running job: sync reads against sync writes, gate opened by the job's awaits; partial index visible by design, signalled by `indexed != head` in the response (line 217). Two concurrent `search` calls on a lagging index both enqueue; dedup leaves one row. No write-write conflict anywhere: the job owns `search_frontier`/`search_todo`/`blobs_fts`, `search` owns only its `jobs` insert.

## Interop check
No git wire surface: push and fetch byte streams are unchanged, so git 2.43/2.45/2.47 are unaffected and scenarios 2, 4, 14 stand. The new surface is `GET /:o/:r/search?q=` behind the section-12 Basic credentials, returning JSON `{indexed, head, hits:[{path, snip, rank}]}` — section 11's "not exercisable by stock git" clause applies and the proof correctly drives it with `curl`. FTS5 specifics: `MATCH ?` receives only double-quoted whitespace-split phrases, so no user byte becomes FTS5 syntax (the first-pass nit); whether a term that tokenizes to nothing (`"..."`, punctuation-only) raises an fts5 syntax error is untested — worst case a 500 on that query, not an injection. `bm25` ascending is the correct best-first order; `snippet(blobs_fts, 2, ...)` targets `body`. `worker::Url::query_pairs` exists in 0.8.5 — the proof's "unverified" flag is stale. The `q > 1024` -> `Protocol` -> 400 path runs through `respond` inside the DO and back through `stub_json`'s `Error::from_do_response` (unverified, as in two-phase-push). The `meta.head` hard-code (8.2: `refs/heads/main`, never re-targeted) means a repo whose only branch is `master` gets `indexed: null` and zero hits forever — silently, not an error.

## Blockers
- The frontier-row `DELETE` (line 75) commits in the span before the `load_tree` awaits (lines 76-78): a kill there permanently loses an entire subtree's adds and deletes while `search.tip` converges. Move the delete into `diff`'s sync span.
- A mid-slice isolate kill wedges the job row in `running`: 4.2 selects `queued` only, 4.5 dedup blocks any replacement, A4 repairs `dead` only — IndexPush never fires again and the demand-enqueue is deduped too. Contract-level, but this proof's resume claim and its scenario 17 depend on a stale-`running` recovery that does not exist.
- Compile/signature drift: `e.oid` is `&oid`, not `ObjectId` (line 124); `budget.req` field vs `SliceBudget::as_req_budget()` (alarm-chain-ci) — one must win; `meta_opt`/`meta_str`/`bucket()` remain assumed helpers no shown code defines (`meta_opt` is at least named by `precomputed-clone-pack`).

## Caveats
- FTS5 in DO SQLite is the load-bearing unverified primitive: `CREATE VIRTUAL TABLE`, `MATCH`, `bm25`, `snippet`, and `DELETE ... WHERE <column>` / range `DELETE` on an FTS5 table are all day-1 items; if absent, the fallback is a different module that loses the DO's span atomicity.
- `path` has no real index inside an FTS5 table: every `del_path`, `upsert` delete-half, and per-row done-check is a table scan, so a k-file diff costs ~3k scans of `blobs_fts` — fine at small scale, quadratic at monorepo scale.
- Two `search_todo` rows sharing one blob sha inside a 64-row batch: `meta.iter().find(|m| m.2 == sha)` binds both reads to the first path; the second row survives to the next loop and re-reads the same object — converges, wasted calls.
- `meta.head` is `refs/heads/main` by construction (8.2): `master`-default repos are never indexed; resolving HEAD to an existing ref or documenting the requirement is a decision the proof does not make.
- The assumed post-span `rearm` convention (A3) is needed by `/_do/search` and by the commit route alike; nothing shown implements it, so an enqueued `run_at=now` job can sit with no alarm armed.
- `Error::Unpack` inside a job is the wrong variant (cosmetic); `Error::Storage` on a swept old-side object burns the 8-attempt backoff ladder (~`30 s * 2^n` capped at 1 h) before the rebuild path engages.
- Orphaned `blobs_fts` rows survive when a crash aborts a job and head moves past the skipped tip before resume; a generation column fixes it, as the proof notes for the analogous rebuild case.
- Async-by-design lag: `indexed` vs `head` is the contract with callers; one head move can strand in the `finish`-to-`Done` window until a query arrives.
- Non-UTF-8 path collisions (last writer wins) and lossy body decode are stated in Known limits and are consistent, if lossy.

## Verdict
lands-with-caveats. A real improvement over the first pass: both blockers are closed structurally (table-held work state, `Index::lookup` + `read_entries` over normalized packs), and every first-pass caveat is either fixed or explicitly dropped. What remains is one span-ordering bug that silently loses a subtree diff on kill, one contract-level `running`-row wedge the resume claim stands on, and the usual handful of mechanical reconciliations — plus the still-unverified FTS5 primitive the whole module rests on.

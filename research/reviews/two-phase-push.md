# Second-pass review: Two-phase push

# Review v2: two-phase-push (idea #6)

## Scores
- Feasibility 4/5 (was 4). Every host call exists in `worker` 0.8.5 source: `Request::new_with_init(&str, &RequestInit)`, `RequestInit::{with_method, with_body(Option<JsValue>)}`, `Stub::fetch_with_request`, `Response::{status_code, json}`, and multi-key R2 delete is `Bucket::delete_multiple(Vec<impl Deref<Target=str>>)` (`r2/mod.rs:91`), so the proof's "unverified, fall back to 300 keys" caveat is a one-word rename. `gix_pack::data::header::decode(&[u8; 12])` and `gix_hash::Hasher::try_finalize` match 0.74.2 / 0.26.2. The code does not compile against its siblings as written (arity drift, below), which is mechanical.
- Reliability 4/5 (was 3). The first-pass data-loss race is gone by construction (no shared R2 key), expiry and every mutation share a sync span, and marking and deleting never share a slice. Residual: a failed ingest leaves the push `open` for a full `PUSH_TIMEOUT` with its `objects` rows in SQLite; an isolate kill mid-multipart leaves parts that only a lifecycle rule removes.
- Correctness 4/5 (was 3). All three cases git sends (no PACK, 32-byte 0-object pack, real pack) are handled in the first ten lines and the 0-object trailer check (SHA-1 of the 12 header bytes) is right. Per-ref results, sideband and gzip are now contract modules, not this code. Deductions: the Janitor deletes `pushes` rows the contract never deletes, a new 1,000,000-link cap sits below 2.4's 2,000,000-entry cap, and the added scenario (b) asserts a state transition that does not exist.
- Effort: weeks. This file is days; a working push needs `streaming-pack-parser`, `wire`, `jobs::dispatch`, and the edge error arm fixed in `repo-do-ref-authority`.

## Contract compliance
Matches: module split (`pack::ingest::run`, `repo_do/push.rs`, `jobs/janitor.rs`); keys `r/<repo>/pending/<push>.pack` and `r/<repo>/packs/<pack>.pack` from `bucket.repo` = `meta.repo_id`; `changes()` as the only write oracle and `rows_written` unread; both DO routes are one sync span; ordering finish -> index -> commit enforced by code shape (`out.finish` line 67, `sink.post` line 68, `Ok(Some(pack))` line 75); no `set_alarm` anywhere, Janitor returns `SliceOutcome` only; 5.1+5.2 in one span; 5.3 targets `dead_at`/`ended_at` older than GRACE; 400 keys per slice, one delete call.
Deviations (each also in the structured list):
1. Janitor deletes `pushes` rows after the pending key (line 169). Section 5.3 deletes only the `packs` row; section 3's `pushes` table has no deletion rule and `result`/`principal` are the only audit of a rejected push (`reflog` covers ok moves only). Effect is mild (a retried DO call gets `Conflict` either way) but it is a schema-lifecycle change the contract does not have.
2. `/_do/push/lookup` body gains `pack` and `Index::lookup_in_pack` is new (1.2, 1.3).
3. `/_do/push/index` upserts `packs` with `ON CONFLICT(id) DO UPDATE ... WHERE state='ingesting' AND push_id=excluded.push_id` in place of `Index::insert_pack`; `PackMeta::EMPTY` and the `i64::MAX` `commit_lo` sentinel are new.
4. `MAX_LINKS = 1,000,000` -> `Error::Limit`, a limit section 2.4/12 does not list, below the 2,000,000-entry cap; and it is only checked at each 10,000-row post, so a batch of large trees can hold far more than 20 MiB of links between checks.
5. Between passes, all `RefDelta` base ids are looked up, including in-pack ones; 2.4 says only those "not entries of this pack". Harmless but extra subrequests.
6. Section 10 after-header mapping: `Limit` (this proof's own cap and the parser's 32 MiB), `Budget`, and `Conflict` from `push_index` reach the sibling's `Err(e) => return Err(e)` arm and become 413/500, not a 200 `unpack`/`ng` report. The proof says the sibling "must also catch" them; nothing shown does.
7. Signature drift across proofs: `run` here is 6 args `(body, bucket, stub, repo, push, budget)`; `receive_pack` calls it with 7 `(body, env, stub, repo, push_id, begin, budget)`. `IndexSink::post` here is `(meta, rows, budget)`; `resolve_and_normalize` calls `post(&rows, budget)`. `PackWriter::create/finish` and `resolve_and_normalize` carry `budget`/`sink` not in 1.2/1.4 (shared, already flagged there).
8. Literal: 2.5 names `unpack error missing object <oid>`; the code yields `unpack missing object <oid>`. Not wire-breaking.

## First-pass blockers
1. Janitor-vs-new-push deletes a key a newer push indexed: **resolved**. Keys are `pending/<push>` and `packs/<pack>` with fresh random ids (lines 58, 62), so no two pushes share a key; deletion targets only `SELECT ... WHERE state='dead' AND dead_at < cutoff` / `state!='open' AND ended_at < cutoff` (lines 157-160) with `cutoff = now - 1 h` > `max_ms` 240 s; readers resolve through `state='live'` only. Structural, not a check.
2. `ok` reported for refs not moved: **resolved by dependency**. This proof "never decides ref outcomes"; `commit_push` step 4 per-ref `changes()` is in the sibling and I re-read it there. Nothing in `run` can reintroduce it.
3. No sideband / no gzip: **resolved by dependency**. `run` receives a `BodyReader` (6.1 gzip) after `parse_receive_header`; `report()` goes through `wire::write_report_status` (rule 4). The `wasm-streams` path is unverified (contract says so).
Caveats from the first pass: manifest leak -> no manifest, `packs` row posted before `PackWriter::create` (line 60-61) and `out.abort()` on pass-B error (line 64): resolved. Expiry check before an await -> `push_index` reads `pushes.state` in its span (line 131-132), Janitor 5.1 is one `UPDATE`: resolved. Connectivity 500 -> `Error::Unpack("missing object ..")` from the edge (line 72): resolved for `Unpack`, not for `Limit`/`Conflict` (deviation 6). Whole-object digest -> parser sibling: resolved there.

## Crash walk-through
Edge killed after `out.finish()` returned (pack complete in R2, `packs` row `ingesting` with count 0, first 10k-row batches indexed) and before the final `sink.post`. No reader sees it: the 2.3 query joins `state='live'`. Janitor at +1 h, one span: 5.1 flips the push `expired`, 5.2 deletes its `objects` rows and sets `dead, dead_at=now`. Janitor at +2 h: both rows pass the cutoff, one `delete_multiple` of `pending/<push>` and `packs/<pack>`, then both rows go. Client retry uses new ids. Clean. Killed between `PackWriter::create` and `finish`: no R2 object exists, the later `delete` of the key is a no-op, the parts wait for the bucket's abort-incomplete-multipart lifecycle rule (not in the memo; storage cost only). Killed after commit returned: sibling's case, clean.

## Concurrency walk-through
Janitor slice lists 400 keys at T and awaits `delete_multiple`. During the await push C runs `begin`, `index`, `commit` in their own sync spans; C's keys were minted after T and are not in the list; the post-await deletes are `WHERE state='dead'`/`!='open'`, one-way states. Nothing of C is touched. Pushes A and B, both thin against base X in live pack P, with `GcSweep` between A's base lookup and A's commit: A's commit sees `gc_epoch` changed, `rejected` (A's pack is self-contained since pass B inlined X, so rejection is conservative and correct); B's lookup after the sweep misses X -> `unpack missing base`. No live ref points into a dead pack. Push A expired by 5.1 while its pass B is running: 5.2 kills its pack in the same span, so A's next `push_index` upsert matches 0 rows (`changes()!=1`, line 138) -> `Conflict`, `run` aborts the multipart. That `Conflict` then hits deviation 6 and the client sees HTTP 500 instead of `ng`.

## Interop check
Push is v0 receive-pack for git 2.43-2.47 regardless of `protocol.version=2`; this module emits no wire bytes, so nothing here can break a byte. Body shapes it must accept are right: delete-only sends no PACK after the flush (`Ok(None)` when the buffer is empty at EOF); a new ref at an existing commit makes `send-pack` run `pack-objects` with zero objects, which sends exactly `PACK 00000002 00000000` + SHA-1 of those 12 bytes = 32 bytes (`fill(32)` true, `fill(33)` false, trailer compared to the header hash: correct); a real pack streams to pass A. Thin packs (`ref-delta` bases outside the pack) are looked up in 1,000s. The only client-visible breakage is deviation 6: a 32 MiB object or a 1,000,001-link push gets HTTP 413 after the client has sent the pack, so git prints `error: RPC failed; HTTP 413` and `fatal: the remote end hung up unexpectedly` instead of a `ng` line. Scenarios 2, 4, 6, 7, 9, 14 are the right set; added scenario (b) asserts the pack row is `dead` "after the next Janitor run", but an unpack failure leaves the push `open` (no route sets `rejected`), so that holds only after the clock passes `PUSH_TIMEOUT`.

## Blockers
- Cross-proof signatures do not line up: `run` 6 args vs the sibling's 7-arg call (`env`, `begin`); `IndexSink::post` 3 args vs the parser's 2-arg call. One of the two proofs must change before the crate compiles.
- Section 10 after-header mapping is not met for `Limit`/`Budget`/`Conflict` raised by this module's paths; the proof defers it to the sibling, which also does not do it. Client sees 413/500 instead of `unpack`/`ng`.
- Janitor deletes `pushes` rows (contract 5.3 does not); either the contract gains a `swept_at` column or the delete goes.

## Caveats
- `MAX_LINKS` is a new limit below 2.4's and is only enforced per 10,000-row batch; memory joint bound admitted unenforced.
- `Bucket::delete` must wrap `delete_multiple`; single-key `delete` exists too, so the 300-key fallback is unnecessary.
- No `rejected` transition on unpack failure: a failed push holds its `objects` rows and `pending/` key for `PUSH_TIMEOUT + GRACE` (2 h). Add `/_do/push/abort` or accept it and fix scenario (b).
- Unverified per memo/contract: `RequestInit` JSON body path at runtime, `Error::from_do_response`, `web_sys::Crypto` for `PushId::random()`, real-R2 multipart, abort-incomplete-multipart lifecycle rule, subrequest limit in production, `wasm-streams` gzip.
- Lookup of in-pack `RefDelta` bases costs extra subrequests (deviation 5); cost formula in 7.3 still holds.
- Message literal `unpack missing object` vs contract's `unpack error missing object`.

## Verdict
lands-with-caveats. Genuinely better than the first pass: all three first-pass blockers are closed, two of them structurally (no shared key; per-ref CAS by contract) rather than by a check, and the crash and Janitor paths now walk clean with numbers (1 h expire, 2 h delete, 400 keys/slice). Reliability 3->4, correctness 3->4. What remains is small and local: two signature reconciliations, the after-header error arm, and one Janitor line that deletes a row the contract keeps.

# Second-pass review: Push-triggered CI as a DO alarm chain

# Review v2: alarm-chain-ci (idea #14)

## Scores
- Feasibility 4/5 (was 4). Every host call exists in `worker` 0.8.5: `Env::fetcher`/`Fetcher::fetch_with_request` (memo section 1: service bindings supported; inside a DO is runtime-unverified), `Request::new_with_init(&str, &RequestInit)` + `RequestInit::{with_method, with_body}` (source-verified per the two-phase-push review, runtime-unverified), `SqlStorage::exec` + `SqlCursor::{to_array, one}` (memo section 1), `gix_object::compute_hash(Kind::Blob, data)` (memo section 3, ran on workerd in the spike). The `PackWriter::create(&Bucket, &str, u32, &mut ReqBudget)` call (line 117) is the A1 form. It does not compile against the sibling as written — private helpers, absent `bucket()`, `RepoDo.env` — all mechanical.
- Reliability 4/5 (was 3). Both first-pass loss windows are closed structurally: the outbox is inside the commit span (no RPC, no second storage) and publish is a stage row, not epilogue-after-`deleteAlarm`. The measured mid-await interleave (#4) is fenced by the claim CAS and the attempt token. Residuals: a kill that catches both driver rows `running` strands CI permanently (Blockers), and an `Err` inside `ci::schedule` now fails the push itself.
- Correctness 4/5 (was 3). The "cannot be lost" claim is now literally true — `ci_runs`/`ci_stages` plus both enqueues are statements in the same span as the ref CASes (lines 50-59). The verdict is a real normalized pack resolvable by `want <blob>` (scenario 10). Deductions: `ci_rerun` re-opens a superseded attempt token, a `ci.stages` list of 256+ entries makes every push fail, per-run parallelism is weakened to two drivers per repo (stated, lines 7 and 196).
- Effort: weeks. The module is days; it needs the foundation plus `hooks-as-workers` (or Workers for Platforms) for real stage code and `auth-and-multitenancy` for the stage's read credential.

## Contract compliance
Matches: post-foundation module under section 12 with an A9 `REGISTRY` block listing both `JobKind` variants, both tables, the `/_do/ci/rerun` route, the `ci.stages` meta key and the `STAGE_WORKER` binding, and explicitly no new R2 prefix (lines 25-28); no `set_alarm` anywhere — `rearm` is supplied by the dispatcher after the slice (4.2) and by the commit route after its span (A3, already required for step 7's `GcMark`); `changes()` is the only write oracle and `rows_written` is never read (lines 52, 93, 124, 147; measured #1); claim/record are sync spans and the only awaits are the stage fetch and publish's R2 calls; `spent_80pct()` between units and `Reschedule` clearing the cursor per A4 (lines 68-73); the verdict goes through the normal machinery — `PackWriter` one-blob pack (2.1), `objects` row with kind 3 (2.3), `refs` row + `refs_version` bump + `GcMark` enqueue mirroring section 3 step 7 (lines 117-132); `commit_lo` `i64::MAX` sentinel per A5 (line 114); no statement nears A6's 100 bound parameters; two added scenarios, under the section-11 cap (line 182).
Deviations (each also in the structured list):
1. `commit_push` gains a `moved` collection and a step 8 calling `ci::schedule` (lines 39-41, acknowledged at line 202). Section 3 fixes the span at steps 1-7; the sibling's `commit_push` (repo-do-ref-authority lines 94-126) has neither. Unstated side effect: an `Err` from `schedule` propagates out of `commit_push`, rolling back the ref CASes — the clearest case is 256+ stage names colliding with `PUBLISH` at seq 255's PK (line 57), which would make every push fail.

3. `refs` upsert outside `commit_push` (lines 128-130). The load-bearing `refs_version` bump is present (line 131). Mild, documented at lines 190 and 199.
4. `claim` UPDATEs the foundation `jobs` table directly (lines 83-85). Section 4 owns that table's lifecycle; the only repair the contract has is A4's boot re-enqueue of `dead` rows. Admitted at line 202; consequence in Blockers.

## First-pass blockers
1. "Enqueue is not transactional with the ref flip; the proof's central 'cannot be lost' claim needs the outbox-in-repo-DO pattern before this lands.": **resolved**. `ci::schedule` is step 8 inside `commit_push`'s existing sync span (lines 41-62): the `ci_runs`/`ci_stages` rows and both `jobs::enqueue` calls are statements in the same span as the ref CASes — if the span commits, refs moved and the run is queued; if it throws, neither happened (section 3 rollback). The prescribed fix, verbatim.
2. "`finish()` ordering (`deleteAlarm` before R2 put and `set-ref`) can strand a run with no verdict and no pending alarm.": **resolved**. There is no `deleteAlarm` and no cross-DO `set-ref`: publish is the terminal stage row at seq 255 claimed and recorded by the same loop (lines 57, 98, 110-134); the `packs` row is inserted `dead` before the upload and flipped `live` in the final span with the `objects`/`refs`/`refs_version` writes, so every kill point leaves either pending work or a collectible row.
Caveats from the first pass: alarm overlap during a non-storage await -> **resolved** — both remedies applied: `LEASE_MS` sits above the stage fetch timeout (line 33) and `record` CASes on `attempts=? AND status='running'` (lines 143-147). Same-sha-different-ref sharing + rerun reset + non-null CAS `old` -> **resolved** — `ci_runs.sha` PK with `ON CONFLICT DO NOTHING` (lines 50-52), `POST /_do/ci/rerun` resets rows (lines 167-172), publish's upsert replaces the old verdict; but the reset re-opens a superseded token (Caveats). "CI means Worker stages" -> **not resolved** — kept as the honest shape; arbitrary user code remains a `hooks-as-workers` / Workers-for-Platforms dependency (line 197). Loose `objects/` verdict keys + assumed `gitBlobSha`/zlib/`set-ref` helpers -> **resolved** — the verdict is a normalized pack with an `objects` row; `compute_hash` + `PackWriter` replace the helpers; the ref write is local SQL (lines 110-134, 192). Watchdog double-run in one isolate -> **resolved** — claim CAS plus attempt token bound duplicates; stages are required idempotent (lines 81-95, 193, 198).

## Crash walk-through
The only awaits are `fetch_with_request`/`resp.text()` (lines 105-106) and `PackWriter::create`/`finish` (lines 117-119). Kill with a stage fetch outstanding at T: the stage row is `running` with `started_at=T`, the driver job row is `running`. The next `CiTick` at T+90s runs `claim`, but the lease predicate is `started_at < now - LEASE_MS` — strict — so the stage is reclaimed at the following tick, worst case ~T+180s, and the same `claim` span repairs the sibling job row once no fresh lease exists (lines 81-85). The stage re-executes with `attempts=2`, bounded by `MAX_ATTEMPTS=3`. Durable: the stage row. Orphaned: nothing. Kill inside publish's `create`/`finish` awaits: the `packs` row is `dead` with `dead_at=T` (line 113); the publish stage is reclaimed as above and re-run under a fresh `PackId`; the Janitor deletes `packs/<old>` and its row after GRACE (5.3) — if the multipart upload was incomplete the delete is a no-op and the parts wait for the bucket's abort-incomplete-multipart lifecycle rule (unverified; same residual as two-phase-push). Kill inside publish's final span: unobservable — the platform commits or rolls back all of `live` flip + `objects` + `refs` + `refs_version` + `GcMark` enqueue (section 3); on rollback the stage is still `running` and is reclaimed. Kill mid-dispatch leaving one job row `running`: repaired by any later `claim` — unless both rows are `running`, which is the Blockers case.

## Concurrency walk-through
Two live drivers are possible by design: a slice's stage-fetch await opens the input gate (#4), a `commit_push` landing in that window ends its span with `jobs::rearm` (A3), which arms the alarm at the queued sibling's `run_at`, and a second dispatch marks the sibling `running` while the first is still in fetch. The claim's `NOT EXISTS (earlier pending|running)` predicate admits only the lowest actionable stage of each run (lines 86-89), so order is preserved; the `status='pending'` CAS plus `changes()` (lines 90-93) admits exactly one winner — the loser loops and re-claims. A late answer from a lease-reclaimed attempt is dropped by the `attempts=?` CAS (lines 143-147), and the window before re-claim is covered because reclaim already set `status='pending'`. A push landing during the await has its enqueues dedup-dropped against the `running` rows (4.5) — safe only because drivers are drainers that rescan all of `ci_stages` every claim. Two soft spots: the repair's "no fresh lease" guard can also reset a sibling that is alive but between units, letting a second dispatch run the same job row — harmless, since the claim CAS is per stage — and `ci_rerun` resets `attempts=0` (line 169), which lets an in-flight attempt holding token 1 match the re-claimed row (`attempts=1, running`) and record a stale result against the fresh attempt.

## Interop check
The push path emits no new wire bytes and adds ~4-6 SQL statements inside an existing span — the first-pass band-2 `remote: CI scheduled` nicety is gone (line 176), which is fine. `git ls-remote 'refs/ci/*'` works: ls-refs lists the row and git does not type-check advertised ids. `git fetch origin refs/ci/<sha>` works through scenario 10's `want <blob>` path — the packfile section carries the one entry verbatim — and `git cat-file blob` then shows the verdict JSON; `fsck` is clean. `refs/ci/*` is an ordinary namespace: `git push origin :refs/ci/<sha>` or `push --mirror` deletes/overwrites verdicts and `clone --mirror` copies them (line 199, kept). The stage Worker reads objects through the public `POST /:o/:r/git-upload-pack` with the read token (auth-and-multitenancy), paying its own subrequests. One genuine interop hole remains inside the foundation: section 5.2 has `GcMark` walk "all refs targets" through the section-9 commit loop, and a blob-typed root is unspecified — if the mark errors on non-commit/tag targets every GC aborts once a `refs/ci` row exists, and if it skips them the verdict pack is consolidated away while `refs/ci/<sha>` still points at it (a 2.5 violation). A one-line write-back ("ref targets of any kind are marked") closes it; the proof claims the mark works (line 180) without providing it.

## Blockers
- Both driver rows stuck `running` is unrecoverable. The only repair for a kill-orphaned job row lives inside `claim` (lines 83-85), which nothing can reach once `CiRun` and `CiTick` are both `running`: `enqueue` dedups on `running` (4.5), `ci_rerun`'s enqueues drop the same way, dispatch selects `queued` only (4.2), and A4's boot repair covers `dead` rows only. The trigger is narrow — an isolate kill while two dispatches overlap during a stage-fetch await — but the state has no exit short of manual SQL. The fix belongs in `jobs::dispatch`/`boot` or in `enqueue` refreshing a stale `running` row, not in this module, which makes it a foundation gap the proof exposes rather than one it creates.
- Does not compile against the siblings as written: private `RepoDo` helpers (`q`, `sql`, `changes`, `meta`, `now_ms`, `env`), the undefined `d.bucket()`/`Bucket.inner` visibility, the `PackWriter::create` 4-arg vs 3-arg conflict with two-phase-push (this side is A1-correct), and `as_req_budget()` vs the shared `SliceBudget.req` convention. All mechanical — `pub(crate)`, one constructor, one rename — but one of each pair must change before the crate builds.

## Caveats
- `ci_rerun` during an in-flight attempt can record the stale attempt's result against the fresh one: `attempts=0` (line 169) re-opens token 1, and the record CAS `attempts=? AND status='running'` cannot tell them apart. A unique token column (or `attempts` left unreset) fixes it.
- `ci.stages` with 256+ entries collides with `PUBLISH` at seq 255 (line 57), and via deviation 1 the `Err` fails the push — cap the list at 254 or reject the config at write time.
- `as_req_budget()` (line 115) never says whether publish's 2-3 subrequests write back into `SliceBudget.subrequests_used`; if it snapshots, the 400 cap (4.3) is under-counted.
- The `/_do/ci/rerun` route's post-span `jobs::rearm` (A3) is not shown; the commit route's is relied on correctly (line 61).
- A transiently failing stage retries on a full `LEASE_MS` backoff — up to ~4.5 minutes to `fail` across 3 attempts; deliberate, but slow.
- Unverified per the proof itself (line 203): `Fetcher` inside a DO, `RequestInit` body path, real-R2 multipart (#6), DO subrequest enforcement (#7), platform alarm retry (backstop only — liveness correctly rests on the lease + `CiTick`).
- GcMark's blob-root behaviour is unspecified (Interop); the verdict's survival past its first GC depends on the write-back landing.

## Verdict
lands-with-caveats. Both first-pass blockers are closed structurally rather than by a check — the outbox rides the existing commit span and publish is a stage row, so there is no gap and no post-`deleteAlarm` epilogue to strand — and the measured mid-await interleave is fenced twice over (claim CAS, attempt token). Reliability 3->4, correctness 3->4. What remains is one narrow-but-permanent stall in the `jobs`-row repair path (a foundation gap, not this module's logic), a rerun token-reuse edge, and a pile of mechanical signature/visibility reconciliations against the siblings.

# Second-pass review: GC and repack as a DO alarm

# Review v2: gc-and-repack-alarm (idea #55)

## Scores
- Feasibility 4/5 (was 3). Every host call exists in `worker` 0.8.5 source: sync `SqlStorage::exec`/`SqlCursor::to_array` (`worker/src/sql.rs`), `Bucket::{resume_multipart_upload, head}`, `MultipartUpload::{upload_part, complete, abort, upload_id}`, `UploadedPart::{part_number, etag}` (memo section 1); `zeroblob`/`json_each` are SQLite builtins satisfying A6. `CkptSha1` is shown in full and is a correct FIPS 180-1 — the `w[i-3]^w[i-8]^w[i-14]^w[i-16]` schedule, the four round functions, and the pad-to-56 + 64-bit-length tail all check out (lines 80-97). Deductions: the new surface `PackWriter::{resume, append_stored, checkpoint, upload_id}` is write-back-only, and `resume` drifts from the signature server-side-rebase already declared.
- Reliability 3/5 (was 2). The replay lattice is real: frontier rows are deleted only inside the span that records their expansion (`commit_ids`, lines 169-176), parts replay byte-identically over a deterministic `(pack_id, idx)` scan, and `head(key)` disambiguates complete-then-crash (lines 282-293). Deductions: `abort()` called from `gc_mark` self-dedups its own re-enqueue (below); stale `running` rows depend on a boot write-back the contract does not have (proof line 378 admits it); and the sibling-busy check misses `dead` GC rows, leaving a narrow orphan-`ingesting`-pack path the Janitor's `JOIN pushes` cannot reach.
- Correctness 3/5 (was 2). The algorithm is right this time: exact mark (one bit per sha across candidates), verbatim copy, one-sync-span sweep with zero R2 calls, header count = bitmap popcount. Deductions: `ObjRow::new` cannot supply `objects.idx`, so every row this proof posts mis-indexes the pack it just built for the *next* mark and for clone-plan; `mpu_err`'s parameter type does not match its call sites; and the abort-from-mark path silently drops the re-mark.
- Effort: weeks. The arms are ~340 lines over the contract's own chain; remaining work is the write-back reconciliations, the two logic fixes below, and conformance 14.

## Contract compliance
Matches: no `set_alarm` anywhere; `enqueue` sync + dispatcher `rearm` (4.1, 4.5, A3); `gc.refs_version`/`gc.started_at` on the first mark slice, `marked(pack_id, bitmap BLOB)`, candidates `created_at < started_at - GRACE`, blobs never read (5.1); verbatim `read_entries` copy into a normal `packs/` key, `push_id` NULL (5.2, 2.2, 2.3); build predicate `>= 2 candidates or any unmarked` exactly as 5.2; sweep is one sync span — check, abort-or-delete, `dead_at`, `gc_epoch` bump, drop `marked`, no R2 calls (5.3); `spent_80pct` between units and <= 64 coalesced spans per `read_entries` (4.3, A4); `json_each(?)` for every `IN` list (A6); REGISTRY block present (A9); `Err` propagates to 4.4 backoff (4.4); error enums stay `Internal`/`Storage` (10).
Deviations (each also in the structured list):
1. Section 5.1 stores the cursor as "the frontier of unvisited ids ... in the job row (capped at 50,000 ids; larger frontiers are spilled to a `gc_frontier` table)". This proof puts the *whole* frontier in `gc_frontier` and returns `Continue { cursor: "{}" }` (lines 126, 30-31). Declared strengthening — a mid-slice kill replays rather than trusting a row the dispatcher rewrites only at slice end — but it is a deviation from the letter.
2. Section 5.2's letter inserts the new pack "`live` with its `objects` rows in the slice that completes it". Here `objects` rows post per-slice under `state='ingesting'` from the first build slice (lines 259, 274, 311), and the live flip happens in `finish_build`. Strictly more conservative — ingesting rows are invisible to the 2.3 query — but a different lifetime than written.
3. Contract section 7 table and 6.4 state the multipart rule as "parts >= 5 MiB, **equal size**". `checkpoint` uploads whatever the >= 5 MiB buffer happens to hold (lines 264-272), so non-final parts are variable-sized. Real-R2 enforcement of equal-size is unverified (platform-facts #6 measured on the simulator only); if enforced, every second checkpoint part fails. The push path's exactly-8 MiB discipline is the safe form.
4. `jobs.kind` literal is serialized inconsistently across proofs: this one queries `kind IN ('gc_consolidate','gc_sweep')` (line 109, matching the contract's own snake-case module list in section 1) while precomputed-clone-pack queries `'GcMark','GcConsolidate','GcSweep'` (its line 84) and hooks-as-workers uses `'PostReceive'` (its line 169). If `enqueue` stores variant names — the serde default — this proof's busy check never matches and a fresh mark's first slice wipes `gc.*` under a running consolidate (leak chain below). Either way one side's query is dead.
5. `ObjRow::new(sha, offset, len, kind, size)` (lines 24, 254) takes no `idx`, but `insert_objects` writes `r.idx` verbatim (content-addressed-r2-keys line 158) and `objects.idx` is load-bearing for this proof's own `bm_set`/`bm_idxs_from` and for clone-plan's bitmaps. The same latent defect exists in server-side-rebase (its lines 186, 200). If `new` defaults `idx` to 0 the rows insert fine — the corruption only surfaces downstream — so this is a runtime defect, not a compile error, whichever way the helper is defined.
6. `PackWriter::resume` drift: server-side-rebase declares `resume(bucket, key, upload_id, parts, pos, budget)` (its lines 140, 259); this proof calls `resume(&bucket, &key, &pos.upload, &etags, pos.st.as_ref()?, &mut budget.req)` (line 203) with a `&PackState { pos, sha, count }`. Only this proof's form carries the checkpointed trailer hasher — under the rebase signature a resumed writer cannot produce a correct trailer. One of the two must change.
7. `mpu_err` takes `e: worker::Error` (line 282) but is called from the `Err(e)` arms of `checkpoint` and `finish` (lines 232, 271), which return `Result<_, Error>` per A1; the header declares `impl From<worker::Error> for Error`, not the reverse. One-word mechanical slip (`e: Error`), but it does not compile as written.
8. `PackWriter::upload_id()` is used (line 202) but only `MultipartUpload::upload_id` is declared (line 15); and `PackWriter.hasher` implicitly changes type from `gix_hash::Hasher` (contract 1.2) to `CkptSha1` — an undeclared field write-back that also drops sha1-checked collision detection from the normal push path's trailer.
9. `abort()` enqueues a fresh `GcMark` (line 187) per 5.3's abort step, but when called from `gc_mark` itself (line 127) the running row counts against `enqueue`'s dedup ("at most one queued or running row per kind", 4.5), the insert is suppressed, and `Done` then deletes the row. See Blockers.
10. Roots add `refs.peeled` (line 119) beyond 5.1's "all `refs` targets" — harmless (the tag object's own link covers it) and justified by A5, but a literal widening.
11. `LOAD = 32 MiB` is attributed to "A4's own bound" (line 13); A4 bounds coalesced spans (64), not bytes. Trivial misattribution.

## First-pass blockers
1. "Schema/key/encoding contract mismatch with `two-phase-push`, `content-addressed-r2-keys` and `precomputed-clone-pack`": **resolved**. The storage model the first pass assumed is gone; this walks the live `objects`/`packs` join (2.3), re-derives links via `extract_links` (1.4) instead of a `links` column, and emits an ordinary `packs/<id>.pack` consumed through the same index and by clone-plan by design.
2. "Sweep race: `refs_version` check is not atomic with the R2 delete": **resolved**. `gc_sweep` (lines 336-346) is a `fn` making zero R2 calls; check, deletes, `dead_at`, `gc_epoch` are one sync span, and R2 keys are the Janitor's after GRACE. The contract's own three-orderings argument (section 5, "why the two review races are now impossible") is implemented faithfully.
3. "Stall-to-death ... `meta.gc` then suppresses re-arming forever; no watchdog": **partially resolved**. The latch is gone, liveness is the jobs row, A4 re-enqueues dead kinds at boot, and 4.4 backs off `Err`. But two stall paths remain: the `abort`-from-mark self-dedup (deviation 9 — the "fresh GcMark" is never actually queued) and stale `running` rows, which need a boot requeue write-back A4 does not contain (the proof says so at line 378).
4. "Single DO alarm shared with at least four sibling ideas": **resolved**. No `set_alarm` in the module; GC is three `JobKind` rows on the shared dispatcher, chained by `enqueue`, with `rearm` as the sole alarm setter (4.1; #5 measured).
Caveats from the first pass: `gc.buf` `number[]` over the 2 MB row limit: resolved — the buffer lives inside `PackWriter`, durable state is ~200 B `gc.pos` + etag rows + BLOB bitmaps. No deltas / storage doubles: partially resolved — dead bytes are genuinely reclaimed now (no loose objects exist, candidates go `dead`), but live bytes never shrink (2.1/12); honestly retained at line 375. Cost/throughput: resolved — coalesced reads, blobs skipped, verbatim copy, no inflate/deflate. MPU 7-day expiry: resolved — `head()` oracle plus `gc.fails >= 2` rebuild; abandoned MPUs still rely on the unverified lifecycle rule (line 379). Serialisable SHA-1 asserted-not-shown: resolved — `CkptSha1` shown and correct. Interop "marked count vs emitted" and "no trailer": both resolved — `rows.len() != idxs.len()` fails loudly (line 248) and `finish` writes the trailer before `complete`.

## Crash walk-through
Kill inside a mark `read_entries` await: the popped batch's frontier rows were never deleted (deletion happens only in `commit_ids`), `bits` is uncommitted, replay re-marks idempotently — `bm_set` is idempotent, kids are `OR IGNORE`, `gc_seen` filters re-admission. Kill inside a `commit_ids` span: all-or-nothing. Kill between `PackWriter::create` and the first `checkpoint`: `pos.upload` is never persisted until `flush` commits it with the first etag (lines 202-204, 275-277), so resume creates a second MPU on the same key and the first is orphaned to the ~7-day abort. Kill inside `upload_part`: the part may exist; `gc.pos`/`gc_parts` do not; resume re-uploads the same part number with byte-identical content (deterministic scan + verbatim entries; S3 overwrite-before-complete, unverified on real R2 #6), and the staged rows re-post through `ON CONFLICT DO NOTHING`. Kill inside `complete`: resume replays the tail, `finish` errors `NoSuchUpload`, `head(key)` finds the object and `finish_build` re-runs its idempotent span with `pos`-derived meta; a truly dead MPU increments `gc.fails` and at 2 wipes to a rebuild from intact `marked`. Kill inside the `gc_sweep` span: atomic, all-or-nothing — but the row is left `running` and no `rearm` ran, so an idle repo holds an unarmed alarm until the next `fetch`/`alarm` triggers `boot` and the unshown stale-`running` write-back revives it. Kill after `finish_build` committed but before the dispatcher applied `Done`: the row is `running`, resume -> exhausted input -> `finish` errors -> `head` finds the key -> the `state IN ('ingesting','live')` predicate (line 327) re-runs the flip idempotently and the dedup'd sweep enqueue stands. Correct — the `'live'` arm is exactly this replay. Residual chain: a `dead` GcConsolidate is invisible to `gc_mark`'s busy check (`state IN ('queued','running')`, line 109); a fresh mark's first slice deletes `gc.*` including `gc.new_pack`, and the still-`ingesting` pack row is then orphaned permanently — Janitor 5.2 selects via `JOIN pushes u ON u.id = p.push_id` (two-phase-push line 154), which `NULL` never satisfies, and no `gc.*` row names it any more.

## Concurrency walk-through
A push landing between mark's first slice and the sweep bumps `refs_version` inside `commit_push`'s span: mid-mark it takes the `abort` arm (line 127) — which is where deviation 9 bites, because the push's own step-7 `enqueue(GcMark)` was already dedup-suppressed by the existing mark row, so the net result is zero pending marks until the next ref move; mid-build the same check sits in `begin_build` (line 297); at sweep it aborts. A push whose `lookup` ran before the sweep and whose `commit` runs after is rejected by `gc_epoch` step 2 with `gc ran during push, retry` — client-visible but resubmittable (line 377 owns this). A fetch that resolved locs pre-sweep still reads bytes: the Janitor deletes keys only at `dead_at + GRACE` (1 h) and a request lives at most `max_ms` 240 s. The dedup window worth noting: a queued mark at T+10 min keeps its `run_at` even when a push lands at T+9 — the contract's dedup never extends the quiet window, so GC can start one minute after the latest push; correct (the version is captured at first slice) but weaker debounce than "10 min after a ref move" reads. Two GC links cannot overlap *if* the busy check matches — see deviation 4 on the kind literal.

## Interop check
The R2 object is a byte-exact pack v2: `PACK` + version + big-endian count where the count is the popcount of `marked` and marking sets at most one bit per sha, so header equals entries exactly — the first pass's short-pack failure is structurally impossible, and a marked idx lacking an `objects` row fails `Internal` before a byte uploads rather than writing a short pack (line 248). Entries are stored bytes copied verbatim — full objects only (2.1) — and the 20-byte trailer is appended by `finish` before `complete`, hash state surviving slices through `PackState.sha`. `index-pack` and the 2.3 read path accept it; precomputed-clone-pack's verbatim path (`stream_verbatim`) consumes it directly. A sha in two candidate packs collapses to one bit and one entry — legal dedup per 2.3's "either row is correct". Submodule gitlinks are skipped only via the presigned-direct-upload write-back to `extract_links`; without it a tree's mode-160000 entry is followed as a link and quietly never marked — same hole the foundation already ships, flagged correctly at line 16. Scenarios 14, 3, 6, 12 plus the two added ones (force-push mid-GC; push spanning the sweep) are the right set and within the two-addition limit.

## Blockers
- `ObjRow::new` supplies no `objects.idx` ordinal (deviation 5). If it defaults to 0, every repacked pack's rows share `idx=0`: the *next* `GcMark` marks only bit 0, `bm_idxs_from` returns `[0]`, and `SELECT ... WHERE idx IN (0)` returns all N rows, so `rows.len() != idxs.len()` throws `Internal` on every retry — GcConsolidate wedges permanently for any repo that has ever been repacked; and clone-plan's bitmaps on such a pack mark bit 0 only, so the fast-path clone streams a pack whose header claims `packs.count` but carries one entry — `index-pack` dies. Same defect in server-side-rebase. Fix is mechanical — pass the running append ordinal — but it is a correctness fix, not a rename.
- `abort()` from inside `gc_mark` can never enqueue the fresh mark (deviation 9): the running row satisfies dedup, the insert is a no-op, `Done` deletes the row, and no `GcMark` exists until the next push — the "re-marks after the quiet window" claim is false on exactly the path it exists for. Fix is mechanical (return `Reschedule` on the current row, or dedup-exempt the running self) but it is the stall class the first pass was failed for.
- `PackWriter::resume` signature drift with server-side-rebase (deviation 6): only the `PackState` form restores the trailer hasher, so the rebase signature cannot produce a correct pack after resume. One of the two proofs must change before the crate compiles.

## Caveats
- `mpu_err`'s `worker::Error` parameter vs `Error`-typed call sites (deviation 7); `PackWriter::upload_id()` and the `hasher` field retype are undeclared write-backs (deviation 8).
- `jobs.kind` serialization is unspecified; the literals across proofs disagree (deviation 4). Whichever side loses, its busy check is dead.
- Variable-size non-final parts lean on real R2 not enforcing the contract's equal-size rule (deviation 3); part-overwrite-before-`complete`, `resume_multipart_upload` on a completed upload, and MPU lifecycle cleanup are all simulator-only (#6).
- The busy check ignores `dead` GC rows; combined with the Janitor's `push_id` join this leaves a narrow orphan-`ingesting`-pack leak (crash walk-through).
- `abort` never calls `MultipartUpload::abort`; the dead build's parts wait out the ~7-day auto-abort (storage cost only).
- `append_stored` must maintain `count`, `commit_lo/commit_hi` and the hasher to keep `finish`'s `PackMeta` right — unspecified; `finish_build` trusts `meta.*` while `mpu_err` trusts `pos.lo/hi` (lines 286-288 vs 328-329), consistent only if the write-back tracks commit bounds.
- Unverified, consistent with siblings: `Vec<u8> -> SqlStorageValue` blob binding, `web_sys::Crypto` for `PackId::random` (8.2), DO subrequest enforcement (#7).
- Retained by design: no delta search anywhere (12), so repack merges and prunes but never shrinks live bytes; a repo pushed faster than a full chain never sweeps (line 376).

## Verdict
lands-with-caveats. The first pass's four blockers are all genuinely closed — the sweep is atomic by construction, the alarm is the contract's own dispatcher, the storage model matches section 2 exactly, and the resumable build is shown rather than asserted (correct SHA-1, `head()` oracle, byte-identical part replay). What remains is local: the `objects.idx` ordinal is never supplied, the abort path's re-enqueue is eaten by dedup when the aborting job is the mark itself, and `PackWriter::resume` disagrees with its sibling declaration. All three fixes are mechanical; none requires redesigning the mechanism.

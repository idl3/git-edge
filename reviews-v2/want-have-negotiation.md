# Second-pass review: Want/have negotiation with a commit-graph in SQLite

# Review v2: want-have-negotiation (idea #56)

## Scores
- Feasibility 4/5 (was 4). Every host call exists in the memo: synchronous `SqlStorage::exec`/`SqlCursor::{to_array, one}` in the DO (rust-server section 1), `Stub::fetch_with_request` + `RequestInit::with_body` JSON bodies (unverified at runtime, same as every sibling), `BinaryHeap` is std, serde_json runs on wasm32. `CommitRefIter::{tree_id, parent_ids}`, `TreeRefIter`, `EntryMode::{is_tree, is_commit}` on gix-object 0.64.1 are named per docs, not run in the spike — admitted. The genuinely unproven piece is the one the idea stands on: `COUNT(DISTINCT)`/`JOIN` latency over a multi-million-row `introduced` in DO SQLite is a day-1 measurement. Code as written does not compile against its siblings (`crate::edge::lookup`/`stub_json` live in `pack::ingest::run`; `SendSet::mark` is private) — mechanical.
- Reliability 3/5 (was 3). Structurally better: graph rows are content-keyed, posted before `/_do/push/commit`, idempotent under interleaving pushes, and every row miss in the walk or the join is designed to fall back. But the fallback net has a hole the proof claims it does not: a push that dies mid-`introduced` leaves permanent, undetectable partial rows that serve wrong packs, and nothing ever deletes them. Plus an algorithmic under-send under gen inversion (blockers).
- Correctness 3/5 (was 3). Under its own invariants — complete rows, `gen(child) > gen(parent)` — the two-colour walk, the n-way `diff`, and the `introduced ⋈ objects ⋈ packs(live)` join are right, and the wire shape is entirely delegated to contract-verified writers (rule 3 holds via `write_fetch_prelude`). But both invariants are breakable by the write path itself, and each break produces a pack missing objects the client needs — the exact failure class the proof claims is impossible ("a superset, never a hole", line 279; "degrades, never corrupts", line 306).
- Effort: weeks. This file plus its write-backs is days; the push-time `diff`/`post` cost tuning, the schema migration, the day-1 join-latency measurement, and the named-but-unbuilt `graph_repair` backfill (without which pre-existing repos never benefit) are weeks.

## Contract compliance
Matches: A9 REGISTRY block lists both tables and both routes, no JobKind, no R2 prefixes (lines 23-28); both routes are `fn` sync spans with `Err` propagating out of `fetch` (A2); every `IN (...)` is chunked at `PARAMS = 90` (A6); `/_do/graph/commits` takes <= 1,000 ids and `/_do/graph/index` <= 10,000 rows, mirroring the 1.3/7.3 batch contract; `changes()`/`rows_written` never read — `INSERT OR IGNORE` and the `ON CONFLICT ... WHERE excluded.gen > commits.gen` ratchet need no CAS (section 3); no `set_alarm` anywhere; section 3 ordering extended, not violated — the graph posts sit between step 2 (`objects`/`packs` rows) and step 3 (commit), so a ref can only point into a fully-rowed pack; the `pushes.state='open'` guard in `graph_index` (line 205) mirrors `push_index`; wire rule 3 is delegated wholesale to `write_fetch_prelude` — acknowledgments omitted iff `done`, `NAK`+flush+end on `NotReady`, `ready`+delim+`packfile`+sideband+flush on `Ready` (protocol-v2-only lines 149-161); `deepen`/`shallow`/`want <tree>` route to `send_set_shallow`, so nothing advertised (`fetch=shallow filter`, rule 6) is silently dropped; `Error::Limit("fetch too large for this server; clone instead")` matches 9.3 verbatim; all R2/stub traffic is charged through `budget` (7.1); `filter` becomes a `kind`/`size` predicate while explicit wants are marked unfiltered, matching the sibling's `NOT_USER_GIVEN` rule (partial-clone-filters line 62); the liveness argument for dropping the join's `state='live'` check on introduced rows is sound — `introduced(c)` is a subset of `closure(tree(c))` and ancestors of a live want are live by 2.5.
Deviations (each also in the structured list):
1. `acks` is computed against the `commits` table (`in_commits`, lines 227-228), not `Index::lookup` as section 9 step 1 specifies. The sets differ both ways: a live have with no graph row is NAKed and never painted (superset, legal per 9.4, but bigger packs and `NotReady` rounds where the contract would ACK); a rowed have whose objects were swept is ACKed though the contract would drop it (harmless — the client holds the closure it offered).
2. `use crate::edge::{lookup, stub_json, RepoRoute}` (line 33): `lookup` and `stub_json` are defined in `pack::ingest::run` (two-phase-push lines 95, 103), not `edge`. Several siblings already assume `edge`, so hoisting is the right fix — mechanical, but as written the import does not resolve.
3. New module `src/graph/mod.rs` imports `repo_do::RepoDo` and `pack::generate::SendSet`; section 1.1 admits `repo_do` imports from `lib.rs` and `edge` only, and the REGISTRY lists tables/routes but not the new module or its dependency edges. Same class as the sibling deviations partial-clone-filters review already flagged (`pack` importing `RepoDo`); mechanical — the DO half could live in `repo_do/graph.rs`.
4. The `fetch_v2` dispatch is a comment, not code (lines 268-275): `write_fetch_prelude(args, acks, [])` drops the `PktWriter` receiver (real signature `(w, args, acks, shallow)`); the `Ok(false)`/`Neg::Miss` discard path never says whether the pre-marked `set` is reused or rebuilt by `send_set_shallow` (both are correct — marks are idempotent bitmap ORs — but it is unspecified); tag peeling is "one read_entries round", which does not cover tag-to-tag chains the sibling's `while !tags.is_empty()` loop handles.
5. `post` inserts `/_do/graph/index` calls into section 3's ordering between steps 2 and 3; A9 registers the route but the ordering insertion itself is the proof's, and it is what makes the crash window in blockers 1 permanent (graph rows are never deleted, by design — REGISTRY line 28).

## First-pass blockers
1. Sideband frame size (65519 -> 65515, "hard client-side die"): **resolved by dependency.** No `emit` remains; all framing is `wire::Sideband::data` at `MAX_BAND_DATA = 65515` (rule 2) inside `write_pack`/`pack_chunk`.
2. `recordCommit` assumed parents already inserted; pack order is not topological: **resolved.** Gens are computed by a Kahn sort over in-pack parents after all commits are known (lines 77-88); external gens come from `/_do/graph/commits`; the DO inserts verbatim under the ratchet. No `.one()` on a possibly-absent parent exists.
3. Per-pop `Array.sort` walk exceeds DO CPU: **resolved.** `BinaryHeap<(gen, sha)>`, `live` is O(1) `everybody_uninteresting`, `MAX_POPS = 200,000` -> `Error::Limit` (9.3's bound and message). Caveat: the fix assumes strict gen order the write path cannot always deliver — see blockers.
Caveats from the first pass: `introduced` tree-diff hand-waved: resolved — `diff` is a specified n-way path diff over changed paths with old trees fetched in coalesced rounds (lines 111-157). `objs` over DO RPC (32 MiB) and `IN` at 32k params: resolved — no RPC (`stub_json` HTTP), the send set never leaves the DO, `IN` batched at 90 (A6; real cap is 100). Stream error must abort the writer: resolved by dependency — section 10 band-3 + end of stream inside `Response::from_stream`. Ref update and `recordCommit` in one transaction: partially resolved — ordering plus coverage gates close the advertised-tip hole, but a mid-post crash leaves permanently partial `introduced` rows the COUNT gate cannot see (blocker 1). `ready` semantics/orphan `have`: not tightened — the contract's own 9.2 rule; superset is legal (9.4). Objects outside `recordCommit` invisible forever: resolved — `feed` runs inside pass B for every push; `presigned-direct-upload` is named as needing the same fill. JS walk / 30 s CPU / fresh clones: resolved — Rust over sync SQLite, 200k-pop cap -> `Limit`, `clone_plan` gate runs first. `OBJ_REF_DELTA` independence: resolved — all packs at rest are full-object (2.1).

## Crash walk-through
`feed` runs inside pass B and is in-memory only; a kill there is the sibling's story (`push` stays `open`, `objects` rows and both R2 keys are collected by the Janitor at +1 h expire/+2 h delete). Inside `post`: kills during the `/_do/graph/commits` reads or the `diff`'s `lookup`/`read_entries` rounds touch nothing durable — the push fails and its fallout is the sibling's. Kills between `graph_index` calls land on batch boundaries because each call is one DO sync span. Between `commits` batches, or before the first `introduced` batch: `commits` rows with zero `introduced` rows — permanent (nothing deletes graph rows) but detectable; the per-chunk `COUNT(DISTINCT commit)` gate (lines 252-253) fails and every affected fetch falls back to `send_set_shallow` forever. Degraded, correct. Mid-`introduced`: `commits` rows are complete and one or more commits carry a fraction of their set — `rows` straddles the 10,000-row batches in `HashMap` order (lines 92-99). The COUNT gate checks >= 1 row, so the hole is invisible; a fetch walking into that commit is served a pack missing objects — the client's `index-pack` succeeds, refs move, checkout/`fsck` then fail on the missing objects. Permanent until a re-push of that commit rewrites the rows, and ref-reachable objects are never re-sent, so "never" is the likely answer. The comment on line 91 ("a mid-crash leaves detectable holes") is wrong. A DO kill inside any of the four handlers is clean — all `fn` sync spans, uncommitted writes roll back (A2), and `negotiate`/`graph_send_set` are read-only. A kill after the last `post_rows` but before commit leaves complete correct rows for an uncommitted push: harmless, since a commit row reachable in a walk is an ancestor of a live want and therefore live itself (2.5), so the join cannot drop a needed row.

## Concurrency walk-through
Pushes A and B interleave `graph_index` calls freely: rows are content-keyed, `INSERT OR IGNORE` and the `gen` ratchet make any order idempotent, identical sha implies identical `parents`/`tree`. Fetch F between A's post batches: `negotiate`/`graph_send_set` are one sync span inside one DO event, but A's posts are separate DO events, so F observes the inter-post state with no crash required — `commits` rows present, `introduced` absent (COUNT gate -> fallback) or, when a commit's set straddles a batch (any push with > 10,000 introduced rows), partial (gate passes -> under-send). F versus `GcSweep`: both sync spans, serialized; after the sweep the `objects` rows of dead packs are gone but `commits`/`introduced` are sha-keyed and survive, and the join resolves relocated objects through the consolidated live pack (scenario 14); an object whose only location died is unreachable from a live want (2.5), so the join cannot starve a needed row. The walk's own span is the real concurrency cost: up to ~200k `crow` reads plus ~2,200 joins with zero awaits queues every other DO event — pushes, fetches, the alarm — for seconds; admitted in Known limits and inside `max_ms = 240 s` (7.1).

## Interop check
The module emits no pkt-lines. Everything a git client sees is `write_fetch_prelude` — verified in protocol-v2-only against rule 3: `acknowledgments` omitted iff `done`; `NotReady` always carries empty `acks`, so the emitted sequence is `acknowledgments`, `NAK`, flush, response ends (rule 3's no-pack case); `Ready` emits `ACK <oid>` per rowed have (or `NAK`), `ready`, delim, `packfile`, 65,515-byte band-1 frames (rule 2), flush; `response-end` never appears. The first pass's 65,524-byte frame bug is gone with `emit`. Semantic deltas a real client sees: `acks` is a subset of the contract's known-haves (deviation 1) — NAK-heavier negotiation and bigger packs on partially-graphed repos, always legal; a promisor fetch (`want <blob>` x N, `filter blob:none`, `done`, no haves) has an empty commit-want list, so `Ready{interesting:[]}` -> `graph_send_set` iterates zero chunks -> `Ok(true)` -> the pack is exactly the marked wants, no graph touched (scenario 10); `filter blob:limit=<n>` sends a boundary blob of exactly n (predicate `size > ?`, same as the sibling) — over-send a promisor tolerates; `deepen`/`shallow`/`want <tree>` hit `send_set_shallow`, never silently ignored; > 200,000 pops is HTTP 413 before any byte (section 10), git prints "RPC failed; HTTP 413" — the `ERR` pkt-line body is discarded at >= 300 by remote-curl (A2's own observation). The failure a real client can hit that no sibling produces: the two under-send paths yield a structurally valid pack missing objects — `index-pack` accepts it, refs advance, and the clone is quietly corrupt until `fsck` or checkout finds the holes.

## Blockers
- Partial `introduced` posts are undetectable and permanent -> under-send. `post` writes all `commits` rows first (line 91), then `introduced` in 10,000-row calls (lines 92-99); the only coverage gate is `COUNT(DISTINCT commit) == chunk.len()` (lines 252-253), which catches a commit with zero rows but not one with half its set. Reached by an isolate kill mid-`introduced` (permanent: nothing deletes graph rows) or by any fetch scheduled between two `/_do/graph/index` calls when a commit's set straddles a batch (transient, no crash needed). Mechanical fix: post `introduced` batches first and `commits` last, so a `commits` row witnesses a complete `introduced` set and the existing COUNT gate suffices; or store a per-commit expected row count and check it.
- `w.live` is double-decremented when a node is flipped after being popped interesting. `offer`'s Occupied arm (line 216) subtracts without knowing whether the node is still queued; the pop already subtracted at line 238. Flip-after-pop needs a child to pop after its parent, i.e. `gen(child) <= gen(parent)` — which the write path admits: a rowless external parent contributes 0 to `gen(child)` (line 84), and if that parent's row is written by a later push it can carry an equal or higher gen. Then `live` hits 0 with a genuinely-interesting node still in the heap, the walk exits, and its `introduced` objects are never sent. Reachable only under partial graphs — exactly the conditions Known limits claims "degrade, never corrupt" (line 306). Mechanical fix: record popped state (a `done` set or tri-state colour) and skip the decrement for popped nodes; gen monotonicity cannot be restored retroactively because a child's row can predate its parent's.
- Import drift, mechanical: `crate::edge::{lookup, stub_json}` (line 33) resolves to helpers defined in `pack::ingest::run` (two-phase-push lines 95, 103); `SendSet::mark` is private in the sibling (partial-clone-filters line 39) — the `pub(crate)` write-back is declared but not yet real. The crate does not compile until the helpers are hoisted.

## Caveats
- `metas` materialises a `serde_json::Value` per commit for the whole push before chunking (lines 89-91), and `GRAPH_CAP` counts fed `data.len()`, not the maps'/JSON's real heap (~2-3x) — a near-cap push can OOM the 128 MB isolate mid-post, which is precisely the crash that leaves blocker 1's permanent hole.
- On repos whose history predates the feature, every fetch whose walk reaches a rowless ancestor returns `Miss` — the graph earns nothing until history is backfilled; the named `graph_repair` job is load-bearing for the idea's value, not optional polish. Post-feature commits also get near-minimal gens (parents contribute 0), which is what makes blocker 2 reachable.
- The `GROUP BY i.oid` bare-column pick between duplicated live packs relies on SQLite filling bare columns from one row of the group (true in its implementation; the proof's "same bytes" argument does not cover a pack/offset cross-pick). Pin it in a conformance test.
- `graph_index`'s `Err(Conflict)` on a non-open push reaches the edge as a failed stub call; the after-header `unpack`/`ng` arm is still unimplemented in the sibling (two-phase-push deviation 6), so a dead push reports HTTP 500/"remote end hung up" instead of a report-status.
- `commits`/`introduced` never shrink (~350 MB of SQLite for a 5M-object repo); graph GC is a named later idea.
- Unverified day-1 list, as the proof admits: `TreeRefIter`/`EntryMode::{is_tree, is_commit}`/`CommitRefIter::{tree_id, parent_ids}`/`TagRef::target` on 0.64.1; `SqlCursor::one::<Cnt>` aggregate shape; `COUNT(DISTINCT)`/`JOIN` latency over multi-million-row `introduced` versus the 7.4 commit-region path it replaces — the measurement that decides whether the idea pays; `RequestInit` stub bodies; `is_some_and` on the pinned toolchain.

## Verdict
risky. Materially better than the first pass: all three first-pass blockers are closed (two by dependency, one by real code), the `introduced` tree-diff is specified rather than hand-waved, and the wire shape is entirely delegated to contract-verified writers. But the safety lattice has two reachable holes — the commits-first post order makes partial `introduced` state permanent and invisible to its own coverage gate, and a gen inversion can strand interesting commits through a double-decremented `live` — both serving packs that miss objects, which is the one outcome the proof argues cannot happen. The fixes are mechanical and small (reorder the posts; track popped nodes; hoist the helpers), so this is one more pass away, not a redesign.

# Second-pass review: Per-blob presigned direct upload for giant pushes

# Review v2: presigned-direct-upload (idea #24)

## Scores
- Feasibility 3/5 (was 4). The platform surface is real: `worker` 0.8.5 `Bucket::{head, get().execute(), delete_multiple}`, `Object::{size() -> u64, checksum() -> R2Checksums, body() -> Option<ObjectBody>}` (verified on docs.rs/source, same list native-lfs verified), `ObjectBody::stream`, sync `SqlStorage::exec`/`changes()` (platform-facts #1, #4), `gix_hash::hasher`, `gix_pack::data::entry::Header::write_to`, and `lfs::sigv4::presign` is pure HMAC/SHA-256. The miss is the centerpiece: `gix_zlib::stream::deflate::Write` in the pinned 0.1.0 has exactly `new`/`reset`/`into_inner` — the proof's `get_mut()` and `try_finish()` do not exist (lines 180, 187), and `Write::flush()` issues `FlushCompress::Finish`, i.e. finalizes the zlib stream, so the per-chunk flush-drain loop cannot work even if the names did. The escape hatch exists — `Compress::compress(input, output, FlushCompress)` is public in the same file, and `Compression::{NONE, DEFAULT}` are real consts — but `copy_blob` must be rebuilt on it; a rework, not a rename. `sha2`/`base64` are not yet in the tree (the proof says so).
- Reliability 3/5 (was 2). The two first-pass data-loss interleavings are dead by construction: no ref ever resolves through `r/<repo>/blobs/<oid>`, every staged byte is rehashed and copied into a normalized pack before commit, and the sweep only touches claims older than `CLAIM_MS` (2 h). What remains is a cleanup path that does not run as written (no reschedule, arming depends on a sibling `rearm` that does not exist), a post-await row delete that ignores fresh leases (fails closed), a durable-unindexed pack leak on a kill between `finish` and `post`, and unmeasured multi-GB deflate+SHA-1 CPU inside a 240 s request.
- Correctness 3/5 (was 3). The protocol story is now contract-shaped and does what the idea says — claims, pinned-checksum presigned PUTs, blob-filtered pack, holes staged into pack2, one commit span flipping both. But the shipped `copy_blob` cannot produce a pack entry as written (the feature's whole point), pack2's rows are posted in one unchunked `/_do/push/index` call that fails above 10,000 staged blobs, `pushes.pack_id` has no specified value for a two-pack push, and the bespoke client that gives the feature users is still unshown.
- Effort: weeks. Server side is ~250 lines plus the `Compress` rework and write-backs; `git-remote-edge` remains the bulk of the work, unchanged.

## Contract compliance
Matches: A9 `REGISTRY` block listing the edge route, both `/_do/blobs/*` routes, `JobKind::BlobSweep`, the `blob_claims` table, the `r/<repo_id>/blobs/` R2 prefix and the write-backs (lines 9-16); 2.1's "no loose objects" kept by construction — every admitted byte lands in a normalized pack as a full-object entry, `blobs/` is scratch like `pending/`; the 2.3 reader query is the only resolution path and `have` uses `Index::lookup` (line 75); 2.5 errors preserved for unclaimed holes (lines 124-126); section-3 ordering held per pack — `finish` before index post before commit, both `ingesting -> live` in one span; both new DO routes are "Awaits inside: none" (1.3), and the claims SELECT+lease-UPDATE is one span (lines 97-101); no `set_alarm` anywhere, `enqueue` dedups by kind (4.5), one slice per firing with `spent_80pct()` between units (4.2/A4), sweep cost 151 <= 80% of 400 (4.3); `json_each(?)` for the claims IN-list and single-parameter deletes (A6); `budget.charge` before every R2/stub call and a per-chunk `max_ms` check (7.1); `Limit`/`Forbidden` -> 413/403 on the JSON route and `Unpack` in the edge -> 200 `unpack`/`ng` after the receive header (10, A2); no `unwrap`/`[]`/narrowing on client or R2 bytes (`oid()`, `try_from`, `get`, `saturating_add`); `repo_id` from `meta` (8); exactly two added scenarios (11).
Deviations (each also in the structured list):
1. `copy_blob`'s deflate loop (lines 154, 173-188) is built on `deflate::Write::{get_mut, try_finish}` — absent from gix-zlib 0.1.0 (source-verified: the adapter exposes only `new`, `reset`, `into_inner`) — and its `z.flush()` per chunk is `FlushCompress::Finish` under the hood (`write_inner(&[], Finish)`), which finalizes the stream at the first chunk. The code does not compile, and with `inner = Vec<u8>` every produced byte accumulates in the inner buffer anyway, so the resident-memory argument (lines 140-141, 274) fails even before the missing methods. Not a mechanical rename: rebuild on `Compress::compress(input, output, FlushCompress)` with a bounded output buffer, or a forwarding `io::Write` sink plus one terminal `flush()` — and the sink/borrow shape must leave `out` usable for `flush_if_full`.
2. `BlobSweep::run_slice` never reschedules: `enqueue` dedups by kind (4.5), so batches arriving while a sweep row is queued are dropped, and the slice returns `Done` whenever `stale.len() < HEADS_PER_SLICE` (line 236) regardless of non-stale claims outstanding. Claims maturing after the last armed firing — and the whole tail after the last batch — leak rows and scratch keys indefinitely. Compounding: `claimed_at < now - CLAIM_MS` (strict, line 220) against `run_at = now + CLAIM_MS` (line 89) makes the enqueue-scheduled firing a no-op for its own claims if the alarm is exact. One-line fix exists: `Reschedule { run_at: min(claimed_at) + CLAIM_MS }` when rows remain.
3. The sweep's arming relies on `jobs::rearm` after the route's sync span (the comment at line 90 asserts it; A3 requires it), but `repo-do-ref-authority`'s `fetch` ends at `crate::edge::respond(out)` with no `rearm` — the identical gap the hooks-as-workers v2 review already filed against `GcMark` (its deviation 6). Until that lands, `BlobSweep` only fires when some other alarm happens to rearm `MIN(run_at)`.
4. pack2's `packs` row is posted only after `out.finish` (lines 137, 257-259): two-phase-push's own invariant is `packs` row `ingesting` before the first part upload (its lines 64, 180) precisely so a completed key always has a row. A kill between `finish` and `post` leaves `packs/<pack2>.pack` durable and unindexed forever — the Janitor only knows rows. Mechanical: `sink.post(&PackMeta::EMPTY, &[], budget)` before `create`, as `run` does.
5. pack2's index post ships `rows2` in one `IndexSink::post` (line 259); `/_do/push/index` rejects > 10,000 rows (1.3; two-phase-push line 133). A staged push with > 10,000 missing links fails `Internal` instead of chunking; the `u32::try_from(missing.len())` guard (line 128) is dead code above that wall.
6. The post-await `DELETE FROM blob_claims WHERE sha=?` (line 235) does not re-check `claimed_at`: a claim leased by `blobs_claims` during the gate-open window between the stale SELECT (line 220) and the deletes is removed while a live request holds it — that request's `get` then 404s into `unpack`. Fails closed, but the lease guarantee the doc comment claims (lines 92-93) only covers leases taken before the SELECT. Add `AND claimed_at < ?`.
7. `CommitRequest.pack_id: Option<String>` -> `pack_ids: Vec<String>` (lines 262-263) rewrites section 3's DTO and step 3 into a loop, but `finish_push` still writes a single `pushes.pack_id` (repo-do-ref-authority lines 158-159); which id lands in the audit column is unspecified. Registered as a write-back; mechanical but incomplete. Related: a `changes()==0` on the second flip would leave pack1 `live` under an `open` push — unreachable in practice (both rows are written by the same push before commit) and GC-collectable, but only because `respond` converts `Conflict` into a response and commits the earlier write (A2 forces rollback only for `Storage`/`Internal`).
8. Signature drift across proofs, all mechanical but compile-blocking: `IndexSink`'s fields `stub, repo, pack, push` are private (two-phase-push line 82) yet `stage` literal-constructs one (line 258); `PackWriter::create` is called `(bucket, &String, count, budget)` here (line 129) vs `(bucket, key: String, expected: u32, budget)` in content-addressed-r2-keys (its line 75) vs `(bucket, String, budget)` in two-phase-push (its line 65) — three shapes, one function; `stub_json` is a private fn inside `pack::ingest::run` (two-phase-push lines 103-112) while native-lfs imports `edge::stub_json` — two homes for one helper; `run`'s return becomes `Vec<String>` vs the sibling's `Option<PackId>` and the `receive_pack` call site (`pack_id.map(|p| p.0)`, repo-do-ref-authority line 177); `ShaRow` is private to `repo_do::blobs` (line 63) but read in `jobs::blob_sweep` (line 221); `Response::from_json` returns `Result` and gets no `?`/map (line 246).
9. The A7 memory-cap lift is asserted in comments (lines 141, 274) but is not in the `REGISTRY` write-back list (lines 15-16) — an unregistered contract change; A9 only blesses what the block lists.
10. `unpack(format!("missing object {id}"))` (line 125) yields `unpack missing object <oid>` vs section 2.5's literal `unpack error missing object <oid>` — the same one-word drift as two-phase-push's deviation 8; the prose claims the contract literal (line 275).
11. `pack::ingest::stage` reaches `stub_json`/`RepoRoute` — a `pack -> edge` dependency, backwards under 1.1 (inherited from two-phase-push; A8 wants shared DTOs/helpers in `wire::http`).
12. Known limits cites "the 32 MiB external-base cap (2.4)" (line 297); A7 sets the single-object cap at 16 MiB. The conclusion — a thin delta against a giant staged base cannot be applied — still holds.

## First-pass blockers
1. Janitor deletes R2 objects, racing `resolveBlobs()`, the ordinary push path, and other tenants: **resolved**. Structurally, not by a check: no ref ever resolves through `blobs/<oid>` (reads go through the 2.3 query into `live` packs), `BlobSweep` deletes keys only for claims older than TTL + GRACE, keys are per-repo (`r/<repo_id>/blobs/`), and the ordinary path never consults the claims table. The worst outcome of a sweep racing a copy is a 404 -> `unpack` — a failed push, never a dangling ref. Residual sweep defects are deviations 2, 3 and 6 — leaks and wasted retries, not loss.
2. `resolveBlobs()` must re-check row state after each `await` and run before the synchronous ref CAS transaction, not inside it: **resolved**. There is no resolve-in-transaction at all: `copy_blob` runs in the edge before `/_do/push/commit`, and `commit_push` is the unchanged sync span except for looping `pack_ids` in step 3. Nothing needs re-checking after the awaits because the row is never trusted — every byte is rehashed (`h.update` per chunk, `try_finalize` compared to the claimed oid, lines 156, 190-191).
3. Prove on a real bucket that a checksum-mismatched presigned PUT is rejected and `head().checksums.sha1` is populated; otherwise the inline `rehash()` on a 4 GB blob happens inside the push request: **partially resolved**. Still unverifiable from documents and kept as the day-1 gate (Known limits). But it is no longer load-bearing: the mandatory copy reads and rehashes every byte anyway, so a dropped checksum only loses the early reject at PUT time — a wrong body fails the push inside `copy_blob`, never enters a pack. Note the full read now always happens inside the push request; that is the design, not the fallback.
Caveats from the first pass: `git-remote-edge` is the bulk of the effort and unshown — **not resolved** (Known limits; the server surface is `blobs/batch` plus ordinary receive-pack, stated). Filter gitlinks / page `blobs/batch` / batch-time quotas — **partially resolved**: 1,000-object and 5 GiB caps -> 413, claims paged at 1,000 ids, gitlink skip is a listed write-back (`extract_links` mode 160000) but exists in no sibling's code yet. Multipart > 5 GiB has no checksum — **resolved** by scoping to single PUT; the effective cap is ~4 GiB via `u32` `ObjRow.len`, disclosed. Key scheme reconciliation — **resolved**: per-repo `r/<repo_id>/blobs/<oid>` registered under A9. `size` inconsistency — **resolved**: `blob_claims.size`, the staged `blob <n>\0` header and `head().size()` are cross-checked (lines 169-170), `ObjRow.size` is always content bytes. Signed checksum byte-identical, `Content-Length` unsigned — **resolved**: the checksum is the only signed extra header, echoed in the `headers` map; size is enforced at copy time. Mode-160000 tree entries failing `head()` — **partially resolved**: same `extract_links` write-back; until it lands they fail as `unpack error missing object`, same as an ordinary submodule push today.

## Crash walk-through
Kill inside `blobs_batch` or `blobs_claims`: no awaits, so the span commits or discards wholesale (platform-facts #4; panic-rollback unverified, scenario 15) — claims are all-or-nothing and a retry is idempotent. Client dies after `batch` but before or during the PUTs: claim rows plus at most partial scratch keys exist, nothing references them, and `BlobSweep` removes keys then rows once `claimed_at + CLAIM_MS` passes — provided the alarm is ever armed (deviation 3) and the firing actually reaches them (deviation 2). Edge killed mid-`stage`: pack1 is `ingesting` with its rows, push `open`; `PUSH_TIMEOUT` (1 h) expires it, 5.2 kills pack1, 5.3 deletes the keys after GRACE — clean. Pack2 is the deviation-4 case: killed before `finish` leaves an incomplete multipart upload for the unverified R2 lifecycle rule (two-phase-push Known limits); killed between `finish` and the index post leaves a durable `packs/<pack2>.pack` with no row — invisible to every query and every sweeper, permanently. Killed between the post and commit: both packs `ingesting`, same expiry path, clean. `BlobSweep` killed between `delete_multiple` and the row deletes: keys gone, rows still stale — a later firing re-heads, finds no key, deletes the rows; self-healing if a later firing ever happens. A mid-slice kill also leaves the `jobs` row `running`, and section 4 has no stale-`running` reset while `enqueue` dedups on queued-or-running — the kind wedges until a boot re-enqueue that only covers `dead` rows (A4); inherited section-4 hole, same as the bundle-uri review found. Killed after commit: both packs live, refs moved; the scratch key and claim row are swept later — clean.

## Concurrency walk-through
Two pushes staging the same oid X: both `blobs_claims` calls lease the row (each `claimed_at = now` in its own span), both `copy_blob` stream the same scratch key into their own pack2s — duplicate sha across two live packs, legal per 2.3, deduplicated by `GcConsolidate`. A staged push against an ordinary push sharing content: the ordinary path never touches `blob_claims` or `blobs/`, so a stale claim cannot affect it; a blob that arrives in-pack goes `live` and the next `batch` answers `have`. Lease vs sweep: the lease UPDATE shares the claims span, so the sweep's stale SELECT cannot return a row leased after its read — but the post-await unconditional DELETE can kill it anyway (deviation 6); the effect is a 404 -> `unpack`, fails closed. A `GcSweep` between `push_begin` and commit bumps `gc_epoch` and the commit rejects all refs (3 step 2) — pack2 dies with the push at `PUSH_TIMEOUT`; no ordering yields a live ref into a dead pack. Inside the DO the only awaits are the sweep's R2 calls; both new routes are single sync spans, so there is no torn claim state. Two `batch` calls for one oid: the upsert last-writer-wins `claimed_at`, both URLs stay valid for the TTL, and identical-bytes is enforced twice (signed checksum, then the copy rehash).

## Interop check
A real `git` client sees nothing new: the feature is unreachable from stock `git push` (correctly disclaimed — the wire protocol has no "blob X is already there"), and the receive-pack bytes are untouched (`unpack <msg>` plus `ng <ref> unpack failed` per command on failure, `ok` per ref on success, per A2). The bespoke client POSTs `{objects:[{oid,size}]}` JSON to `blobs/batch`, PUTs exactly `blob <n>\0<content>` to `<account>.r2.cloudflarestorage.com` with the echoed `x-amz-checksum-sha1` (base64 of the 20 oid bytes — correct S3 checksum encoding), then drives `git pack-objects --revs --thin --stdout --filter=blob:limit` into an ordinary receive-pack POST. Byte-level: a body that is not `blob <n>\0...` fails header parse (`pre` bounded at 64 bytes, lines 161-170); a body whose `n` disagrees with the claim or with `head().size()` fails the three-way size check; a body that does not hash to the oid fails the final `try_finalize` comparison. A claim for a non-blob oid cannot be satisfied — `blob ...` bytes cannot hash to a commit or tree id without a SHA-1 collision, and `gix_hash` is collision-detecting (`unpack("sha1 collision")`). Since the oid equality is proven by hash, stamping `Kind::Blob` on the entry (line 193) is sound. Entries in pack2 are ordinary full-object entries, so fetch, `fsck` and GC paths need no new code — the interop claim holds. The batch route is JSON, not git-protocol; `Limit` -> 413 and `Forbidden` -> 403 there are correct for the bespoke caller. Scenario (a) is honest about needing a real bucket, and its assertion set (blob lands in the second pack, scratch key gone after CLAIM_MS + alarm, byte-exact clone) tests the right things.

## Blockers
- `copy_blob`'s deflate stage does not compile and cannot work on the pinned adapter: `gix_zlib::stream::deflate::Write` 0.1.0 has no `get_mut`/`try_finish`, and its `flush()` finalizes the stream (`FlushCompress::Finish`), so a multi-chunk blob would die at the first flush even if the names resolved. Rebuild on the public `Compress::compress(input, output, FlushCompress)` loop — which also restores the bounded-memory argument the current code silently breaks by accumulating all output in `inner`.
- `BlobSweep` cleanup is inoperative as written: nothing arms the alarm for it (the sibling `fetch` never calls `jobs::rearm`; A3) and `run_slice` never reschedules while non-stale claims remain, so claim rows and scratch keys leak indefinitely in a quiet repo.
- pack2's `packs` row must exist before the first part is uploaded — post `PackMeta::EMPTY` before `PackWriter::create`, mirroring `run` — or a mid-stage kill leaves a durable, unindexed pack object no sweeper can find.
- Cross-proof signature reconciliation: `IndexSink` field visibility, `PackWriter::create` arity (three call shapes across three proofs), `CommitRequest.pack_ids`/`run` return type vs the `receive_pack` call site. All mechanical, all required before the crate compiles.

## Caveats
- pack2 rows are posted in one `/_do/push/index` call; above 10,000 staged blobs the push fails `Internal` instead of chunking (deviation 5). For the headline case — few huge blobs — it is unlikely, but the feature is "giant pushes" and the wall is silent.
- `req.text()` buffers the entire batch body before the 1 MiB check (lines 243-244); a zone-capped 100 MB body is fully resident first.
- The sweep heads every stale key before `delete_multiple`; a delete of a missing key is a no-op (two-phase-push line 170), so the 150 heads per slice are avoidable subrequests.
- `MAX_BLOB` admits 5 GiB but `end_entry` fails `Limit` above ~4 GiB compressed (`u32` len); the batch should cap where the pack can succeed.
- `blobs_batch` fails the whole batch on the first oversize or malformed oid; native-lfs emits per-object `error` entries — divergent convention, worth aligning for the client's retry logic.
- The `pushes.pack_id` audit column has no specified value under `pack_ids` (deviation 7).
- Unverified, day-1 list stands: real-bucket `x-amz-checksum-sha1` enforcement and `checksum().sha1` population; `Request::new_with_init` JSON stub path; `web_sys::Crypto` for `PackId::random`; the deployed-Worker subrequest cap (platform-facts #7); deflate throughput on workerd for multi-GB inside 300 s `cpu_ms`; the abort-incomplete-multipart lifecycle rule. `sha2`/`base64` must enter the tree for `sigv4` — both pure Rust, wasm-safe.
- `Depends on: gc-and-repack-alarm` names a first-pass proof with no `proofs-v2/` counterpart; the jobs machinery it actually needs is contract-covered (section 4), so it is a naming dependency, not a code gap.
- The bespoke client remains unshown — without `git-remote-edge` speaking receive-pack itself, the feature has zero users; unchanged from the first pass and correctly scoped.

## Verdict
lands-with-caveats. The redesign is genuinely better: all three first-pass blockers are closed, two of them structurally — scratch keys are unreachable by any ref, and nothing awaits inside the ref span — and the third is defused by folding the rehash into a copy the bytes must undergo anyway. What remains is not redesign: one deflate loop rebuilt on `Compress`, a reschedule line in `BlobSweep`, a row posted earlier, and a cluster of mechanical signature reconciliations with its siblings. Scored down on feasibility and held on correctness because the centerpiece loop cannot compile or drain as written — that is a defect of code, not of approach.

# Second-pass review: Packfile parsing in a Worker with a streaming inflater

# Review v2: streaming-pack-parser (idea #4)

## Scores
- Feasibility 4/5 (was 4). Every gix call was checked against the pinned crates in the local registry: `header::decode(&[u8;12])`, `Entry::from_bytes` (panic-free on short input, `checked_shl`/`checked_add`), `Header::{write_to, verified_base_pack_offset, is_delta}` (`Header` is `Copy`, so `match rec.kind_or_delta` compiles), `File::from_data` + `with_alloc_limit_bytes` + `decode_entry(entry, out, &mut Inflate, &dyn Fn, &mut dyn DecodeEntry)`, `Decompress::{new, reset, total_in, total_out, decompress(&[u8], &mut [u8], FlushDecompress)}`, `Status::{Ok, BufError, StreamEnd}`, `deflate::Write::{new(inner, level), into_inner}` with `flush()` issuing `FlushCompress::Finish` (so the level-0 base is a complete stream, which gix's `decompress_complete_entry_from_data_offset` insists on: `status != StreamEnd` is `Corrupt`), `Compression::new(0)`, `gix_hash::hasher`/`try_finalize`, `gix_object::compute_hash`. Unverified per memo/contract: level-0 deflate at runtime on wasm32 (pure zlib-rs, low risk), real-R2 multipart rules, `wasm-streams` gzip (section 6, not this module).
- Reliability 3/5 (was 3). Crash and concurrency stories are now correct because the contract's ordering/janitor rules are followed, but pass B's memory arithmetic breaks the 128 MB isolate at the contract's own 32 MiB object cap (blocker 1), and crashed multipart uploads are never aborted (caveat).
- Correctness 4/5 (was 3). No wire byte in this module would break git 2.43-2.47; both first-pass interop breaks are fixed with code (one here, one in the sibling). Up from 3 because trailer SHA-1, resumable inflate, and delta resolution are now real code against real APIs.

## Contract compliance
Followed: module `src/pack/ingest.rs`; `stream_to_pending` signature and return type exactly as 1.4; keys via `keys::pending`; `pending/`/`packs/` layout 2.2; `Error::{Unpack, Limit, Protocol, Storage, Internal}` used per section 10; no `[]` indexing, no `unwrap`, only widening `as`; no `set_alarm`, no `rows_written`, no CAS in this module (edge code); 2,000,000-entry and 32 MiB caps; 10,000-row index posts; 1,000-id lookups delegated to caller; coalesced `read_entries` for external bases; nothing visible before `/_do/push/commit`.
Deviations (each a formal violation; all four are declared by the proof as write-backs, and in three the contract is the party that is wrong):
1. `resolve_and_normalize` gains `sink: &mut IndexSink` (1.4 has no such parameter). Needed: 2,000,000 `ObjRow`s (~56 B each) is 112 MB, so the contract's `-> Vec<ObjRow>` cannot hold the rows 2.4 itself says are posted every 10,000.
2. `store::RawWriter` is a new type (1.2 lists `PackWriter` only); `RawWriter::create/flush_if_full`, `Bucket::read_range`, `PackWriter::flush_if_full` all take `&mut ReqBudget`, which the 1.2 signatures do not. 7.1 ("every Bucket call charges first") is unimplementable without it since `Bucket` holds no budget.
3. `Bucket::read_entries(&[(ObjectId, ObjLoc)])` instead of `&[ObjLoc]`. The contract's own return type `Vec<(ObjectId, Vec<u8>)>` is impossible from `&[ObjLoc]`, which carries no sha.
4. Pass A does not use `BytesToEntriesIter` (2.4, 6.4). The proof is right: `next()` is synchronous over `BufRead`, reads the whole compressed entry inside one call, and cannot await body bytes; 6.4's claim that `EntryDataMode::Ignore` avoids this is false (the bytes must still be read). The replacement (`Entry::from_bytes` + `Decompress::total_in` + `Hasher`) produces the same `EntryRec` and trailer check.
Minor: one 48 MiB FIFO cache instead of "16 MiB LRU + 32 MiB base map" (same total, weaker hit behaviour); `bucket.repo` must become `pub`.

## First-pass blockers
- "Delete-only / pack-less pushes crash the parser": resolved, by code in the sibling `two-phase-push::run`, quoted: `if !body.fill(12).await? { return if body.buffered().is_empty() { Ok(None) } ... }` and `if count == 0 { ... return Ok(None); }`. `stream_to_pending` is never entered without a real pack, and its `for _ in 0..count` loop would run zero times anyway.
- "`sha1()` array-spread OOMs the isolate": resolved by code shown here: `take()` calls `h.update(bytes)` per chunk and `compute_hash(H::Sha1, kind, &data)` hashes in place. No JS arrays exist in the Rust path.
- "No tip-existence check before the ref flip": resolved by sibling code `repo-do-ref-authority::apply_one`: `let loc = idx.lookup(&[c.new])?...; if loc.is_none() { return Ok(Some("missing necessary objects")); }` inside the same sync span as the CAS, plus the `gc_epoch` guard (section 3 step 2). This module contributes `sink.links` for the 2.5 induction. Genuinely resolved, though the resolving lines live in two other proofs.

## Crash walk-through
Push of 40,000 objects, edge Worker dies in pass B after three `/_do/push/index` posts (30,000 rows, `packs` row `ingesting`). State: `pending/<push>.pack` complete in R2; `packs/<pack>.pack` is an incomplete multipart upload with no visible object; `pushes` row `open`; refs untouched; `Index::lookup` joins on `state='live'` so no reader sees the 30,000 rows. Client gets a dropped connection and retries with a fresh push_id, which succeeds independently. After PUSH_TIMEOUT the Janitor sets the push `expired`, marks the pack `dead` and deletes its `objects` rows in one span, and after GRACE deletes `pending/` (the `packs/` key delete is a no-op). Correct. Hole: neither this proof nor CONTRACTS.md aborts the orphaned multipart upload (the upload id is only in the dead Worker's memory), so its parts persist and bill until an R2 lifecycle `abortMultipartUploadsAfter` rule exists. Crash in pass A leaves the same orphan for `pending/`.

## Concurrency walk-through
Pushes A and B, both thin against live base X, at once. Both `/_do/push/lookup` X (sync, both see it live), both `read_entries` X from R2, both write distinct `pending/` and `packs/` keys and distinct `packs` rows, both post rows for their own pack_id, both commit. Per-ref CAS gives one `ok`, one `ng failed to update ref`; the loser's pack is `live` with junk until GC, which the contract accepts. If `GcSweep` kills X between A's lookup and A's commit, A's `gc_epoch` differs and A is rejected (section 3 step 2); A's range read of X still succeeds because R2 deletion is GRACE after `dead`, longer than any request. No path yields a live ref into a dead pack. The FIFO cache is per request, so nothing is shared between A and B.

## Interop check
git 2.43-2.47 pushes receive-pack over v0 (there is no v2 push); this module only sees bytes after the command flush. It accepts exactly what `send-pack` emits: `PACK`, version 2, count, entries with ofs-delta (advertised) and ref-delta (thin), a 20-byte SHA-1 trailer, nothing after. Rejecting bytes after the trailer is safe: git sends none. Ref-deltas against in-pack bases that appear later would fail `missing base`; git's pack-objects never emits that ordering. Zero-object packs and delete-only bodies are handled before entry (sibling). No wire byte breaks. The `Status::BufError`-with-progress loop is correct: zlib stops consuming at `StreamEnd`, so `total_in` is the exact member length and the next entry's header is byte-aligned.

## Blockers
1. Pass B peak memory exceeds 128 MB at the contract's 32 MiB single-object cap. For one 32 MiB incompressible blob (zlib stored blocks): `Window::entry` reads the entry (`self.buf` 32 MiB) and copies it (`to_vec`, `raw` 32 MiB); `decode_mini` copies it again (`mini.extend_from_slice(body)`, 32 MiB); `decode_entry` allocates `out` 32 MiB = 128 MiB before `PackWriter::append_entry` re-deflates into the part buffer (another ~32 MiB) and before the 48 MiB cache. With a delta on top, `base` (Rc, 32) + `mini` (32) + `out` (32) + window + part is over the limit again. Fix is mechanical: hand `decode_mini` a borrowed window slice, build `mini` only for the base, and either drop the cap to 16 MiB or drop the level-0 copy (the described `cache::DecodeEntry` adapter). The contract's own day-1 test ("one 32 MiB blob with a delta") would fail as written.
2. Four signature/spec deviations from CONTRACTS.md (above). Each is a required write-back before this module can be coded against the contract; three fix contract errors, so the blocker is on the contract owner, but the proof cannot land against the file as it stands.

## Caveats
- FIFO, not LRU, cache: prefetched external bases are evicted first once 48 MiB of in-pack objects flow past; a thin pack whose many deltas target one external base late in the pack re-reads it via `external()` per miss (one range read each, budgeted, not coalesced).
- Orphaned R2 multipart uploads after a crash need a bucket lifecycle rule; not in the contract.
- `packs` row inserted `ingesting` on the first index post needs placeholder `count/bytes/commit_lo/commit_hi`; 1.2 has no `update_pack_meta`, only `insert_pack`/`set_pack_state`.
- Level-0 deflate copy per delta application: memcpy + adler32 of the base per delta; a 30 MiB base with 500 deltas is seconds of CPU. Described optimisation not written.
- Unverified at runtime: level-0 `deflate::Write` on wasm32, real-R2 5 MiB/equal-part rules (#6), subrequest ceiling (#7), deployed cold start and the 128 MB joint bound (platform-facts open items).
- Delete-only and tip-check resolutions depend on sibling proofs `two-phase-push` and `repo-do-ref-authority` shipping their quoted lines.

## Verdict
lands-with-caveats, conditional on the four write-backs. Better than v1 with numbers: 3/3 first-pass blockers resolved by code (one here, two in siblings), every API name verified in the pinned sources rather than assumed, resumable inflate removes the 2x CPU retry, and trailer SHA-1 is real. One new blocker (memory copies, about a day) and one process blocker (CONTRACTS.md 1.2/1.4/2.4/6.4 must be corrected). Effort to a working `pack::ingest` against real git: 2-3 weeks including the write-backs, the two conformance scenarios (7, 9) and the added "chain past the cache" test.

# Review v2: pinned-delta-bases (idea #8)

## Scores
- Feasibility 4/5 (was 4). Every host and crate call now exists as named: I checked `worker` 0.8.5 `src/sql.rs` (`SqlStorageValue::Blob(Vec<u8>)` line 30, `exec(&self, &str, impl Into<Option<Vec<SqlStorageValue>>>)` line 201, `raw()` line 388 converting `Uint8Array`/`ArrayBuffer` to `Blob` lines 154-167), `gix_object::Kind { Tree, Blob, Commit, Tag }` (lib.rs line 85, so the `kind_num` match is required and right), `ObjectId::{from_hex, as_slice}` and `TryFrom<&[u8]>` (object_id.rs lines 72, 128, 315). `split_at_checked` is std 1.80. Still unverified at runtime: Blob round trip, `RequestInit::with_body` stub path, level-0 deflate on wasm32, 2 MB SQLite value cap.
- Reliability 3/5 (was 4). Lower, not higher: the one invariant this module owns, "the table fits `PIN_BUDGET`", is broken by its own `for _ in 0..8` eviction loop (Blockers 1). Everything else is a pure cache with span-atomic writes, so the failure is unbounded DO storage growth, never wrong bytes.
- Correctness 4/5 (was 3). Up because no byte on the wire depends on this module any more; the first-pass `--fix-thin` hole is closed by construction. Down from 5 for the wrong loop-bound claim, an `Error::Protocol` on an internal body, and a `gen` that is not a push ordinal under concurrency.
- Effort: weeks. This module is 2-3 days; it needs all six named foundation slugs compiled and two of their function bodies edited (section 9 rounds, 2.4 between-passes).

## Contract compliance
Matches: `store::pins` imports no `worker` (1.2); both routes are body-then-one-sync-span with `Awaits inside: none` (1.3, lines 99-114, 136-142); no `set_alarm`, no `JobKind` (4.1, 4.5); existence is only ever `Index::lookup` / the 2.3 query (`bases` line 138, `load_entries` receives `ObjLoc`s); no `rows_written`, no `changes()` needed; R2 keys never built here (`Bucket::read_entries` over `meta.repo_id`, 2.2/8); section 10 lint set honoured (`split_at_checked`, `get`, `try_from`, `saturating_*`, no `[]`, no `as`); pins are sent only after `commit_push` returned an `ok` (section 3 ordering). Section 12 lists "pinned bases" as not built; the proof correctly positions itself as post-foundation and lists its write-backs.
Deviations:
1. `decode_frames` line 42 returns `Error::Protocol("bad pin frame")` for a body produced by our own edge. Section 10 defines `Protocol` as "malformed client bytes" -> 400; an internal framing failure is `Internal` -> 500. One-word fix.
2. `pin_put` line 110 bounds eviction at 8 rounds of `DELETE ... WHERE gen = MIN(gen)`, with the comment "a generation is <= PIN_PUSH_MAX, so 4 rounds always suffice". False on two counts: (a) `gen = refs_version` is read at pin time (line 102), so pushes A, B, C that commit before any of them pins all land in one gen of up to 3 x 2 MiB; (b) gens can be tiny (a one-line commit pins ~1 KiB). After 8,000 small commits (8 MiB, 8,000 gens) each 2 MiB push removes 8 KiB and adds 2 MiB: 1,000 such pushes leave ~2 GB in `pins`. The proof's "bounded by PIN_BUDGET" (Why it works, bullet 3; Known limits) does not hold. Fix: loop until `SUM <= PIN_BUDGET` (terminates: each round deletes >= 1 row) or one `DELETE WHERE gen <= ?` from a cumulative window query.
3. `PinCollector::offer` must be called from inside `resolve_and_normalize` (2.4), whose 1.4 signature has no collector parameter; the proof adds a field or argument it does not show. Same drift class the two-phase-push review flagged.

## First-pass blockers
1. "`ctx.id.name` is undefined ... `repoKey` yields `objects/undefined/<sha>`": **resolved structurally.** No key is derived in this module; the cold path is `bucket.read_entries(&cold, budget)` (lines 90, 153) and `Bucket { inner, repo: RepoId }` builds `r/<repo_id>/packs/...` from `meta.repo_id` (refs-sqlite-objects-r2 line 166). `Reflect::get` appears nowhere.
2. "`clientHas` ... shallow and partial-clone clients ... `index-pack --fix-thin` fails": **resolved by removing the feature.** No `REF_DELTA` is ever emitted: `write_pack` copies full entries from R2 windows (section 9 step 6) and `load_entries` only pre-fills `MemFind` (lines 151-153). There is no `clientHas` to get wrong. Honest reading: the idea as titled ("incremental fetches can delta against them") is abandoned; what remains is a DO byte cache for the negotiation rounds and thin-push bases. The proof says so ("Known limits", first bullet).
First-pass caveats: zlib boundary (moot, re-encoded via `encode_entry` line 63), sideband framing (owned by `wire`), `deflateSync` in the DO (no deflate in the DO; `encode_entry` runs at the edge, capped 256 KiB/object, 2 MiB/push), live-cursor delete (no cursor, `SUM` re-read per round), `deltas` table (gone): all resolved.

## Crash walk-through
Edge dies after `/_do/push/commit` returned `ok` and before `/_do/push/pin`: refs moved, pack live, client may see a hung connection (the sibling's problem), pins simply absent; next fetch pays the contract rounds. DO throws inside `pin_put` at frame 500 (`entry_header` fails): per section 3 the span's inserts roll back only if the handler *throws*; if the route maps the `Err` to a 500 `Response` without throwing, 499 rows persist and eviction never ran, so the table sits over budget until the next successful `pin_put`. Harmless for bytes (every pin is also in a live pack), but it is a second way the budget invariant is soft. Edge dies mid-`fetch_bases` (after the stub call, before `read_entries`): push aborted, `pending/` and `ingesting` rows take the Janitor path (5.1-5.3); nothing pinned. No path leaves a pin for a sha that `Index::lookup` will resolve to bytes different from the pin, because sha is content-addressed.

## Concurrency walk-through
Fetch F is in `fetch_v2` step 5 round 3; `load_entries` had one cold miss and is awaiting `read_entries`. Push P's `/_do/push/pin` runs in that gap: `pin_put` inserts P's gen and evicts the two oldest gens, one of which held trees F loaded in rounds 1-2. F already copied them into `mem` (line 151, sync, before the await), so nothing tears; F's round 4 calls `pins_take` again and any evicted id falls to R2 with the `ObjLoc` it already holds. `write_pack` reads R2 windows, unaffected. Pushes A and B commit back-to-back and pin concurrently: both read `refs_version` = N+2, both spans are serial (sync), `ON CONFLICT(sha) DO UPDATE SET gen` makes overlapping shas idempotent; the two land as one gen and are evicted together (deviation 2a, benign). `GcSweep` runs between F's `Index::lookup` and F's `pins_take`: F gets a stale pin for a now-dead pack, exactly as it would get the R2 bytes of that pack (key survives GRACE); same behaviour as the contract path. A `pin_put` of 20,000 tiny objects is one sync span of 20,000 `INSERT`s; every other event on that DO waits for it. The proof flags a day-1 timing test but does not move the call out of the push's response path (`ctx.wait_until` after report-status would).

## Interop check
This module writes no wire bytes. git 2.43-2.47 with protocol v2 sends `thin-pack` in `fetch` args; the server ignores it and sends full entries, which git accepts (a thin pack is permitted, not required). `x-ge-subrequests` is an unknown response header git ignores. Ingest `bases` bytes are `decode_entry`'d into the 32 MiB base map exactly as `read_entries` bytes are, so `--fix-thin`-style resolution on the server side sees identical input. No byte breaks. Scenarios 9 and 12 are the right gate; 12b's byte-identical-pack assertion is the correct oracle because the response path is unchanged.

## Blockers
- Eviction loop bound (deviation 2): `pins` grows without bound under the ordinary pattern "many small commits, then large pushes"; the stated invariant and the "4 rounds" comment are wrong. One-line fix, but the proof's reliability claim rests on it.
- `Error::Protocol` for an internally produced body (deviation 1) violates the section 10 mapping.

## Caveats
- `gen` is pin-time `refs_version`, not a push ordinal; concurrent pushes share a gen. Fine as a cache, but do not describe it as "push order".
- `SUM(bytes)` counts entry bytes only; the 40-char sha, index and row overhead add ~100 B per row, so the real footprint of an 8 MiB budget of small objects is ~12 MiB.
- `resolve_and_normalize` needs a collector hook (deviation 3); the section 9 rounds and 2.4 between-passes step must be edited in two sibling modules.
- Benefit is unmeasured and smaller than the title implies: 7.4 already coalesces commits per pack, so step 3 gains ~1 read per young pack; the real saving is the serial tree-depth rounds of step 5 and one `bases` call on thin pushes. `write_pack` still reads R2. This overlaps heavily with `in-do-object-cache`; one of the two should absorb the other.
- Unverified at runtime: Blob round trip through `exec`/`raw()`, `RequestInit::with_body` stub path, level-0 wasm32 deflate, DO SQLite 2 MB value cap, `IN (...)` with 100 bindings.
- Push latency: the pin call and its sync `INSERT` burst sit before the client's report-status unless the edge defers it.

## Verdict
lands-with-caveats. Genuinely better than the first pass on the things that mattered: both blockers are gone structurally (no key derivation; no wire deltas at all), every API is now traceable to a source line, and the crash and concurrency walks are clean. It is also a smaller idea than it was: no delta bases, a DO byte cache for negotiation rounds and thin-push bases. Correctness 3->4. Reliability 4->3 only because the single invariant the module owns is broken by an 8-iteration loop; fix that and the `Protocol` variant and it lands.

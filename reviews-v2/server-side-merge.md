# Second-pass review: Server-side three-way merge in the Worker

# Review v2: server-side-merge (idea #17)

## Scores
- Feasibility 4/5 (was 4). Every host surface exists or is a declared write-back: `GET /_do/refs` and the `pack` param on `/_do/push/lookup` are contract + sibling (1.3, two-phase-push lines 95-126), `SELECT changes()` is measured 1/0/1 (platform-facts #1), sync-span atomicity is measured (#4), and the option-section framing is exactly gitprotocol-pack's rule (options after the command flush, only on client echo). The one real unknown is the vendored 926-line `gix-merge` text driver (memo 3: imports only `imara_diff` + `bstr`) — claimed, not built. As written the file does not compile: five verified-wrong calls (deviation 3), all mechanical.
- Reliability 4/5 (was 3). The first-pass orphan class is closed structurally: merge objects are a normalized pack whose `packs`/`objects` rows + `live` flip share the CAS span, and a lost CAS marks it `dead` in the same span (lines 270-298). Residuals: a kill between `PackWriter::finish` and `/_do/merge/cas` leaves a *completed*, rowless R2 object that nothing deletes (deviation 7 — the proof calls it the accepted ingest residual, but ingest's residual is the *incomplete* multipart and two-phase-push posts `PackMeta::EMPTY` before `create` precisely to close this); `?` paths inside `plan` skip `out.abort()` (only the conflict path aborts, line 113); prefetch re-runs append duplicate entries.
- Correctness 3/5 (was 2). The headline defect is fixed — merge objects are registered in the CAS span so `Index::lookup` sees `new` immediately, and the wire path (echo-gated option parse, band-1 report-status, client-only result refs, band-2 note) is right. Deductions: `merge_base` drops paint-down's re-queue-on-flag-gain and can falsely answer `unrelated histories` under timestamp inversion (deviation 4); a file->dir change on both sides silently resolves to the merged directory, dropping the base file — the one dangerous-direction acceptance in a design that claims "everything else is a conflict" (deviation 5); a `merge_cas` error after the attempt-0 commit reports `ng` on a feature ref that already moved (deviation 6).
- Effort: weeks. The shown code is days on top of the foundation; vendoring the driver, reconciling the triplicated merge machinery (deviation 9), and the receive-pack integration branch are the work.

## Contract compliance
Matches: A9 REGISTRY block present and honest (lines 26-31: wire write-backs, `POST /_do/merge/cas` "Awaits inside: rearm", deps, no new tables/JobKinds/R2 prefixes); section 9 shape — `merge_trees`/`union`/`commit_info`/`write_tree`/`write_obj` are `fn`s over `MemFind`, `load` is the async filler in <= 1,000-id chunks (7.3) with coalesced `read_entries` (7.2), `WALK_MAX`/`MEM_MAX` bounds (lines 141, 203); section 3 mirrored — `PackWriter::finish` durable before any row (line 119), pack rows + `live` flip + tip check + CAS + reflog + `refs_version` + `GcMark` in one sync span (lines 266-292), `changes()` the only oracle, `push_id` NULL per the gc_consolidate precedent (2.3); A3 — `enqueue` inside the span, `rearm(self).await` after (line 254); A1 signatures used correctly (`create` 4-arg, `append_entry -> Result`, `finish(budget)`); A7 16 MiB cap (line 230) and 10,000-row cap (lines 231, 269); `commit_push` DTO matches repo-do-ref-authority's `CommitRequest{push_id, pack_id: Option<String>, principal, commands: Vec<CmdDto>}`/`results: Vec<(String, Option<&'static str>)>` (its lines 31-34); scenarios named, two added, harness note stated (section 11, lines 357-358); no `set_alarm`, `transactionSync`, `Reflect`, `unwrap`/`expect` on client bytes.
Deviations (each also in the structured list):
1. The v0 advertisement gains `push-options` — against rule 5's "exactly" cap list and section 12's explicit not-advertised list. Declared in REGISTRY and load-bearing for the idea; same class as server-side-rebase's rule-6 additions, which its review accepted under A9. Declared write-back, not smuggled.
2. `ReceiveCaps.push_options` / `ReceiveHeader.options: Vec<BString>` change contract `wire` types (1.1); `MergeCasDto`/`MergePackDto`/`RefsDto` join `wire::http` (A8). Declared.
3. Verified-wrong calls (does not compile as written): `gix_object::compute_hash(kind, data)` (line 232) — 0.64.1's signature is `(hash_kind, object_kind, data)`; `TreeRefIter::from_bytes(&data)` (line 187) and `CommitRefIter::from_bytes(&data)` (line 211) — both take `(data, hash_kind)`; `id: ent.oid` (line 189) — `EntryRef.oid` is `&oid`, needs `to_owned()`; `mem.exists` (lines 143, 168) — `gix_object::Exists` is not in the line-34 use list. The same `compute_hash`/`from_bytes` drift was verified in the wasm-git-core and server-side-rebase reviews. All mechanical.
4. `merge_base`'s `QUEUED` bit (line 137) prevents re-queueing a commit that gains flags after being popped. git's `paint_down_to_common` re-pushes a parent whenever it gains flags (`prio_queue_put` is unconditional on flag change); here a commit popped while `P1`-only and later gaining `P2` is never revisited — it is neither recorded as a base nor propagates `P2` to its ancestors. Under timestamp inversion (rebase, cherry-pick, clock skew — precisely why git keeps a heap) this yields a worse base or a false `unpack unrelated histories`. Safe direction only.
5. `union` filters non-tree base entries (line 183), so when base is a file and both sides made it a (different) directory, the recursion merges children as add/add and returns the merged tree — the base file's content is silently dropped where git reports `CONFLICT (file/directory)`. The comment at line 148 and the Known-limits safety claim are falsified in this narrow case. (A base tree with both sides changed to a regular file is accidentally safe: the tree bytes hit the NUL check at line 172.)
6. After `/_do/push/commit` succeeds on attempt 0, any `merge_cas` result other than `ok`/`failed to update ref` maps to `Err(Error::Unpack)` (line 86) → HTTP 200 + `unpack <msg>` + `ng` on a feature ref that already moved. The only reachable case is `"gc ran during push, retry"` (a sweep in the commit→cas window). Should take the 3-attempts note path once `results` is populated.
7. No `packs` row precedes `PackWriter::create` for the merge pack (lines 101-103): a kill in the finish→cas window leaves a completed `packs/<id>.pack` with zero rows — Janitor 5.3 needs a `dead` row and the R2 abort rule covers only *incomplete* multipart uploads, so nothing ever deletes it. Lines 319/352 claim this is "precisely the residual the contract already accepts for ingest" — it is not; two-phase-push posts `PackMeta::EMPTY` before `create` (its line 64) to close exactly this window, and the wasm-git-core review flagged the identical ordering as deviation 5.
8. `Error::{Limit, Budget, Conflict, Internal, Storage}` raised after the header (lines 141, 203, 230-231, and every `?`) hit the sibling's `Err(e) => return Err(e)` arm (repo-do-ref-authority line 175) → 413/500 after the pack was uploaded, not the 200 + `unpack` + `ng` A2 requires. Line 313's error-policy bullet claims the A2 mapping; the sibling shown code implements it only for `Unpack`. Shared with two-phase-push review deviation 6; the fix lives there.
9. Merge machinery is now triplicated and already drifting: this proof's `merge_trees(mem, Option<E> x3, path: &BStr, out, rows, conf, need)` + paint-down `merge_base` + `union`/`write_tree`/`sort_name`/`commit_info`/`load` (lines 124-228); server-side-rebase carries the same `Option<E>` signature family in the DO (its lines 130, 160-181) with both-changed blobs as `conflict`; wasm-git-core carries a third architecture (`Load` enum, `&ObjectId` roots, `Tm::dir`, its lines 64-186). The drift is concrete, not hypothetical: `join` adds `/` (line 245) where wasm-git-core mangles nested paths (its deviation 2); file/dir resolves silently here, 400s there, conflicts in rebase; the three base walks have three different bugs. The vendored driver is registered twice at two paths with two signatures — `src/merge/text.rs` `merge(&b,&o,&t) -> Result<Vec<u8>>` (line 173) vs `src/core/merge_text.rs` `merge(b,o,t,ConflictStyle) -> Result<(Vec<u8>, u32)>` (wasm-git-core lines 26, 33, 158-160) — and this proof's Depends-on names server-side-rebase (line 368) but not wasm-git-core. One module must own merge.
10. The `GET /_do/refs` call hand-rolls `Request::new` + `fetch_with_request` + `.json()` (lines 68-70) with no `status_code` check and no `Error::from_do_response` — a DO error becomes `Internal("do response: ..")` instead of the typed error. `branch-level-dos`'s `stub_get` (its lines 127-133) is the existing pattern. Mechanical.
11. reflog `push_id` is `format!("merge:{}", b.push)` (line 289): a pseudo-id that does not join to `pushes.id`. Contract-silent (TEXT, no FK; same pseudo-id convention rebase uses); audit value only.
12. `merge=` accepts exactly one option and one command (lines 50-56): `git push -o merge=main origin f1 f2` is rejected whole (`unpack merge takes one option and one ref update`) though stock git can legally send it. A real restriction, stated nowhere as a limit.

## First-pass blockers
1. "Merge objects are invisible to `commit()`: `known(mergeSha)` fails ... Needs a `stub.register(pushId, objects+links)`": **resolved**. `/_do/merge/cas` is that registration in one sync span — `packs` row + `objects` rows + `live` flip precede the tip check and CAS (lines 267-279), so `Index::lookup` sees `new` in-span (the ref-authority same-connection argument). `commits`/`parents`/`introduced` correctly do not exist (section 12); ancestry is walked over objects.
2. "tip unfetchable and un-merge-able next time; abandoned merge objects leak permanently": **resolved** with one residual. The merge pack is a normal `live` pack served by the 2.3 query, so the tip is fetchable and the next `merge_base` walks it. CAS-loss packs go `dead` + rows deleted in the same span (lines 286, 295-301), swept by Janitor 5.3 after GRACE. The residual is the finish→cas completed-object window — deviation 7, real but narrower than the first pass's permanent loose-object leak.
3. "Sideband-wrapped report-status and push-options capability echo check": **resolved by dependency**. `write_report_status` band-1 framing is `wire` (rule 4) and the echo-gated option parse is a declared write-back to `parse_receive_header`; results carry only client-named refs and the note rides `Sideband::progress`. The shown wiring stops at `merge_push` returning `(results, note)` — the `receive_pack` branch that calls `merge_target`/`merge_push` and emits the band-2 note is not shown in either proof (integration write-back). Non-`Unpack` errors still miss the 200-report arm (deviation 8).
Caveats from the first pass: single-BFS base without generation ordering -> **partially resolved** (paint-down + commit-time heap is git's algorithm minus generations, but deviation 4 drops its re-queue — false `unrelated histories` becomes possible, still safe-direction). Blobs written before conflicts known -> **resolved** (conflict path is `out.abort()` + `Err`, line 113; no rows ever precede the CAS span). `x-git-user` spoofable -> **resolved** (ident is `Principal.name`/`@git-edge`, line 115; newline sanitization deferred to an `auth` invariant, declared line 354). Memory/CPU bound by largest blob -> **resolved** (16 MiB/64 MiB/100k-commit caps surface as `Limit`, distinct from conflict). `send-pack` warns not rejects -> **resolved** (results hold only client refs; merge outcome is band-2 or silent). UTF-16 tree sort -> **resolved** (`sort_name` compares raw bytes, dirs as `name/`, line 244). Delete/empty-pack unguarded -> **resolved** (`merge_target` rejects delete/self/multi-command before any object is touched; a 0-object pack resolves `theirs` through the live index). `ok`-for-feat-b leak -> **resolved** (per-ref independence by contract; the report is built once post-loop). `commits(sha,parents)` vs `parents(oid,parent)` mismatch -> **resolved** (neither table exists; `merge_base` parses commit objects, lines 207-216).

## Crash walk-through
Kill before or inside `plan` (any `load`/`lookup`/`PackWriter` await): the client push is `open` with an `ingesting` pack — Janitor 5.1 expires it at +`PUSH_TIMEOUT` (1 h), 5.2 kills the pack and its rows in one span, 5.3 deletes `pending/` and `packs/` keys at +`GRACE`. The merge pack's MPU parts have no row — the incomplete-multipart residual, cleanup resting on the unverified lifecycle rule (#6 class). Kill between `out.finish` (line 119) and the cas call: a **completed** `packs/<id>.pack` with no row anywhere — permanent leak, deviation 7; the claim that this equals the ingest residual is wrong (completed object vs incomplete MPU; the sibling's `PackMeta::EMPTY` ordering exists to prevent exactly this). Kill inside `merge_cas_span`: atomic — either nothing or pack-`live` + ref moved + reflog + `refs_version` + `GcMark` row together; the `ingesting` merge pack can never persist (created and flipped in one span), so 5.2's `JOIN pushes ON push_id` — which never matches NULL — is untested but unreachable. Kill between cas `ok` and `jobs::rearm().await` (line 254): the `GcMark` row is queued; the alarm is unarmed only in a vacuum — the Janitor's self-enqueued 15-min chain keeps a pending alarm in steady state (4.2). Kill after cas, before report-status reaches the client: both refs moved, client sees a hangup, next `fetch` reconciles — git-over-HTTP normal. Kill after the attempt-0 commit but before a successful cas: feature moved, merge never landed — consistent with the stated per-ref semantics, reported (when reachable) via the note path.

## Concurrency walk-through
Two `merge=main` pushes A and B both sample `ours = T0` from `/_do/refs`, both build merge packs in parallel (every stub/R2 await opens the input gate; the merges hold no DO locks — correct by design). A's `merge_cas_span` wins `UPDATE refs ... WHERE target=T0` (`changes()` 1/0, measured #1); B's span gets 0, `kill_pack` marks B's pack `dead` and deletes its rows in the same span, returns `failed to update ref`; B's attempt loop re-reads the tip (now `MA`, `live`, walkable), re-merges, CASes `MA -> MB`. Bounded at `ATTEMPTS = 3`; each loser's pack is swept after GRACE; on exhaustion B's feature still landed with a band-2 note — honest under section 3's per-ref rule. Merge vs a plain push to `main`: identical CAS race, same outcome. Merge vs `GcSweep` between `plan` and cas: the sweep's span bumps `gc_epoch`, cas's first statement returns `gc ran during push, retry` — clean rejection pre-commit, deviation-6 false `ng` post-commit. Merge vs Janitor: the merge pack is `ingesting` and `live` (or `dead`) inside one span, so no interleaving exposes it; `GRACE` (1 h) > `max_ms` (240 s) keeps 5.3 honest. A `ingesting` merge pack racing 5.2 is impossible — the NULL `push_id` never joins `pushes`, and no such row can exist outside the span.

## Interop check
Wire-level: v0 receive-pack regardless of `Git-Protocol`; the option section is one pkt-line each between the command flush and the PACK, parsed only when `caps.push_options` was echoed — the first-pass "eat the pack header" break is closed by construction. Report-status frames `unpack ok` + `ok/ng refs/heads/feature` in band 1 under `side-band-64k` (rule 4); `main` is never in `results` (send-pack warns on unknown refs — the review's correction honored). The merge note is band-2 `Sideband::progress`, dropped without sideband — the `ok`/`ng` lines still carry the outcome. The merge commit is canonical — `tree`/`parent ours`/`parent theirs`/`author`/`committer`/message — so `git fetch` + `rev-parse main^2` = feature tip and `fsck` is clean provided `who.name` is sanitized (newline would corrupt the header; declared as an `auth` write-back, line 354). Trees are byte-sorted with dirs-as-`name/` — the first-pass `treeNotSorted` break is fixed. Real exposure: deviation 8's non-`Unpack` errors print `RPC failed; HTTP 413` / `the remote end hung up` after the pack upload; deviation 12 rejects legal multi-ref pushes wholesale; a post-commit `gc ran` reports `ng` on a landed ref (deviation 6). Scenarios (a)/(b) are consistent with the code as written — including "no `packs` row for the merge attempt" on conflict, since rows exist only inside the cas span.

## Blockers
- Deviation 9: three parallel tree-merge implementations now exist with divergent semantics and the same 926-line driver is registered at two paths with two signatures (`src/merge/text.rs` vs `src/core/merge_text.rs`); this proof's Depends-on does not name wasm-git-core. One shared module (`src/merge` or `src/core`) must own the driver, the tree merge, and the base walk before all three land — the rebase proof already defers the driver to this one.
- Deviation 7: the finish→cas window leaves a completed, rowless pack no mechanism deletes; post a `packs` row (`ingesting`, `push_id` NULL) before `PackWriter::create` — the sibling's `PackMeta::EMPTY` pattern — or accept a permanent leak and say so honestly.
- Deviation 4: `merge_base` is not the paint-down it claims — the `QUEUED` dedup suppresses git's re-queue-on-flag-gain, so timestamp inversion can return `None` for related histories. Re-push on flag gain (flags are monotonic, so it still terminates) or stop claiming `commit-reach.c`.
- Deviation 3: five verified-wrong calls (`compute_hash` arity, both `from_bytes` arities, `EntryRef.oid` ownership, missing `Exists` import) — mechanical, but the file does not compile as written.
- Deviation 5: file↔dir on both sides silently resolves to the merged directory — the one dangerous-direction acceptance in the design; either conflict it or check the base entry's kind in `union`.

## Caveats
- Deviation 6: post-commit `merge_cas` failures report `ng` on an already-moved feature ref; degrade to the exhausted-attempts note once `results` is set.
- Deviation 8 (inherited): `Limit`/`Budget`/`Conflict` from merge paths hit the sibling's `Err` arm → 413/500, not `unpack`/`ng`; the fix belongs in repo-do-ref-authority's receive arm.
- Prefetch re-runs re-append already-written blobs/trees to `out`/`rows` (lines 104-112): duplicate pack entries (legal, `objects` dedups on `(sha, pack_id)` so the first offset wins) plus duplicated conflict paths in the message — cosmetic bloat, bounded by the 10,000-row cap which the duplicates also consume.
- `plan` abandons the MPU without `abort()` on `load`/`lookup`/`write_obj` errors (only conflict aborts, line 113) — same orphan-part class flagged in the wasm-git-core review.
- `merge=` restricted to one option + one command (deviation 12); reflog `push_id` is a pseudo-id (deviation 11); the `receive_pack` integration branch and band-2 note emission are unshown (integration write-back, noted under blocker-resolution 3).
- `/_do/refs` returns the whole ref list per attempt — JSON-parse cost ×3 on ref-heavy repos; fine but uncounted.
- Unverified per memo/platform-facts and honestly flagged (line 356): `Request::new`/`new_with_init` + `apply_headers`, `Token::Committer`/`SignatureRef.time.seconds`, `EntryMode::kind`/`EntryKind`, `Find::try_find` return shape, `web_sys::Crypto` (`PackId::random`, 8.2), real-R2 multipart and subrequest enforcement (#6, #7), the vendored driver end-to-end on wasm.
- `mem` persists across attempts and across `plan` calls — correct (epoch guard at cas), and `MEM_MAX` bounds it; a third-attempt merge inherits two attempts' worth of loaded objects.

## Verdict
lands-with-caveats. The first pass's fatal gap — merge objects invisible to commit and uncollectable — is closed structurally by registering the pack inside the CAS span, and the wire story (echo-gated options, band-1 report, client-only result refs) is now right. Reliability 3->4, correctness 2->3. What remains: the merge machinery must be de-triplicated against wasm-git-core (and rebase, which already defers to this proof), the finish→cas window needs the sibling's row-first ordering, `merge_base` must either implement paint-down's re-queue or drop the claim, and the compile cluster is mechanical but real.

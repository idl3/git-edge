# Second-pass review: Server-side rebase and squash as protocol v2 extensions

# Review v2: server-side-rebase (idea #18)

## Scores
- Feasibility 4/5 (was 4). Every used API exists in the pinned set: `gix_object::TreeRefIter`/`CommitRefIter::from_bytes(..).parent_ids()`/`compute_hash` (0.64.1, wasm CI per memo section 3), `gix_validate::reference::name_partial` (0.11.4), `SqlStorage::exec`/`SqlCursor::{to_array,one}`/`SELECT changes()` (platform-facts #1), `jobs::{enqueue,rearm}`/`SliceOutcome`/`SliceBudget` (4.x + A3/A4), `Bucket::resume_multipart_upload` (memo section 1; `PackWriter::resume` is a declared write-back, contract 5's GcConsolidate needs the same). `Request::new_with_init` JSON stub path remains unverified at runtime, as in every sibling. As written the code does not compile against its siblings (`compute_hash` arity, `ObjRow::new`), and one internal inconsistency breaks resume (deviations 1, 3, 4) — all mechanical.
- Reliability 4/5 (was 2). The three first-pass job holes are closed structurally: the shared dispatcher drains `rebase_jobs`, both client routes run `enqueue` + `rearm().await` (A3), errors take the 4.4 backoff path, and deterministic committer (`created_at`) + byte-copied author make regeneration byte-identical, killing the `Date.now()` orphan class. Residuals: a crash in the `[finish() returned, commit span committed]` window leaves a completed multipart upload that `PackWriter::resume` cannot resume (S3 semantics: completed upload ids are gone) — the row grinds 4.4 retries until the Janitor write-back fails it at `PUSH_TIMEOUT`; and a permanently erroring oldest `running` row head-of-line blocks later ones (`ORDER BY created_at LIMIT 1`, `step(...)?` before the second SELECT) for the same hour.
- Correctness 3/5 (was 2). Squash is now a real branch (`todo=[tip]`, `merge_trees(base, onto, tip)`, one commit), the CAS + reflog + `refs_version` + `GcMark` terminal span is right, tree ordering (`name/` for directories) and header byte-copy are right, and the wire additions are honestly declared. Deductions: `r.pack_id` reads a column the DDL never creates so resume re-keys the upload (deviation 1); `commit_rebase` omits section 3 step 2 — nothing re-checks `onto` is still live at CAS time, so a mid-rebase sweep can produce a live pack violating 2.5 (deviation 2); `ObjRow::new` records no `idx` (deviation 3); `author` is stored but never read (deviation 5); the commit-level driver `replay_one` and `merge_base`/`rev_list`/`checkpoint`/`conflict`/`fail` are referenced but never shown.
- Effort: weeks. The engine shown is days on top of the foundation; the blob-merge driver is correctly deferred to `server-side-merge`, which has no v2 proof yet.

## Contract compliance
Matches: A9 REGISTRY block present and complete (routes `/_do/rebase`, `/_do/rebase-status` — awaits allowed per the `/_do/fetch` precedent; `JobKind::Rebase`; `rebase_jobs` table; `V2Command` variants; rule-6 advertisement lines); no loose objects (2.1); output is one normalized pack under `r/<repo>/packs/` (2.2) with `packs.push_id` NULL per the gc_consolidate precedent (2.3); `objects` rows posted in <=10,000 batches (1.2, line 148); ordering finish -> index -> terminal span holds (lines 151-154, section 3); `changes()` is the only oracle, `rows_written` never read (platform-facts #1); A3 followed — `enqueue` is sync, `rearm(self).await` follows each span (lines 96-97, 106-107), no `set_alarm` in the module (4.1, measured #5); `spent_80pct` between commits (A4); `Err` -> 4.4 retry/backoff/dead-after-8 and dedup ignores `dead` so a later request revives the kind; parse-before-storage in `rebase_begin` (section 3, lines 81-95); body <= 1 MiB via `parse_v2_command` (6.3); `Protocol` -> 400 before response bytes (10, spike correction 4); DO-side `Limit`/`Storage`/`Internal` propagate as `Err` (A2); edge `can_write` gate before the stub call (12); `PktWriter` only, flush-terminated, `response-end` never written (1.1 rules 1, 3); coalesced `read_entries`/commit-region reads (7.2, 7.4) with `budget.req` passed per A1; <=9 bound parameters per statement (A6); <=2 added scenarios with the stock-`git` substitution stated (11); Janitor write-backs (fail stale `running` rows, kill `ingesting` rebase packs, delete `ended_at < cutoff` rows) are declared, not smuggled — unlike the sibling's silent `pushes` delete.
Deviations (each also in the structured list):
1. `rebase_jobs` DDL (REGISTRY, lines 31-34) has no `pack_id` column and the `INSERT` (lines 91-95) never writes one, yet `Row` selects `pack_id` (line 55) and `step` reads `r.pack_id` (line 137). `Option<String>` deserializes `None`, so every slice after the first mints a fresh `PackId` while `cursor.upload` resumes the first upload's id — `resume_multipart_upload` is then called on a key that does not own that upload. Line 90's "job id == pack id" says `r.id` was intended. As written, every rebase longer than one slice — the `pending` path the job machine exists for — fails or writes a packs-row-less key on resume. Mechanical.
2. `commit_rebase` (lines 207-227) mirrors section 3's span minus step 2: `rebase_begin` snapshots no `gc_epoch` and the terminal span never re-checks that `onto` resolves through the `state='live'` query. The proof's own claim is "section 3 ordering, mirrored" (line 7). If the ref that named `onto` moves and a full GC cycle (`GC_QUIET` 10 min + GRACE-aged candidates + slices) sweeps its pack mid-replay, the output pack goes `live` referencing dead objects — a 2.5 violation that `git fsck` on the next clone exposes. Mechanical: one 2.3-query on `onto` inside the span covers it, since `base`/`theirs`-side ids are already pinned by the `expect` CAS on `branch`.
3. `ObjRow::new(id, offset, len, kind, size)` (lines 186, 200) exists in no sibling and no contract section; all four object-writing siblings use `ObjRow { sha, idx, offset, len, kind, size }` literals (streaming-pack-parser 177, content-addressed-r2-keys 173, presigned-direct-upload 193, tui-rpc-push 137). `idx` — the in-pack ordinal 2.3 requires and `GcMark`'s per-`idx` bitmaps (5.1) consume — is never recorded. Undeclared API plus a missing schema field; mechanical (struct literal + ordinal counter).
4. `gix_object::compute_hash(Kind::Tree, &data)` / `(Kind::Commit, &body)` (lines 184, 198) drops the leading hash-kind argument. The real 0.64.1 signature and every other sibling's call is `compute_hash(gix_hash::Kind::Sha1, kind, data)` (content-addressed-r2-keys line 14, wasm-git-core 106/248/263, streaming-pack-parser 174, tui-rpc-push 155/166/214); alarm-chain-ci line 120 has the same 2-arg drift, so the canonical form should be written back to the contract. Mechanical.
5. `RebaseArgs.author` / `rebase_jobs.author` are parsed and stored (lines 36, 94) but `write_commit` (lines 194-197) byte-copies the source `author ` line unconditionally — the squash override the Changes table claims (line 248) is never applied.
6. `command=rebase-status` has a DO route but no edge arm; the Changes table (line 244) describes a `status <state>` + delim'd detail response (`tip`, `path`, `error`) that no shown code emits. The `rebase` edge arm (lines 66-75) is the template; the status framer is missing, not wrong.
7. `SliceBudget.req` is assumed (lines 140-141, 150-151) — a write-back the siblings (bundle-uri line 222, precomputed-clone-pack line 218) declare and this proof relies on without listing; `SliceBudget::fresh()` is listed (line 259). Consistent across proofs, but the field exists only if those write-backs land. Not a conflict; a dependency.

## Crash walk-through
Kill in `rebase_begin` before the `INSERT` span commits: nothing durable; the client gets 5xx and retries — clean. Kill mid-`step` at an R2 await: the uncommitted span rolls back (measured #4 semantics); durable state is the `running` row, the last `checkpoint` cursor (`upload`, `parts`, `pos`, `pending`), the `ingesting` packs row and posted `objects` batches — all invisible to the 2.3 query — plus uploaded MPU parts in R2. Resume regenerates byte-identical entries (committer `created_at`, byte-copied author) and re-uploads the same part numbers; safe only if part-overwrite-before-`complete` holds on real R2 (simulator only, #6) — and only once deviation 1 is fixed, since today the resumed slice re-keys the upload. Kill in the window `finish()` returned -> terminal span not yet committed: the MPU is *completed*, but the cursor still names the old upload id; resume calls `resume_multipart_upload` on a completed id, which fails under S3 semantics, so every 4.4 retry fails — `dead` after 8 attempts (about 3 h of backoff), the row stays `running` until the Janitor write-back fails it at `created_at + PUSH_TIMEOUT` (1 h), and the finished pack sits `ingesting` until the same pass kills it. No corruption — the ref never moved — but a client-visible `failed` where a head-check on the key in the resume path would have recovered. Kill inside `commit_rebase`: all-or-nothing; the rolled-back case is the window above, the committed case is fully consistent (pack `live`, ref moved, reflog + `refs_version` + `GcMark` in the same span — armed indirectly when the queued `Rebase` job row fires and `dispatch` re-arms, 4.2). Orphan accounting: `dead` pack keys go to Janitor 5.3 after GRACE; never-completed MPU parts need the bucket abort-incomplete-multipart lifecycle rule, same gap as pushes, not in the memo.

## Concurrency walk-through
Two `rebase` calls, same `branch`+`expect`: both advisory checks pass (lines 85-89), both insert rows; slices serialize, first `commit_rebase` wins the CAS, the loser gets `changes()==0` -> `stale` and its pack goes `dead` (lines 221-225). Correct, the loser's replay is wasted work — same as first pass, now with bounded cleanup. `git push` mid-replay: push `commit_push` and `commit_rebase` are both single sync spans; the platform serializes them (measured #4), exactly one CAS wins, matching scenario 6's two-push outcome — and the added scenario (b) exercises this. Every mid-run mutation (`rebase_jobs`, `objects` rows on an `ingesting` pack) is invisible to readers and to `commit_push`; R2 awaits inside `step` open the input gate so pushes interleave rather than queue behind the slice — the first-pass caveat is now load-bearing and safe. `GcSweep` mid-rebase: the `ingesting` pack is not a candidate (not `live`, and candidates need `created_at < started_at - GRACE`); if the rebase lands first, its `refs_version` bump aborts the sweep's span check (5.3). The one open lane is deviation 2: a sweep of the pack holding `onto` can complete while a long rebase still references its trees. Polls: `rebase-status` on a `running` row re-`enqueue`s (deduped) and re-arms — an idempotent nudge, exactly the resume mechanism the first pass lacked; on a terminal row it is read-only plus a harmless `rearm`.

## Interop check
A stock `git` sees two extra v2 capability lines (`rebase`, `rebase-status`) and provably ignores them — verified in the first-pass review against git 2.4x `ls-remote`/`fetch`, and no stock client can emit `command=rebase` because command names are compiled into `remote-curl`. Byte-level: `ack <oid>\n`, `conflict\n` + `0001` + `path <p>\n` lines, `pending\n` + `0001` + `job <id>\n`, then flush — legal pkt-line framing (`w.text` bounds each line at `MAX_PKT_DATA` 65,516; a pathological conflict path over it errors before the response is sent), `application/x-git-upload-pack-result` content-type, no `response-end` (rule 3). The replayed commits are real objects: `tree`/`parent`/`author`/`committer` headers and message in canonical order, committer `principal <rebase@git-edge> <unix> +0000` — well-formed provided the principal name contains no `\n`/`>` (never sanitized; caveat). A subsequent stock `git fetch` serves the pack through the one 2.3 query once `live`, and `fsck` on the clone is clean — modulo deviation 2's swept-base window. Squash is `mergeTrees(base, onto, tip)`, one commit; merge commits in `base..branch` are dropped per `git rebase` defaults; no interactive modes. Scenarios 1, 2, 12 plus the two added harness scenarios are the right set, and the hand-framed POST substitution is properly declared since no stock client can drive this.

## Blockers
- Deviation 1: `Row.pack_id`/`step` read a `pack_id` the `rebase_jobs` schema never creates and nothing writes; every resumed slice re-keys the multipart upload. Use `r.id` (the line-90 comment already says job id == pack id) or add the column. Mechanical, but it disables the entire multi-slice path as written.
- Deviation 2: no `gc_epoch`/`onto`-liveness guard in the terminal span; a mid-rebase sweep of `onto`'s pack yields a `live` pack referencing dead objects (2.5). One live-query on `onto` inside `commit_rebase` closes it.
- Deviation 3: `ObjRow::new` is invented and drops `idx` (2.3 ordinal, consumed by `GcMark` bitmaps 5.1); use the sibling struct literal with an ordinal counter.
- Deviation 4: `compute_hash` is called 2-arg where the pinned API and all other siblings use `compute_hash(H::Sha1, kind, data)`. Mechanical; the same drift exists in alarm-chain-ci, so write the canonical signature into the contract.

## Caveats
- Post-`finish`-pre-commit crash is a liveness dead end: resume re-arms a completed MPU and fails permanently; the row burns 4.4 retries (~3 h) then sits `running` until the Janitor write-back at `PUSH_TIMEOUT`. An `R2 head` on the key in the resume path would recover in one slice.
- A permanently-erroring oldest `running` row head-of-line blocks later rebase rows (`ORDER BY created_at LIMIT 1` + `step(...)?`) for up to `PUSH_TIMEOUT`; skip-on-`Err` or a per-row attempt counter would fix it.
- `merge_base`/`rev_list`/`replay_one`/`checkpoint`/`conflict`/`fail`/`union`/`sort_name`/`header_line`/`commit_message`/`insert_pack_row` are referenced but never shown — the commit-level merge driver (`replay_one`, where `merge_trees`'s `need`-prefetch rounds actually live) is the entire missing body. Also: `MEM_MAX` is declared but no check is visible, and a `need`-driven `merge_trees` re-run leaves the abandoned partial trees as extra pack entries (legal per 2.5, and `objects` dedups by `(sha, pack_id)`, but uncounted pack bloat).
- `author`/`message` columns and the `author` argument are stored but never read by `write_commit` (deviation 5); `command=rebase-status`'s edge framer is absent (deviation 6).
- `r.principal` is interpolated into the committer header unsanitized — a name containing `\n`/`>` mints a malformed (or header-injected) commit object. Operator-chosen token names make this low-risk; one validation line closes it.
- `rebase-status` on an unknown/expired job id hits `.one::<StateRow>()` -> `Err` -> 500 rather than a clean `unknown`/`failed` answer.
- Two entries in "Depends on" (`gc-and-repack-alarm`, `server-side-merge`) have no v2 sibling proof; `PackWriter::resume` is therefore only a write-back, and the blob-merge upgrade path is unproven beyond the memo's 926-line count.
- Unverified per memo/contract and honestly flagged: `Request::new_with_init` JSON stub path, part-overwrite-before-`complete` on real R2 (#6, simulator only), `TreeRefIter`/`CommitRefIter` field names (compile-pinned), `web_sys::Crypto` for `PackId::random` (8.2), DO subrequest enforcement (#7).
- reflog `push_id` carries a `rebase:<job>` pseudo-id — the only audit trail, since a rebase writes no `pushes` row.

## Verdict
lands-with-caveats. All four first-pass blockers are closed — squash is a real merge branch, the status command and the drain-the-table dispatcher exist, and storage moved to normalized packs — and the deterministic-regeneration design removes the orphan class by construction rather than by a check. What remains is local and mechanical: the `pack_id` schema mismatch that disables resume as written, the missing `onto` liveness re-check in the terminal span (the one narrow 2.5 hole), and two signature reconciliations (`ObjRow::new`/`idx`, `compute_hash` arity) plus the never-wired `author` override and missing status framer.

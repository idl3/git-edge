# Review v2: content-addressed-r2-keys

## Scores
- Feasibility: 5/5 (was 4). Every API in the block checked against pinned source, not the memo: `Bucket::create_multipart_upload(impl Into<String>) -> CreateMultipartUploadOptionsBuilder` with `.custom_metadata(impl Into<HashMap<String,String>>)` and `execute() -> Result<MultipartUpload>` (`r2/builder.rs:297-303`); `MultipartUpload::{upload_part(u16, impl Into<Data>), complete(impl IntoIterator<Item=UploadedPart>) -> Object, abort(&self)}`; `Object::size() -> u64`; `From<Vec<u8>> for Data`; `SqlStorage::exec(&str, impl Into<Option<Vec<SqlStorageValue>>>)` with `Null` and `From<String/&str/i64>`; `gix_hash::hasher(Kind)`, `Hasher::{update, try_finalize -> Result<ObjectId>}`; `gix_object::compute_hash -> Result<ObjectId, hasher::Error>`; `Entry::from_bytes(&[u8], Offset, gix_hash::Kind)`, `Entry::{header_size(), decompressed_size}`, `Header::{write_to(u64, &mut dyn Write) -> io::Result<usize>, as_kind()}`, `header::encode(Version, u32) -> [u8;12]`; `gix_zlib::{Inflate: Default, Inflate::once -> (Status, in, out), Compression::DEFAULT = 6, stream::deflate::Write::new(W, Compression)}`. The first pass's Web-Crypto and per-object-put limits are gone with the design. Unmeasured, not unknown: deflate on wasm32, real-R2 multipart (#6).
- Reliability: 4/5 (was 4). Idempotence now rests on fresh `pack_id` per attempt plus `DO NOTHING` rows plus the section 3 CAS, all shown. Residual: incomplete multipart uploads after an isolate kill are never aborted and the proof's "Janitor 5.3 is the backstop" is wrong (5.3 deletes keys; an incomplete MPU is not a key and the upload id is stored nowhere).
- Correctness: 3/5 (was 4). The pack bytes and hashes are right and git-compatible (below), but `Index::insert_pack` as written cannot record the final pack metadata under the contract's own 2.4 sequencing, and the proof's signatures contradict two sibling proofs it depends on.
- Effort: days for this slice; weeks to "working" (ingest, wire, jobs around it). Genuinely better than the first pass on feasibility (memo claims -> source-verified) and it removes the 5,000-object cap and the GC/HEAD race by construction; it loses a point on correctness for the index defect.

## Contract compliance
- Key layout: `keys::pack` output is the only key; `pack_id` re-derived from it by `rsplit('/')`/`strip_suffix` (fragile but pure). `customMetadata` fields exactly `{repo, pack, count, created_at}` (2.2). Pass.
- Schemas: `packs` and `objects` column lists verbatim from 2.3; `PRIMARY KEY (sha, pack_id)` honoured by `ON CONFLICT(sha,pack_id)`. Pass.
- `changes()`/`rows_written`: neither used, none needed (no decision taken on an insert outcome). No await in any `Index` method; `insert_*` are `fn`. No `set_alarm`, no alarm. Pass.
- Signatures vs 1.2 (declared write-backs): `create(bucket, key, expected, budget)` vs `create(bucket, key)`; `flush_if_full/finish(&mut ReqBudget)`; `encode_entry -> Result`; `append_entry -> Result<(u64,u32)>`; field `pack` replaces `key`; `finish` no longer "patches header count". Violation. Worse, `proofs-v2/two-phase-push.md:61` calls `PackWriter::create(bucket, key, budget)` (no `expected`) and `streaming-pack-parser.md:172` does `let (offset, len) = out.append_entry(kind, &data);` (no `?`): the three proofs do not compile against each other.
- 2.4 says the `packs` row is inserted `ingesting` on the first `/_do/push/index` post, i.e. before `finish` knows `count/bytes/commit_lo/hi`; two-phase-push therefore posts `PackMeta::EMPTY` first and upserts. This proof's `insert_pack` is `ON CONFLICT(id) DO NOTHING`, so the post-`finish` metadata is silently dropped, and its change-table claim "Rows are inserted only after `finish` returned" contradicts 2.4. Violation.
- `commit_lo` "none" is stored as `i64::MAX` (SQLite INTEGER), contract says u64 max. Necessary; needs write-back. `insert_objects` >10,000 rows returns `Error::Protocol` (400) for an edge-side invariant; section 10 says `Internal`. Minor.
- Error policy otherwise correct: delta header in a normalized pack -> `Internal`; corrupt R2 bytes -> `Storage`; oversize -> `Limit`/`Unpack`; no `unwrap`/indexing/`as` on client bytes in `codec`/`record` (the two `as` casts are on host numbers outside the lint list). Pass.

## First-pass blockers
The first pass listed none ("None for the idea as scoped"). Its seven caveats, checked against code: (1) pending-prefix conflict: resolved at contract level (different bytes, 2.2), nothing to show. (2) HEAD-skip/GC race: resolved; no R2 read anywhere in the write path ("nothing in this code consults R2 to decide whether to write"), the guard is `commit_push` step 2/tip lookup in the sibling. Genuine. (3) 2 subrequests/object: resolved by `flush_if_full` (one `upload_part` per 8 MiB) and `insert_objects` batches; `budget.charge(1)` precedes `create`, every `upload`, `complete`. Genuine. (4) No incremental SHA-1: resolved by `self.hasher.update(entry)` in `append_entry` and `try_finalize` in `finish`. Genuine. (5) Uncompressed at rest: resolved by `deflate::Write::new(out, Compression::DEFAULT)` in `encode_entry`; `flush()` is `FlushCompress::Finish` (`deflate.rs:223`), so each entry is a complete zlib stream. Genuine; wasm deflate unmeasured. (6) sha256: `HashKind::Sha1` fixed; rejection lives in `wire`, not shown, contract-mandated. Claimed, acceptable. (7) Circular dependency: `pack -> store` only. Genuine.

## Crash walk-through
Push of 30,000 objects. Edge dies after `complete` returned and two of three index posts landed, before the final post and commit. State: `packs/<p>.pack` durable (size-checked), `packs` row `ingesting` (created by the first post per 2.4), 20,000 rows, push `open`, refs untouched; `lookup` cannot resolve any of them (`p.state='live'`). Client retries with new `push_id`/`pack_id`: full re-ingest, second pack, `DO NOTHING` rows, CAS moves the ref once. Janitor after PUSH_TIMEOUT expires the first push, kills its pack and rows in one span, deletes the key after GRACE. Converges, cost only. Variant, death between `create` and `complete`: no object exists, `packs` row says `ingesting` forever until expired, but the R2 multipart upload is orphaned; nothing stores `upload_id`, so neither `abort` nor 5.3 can reach it. Lifecycle rule for incomplete uploads is unverified (two-phase-push says the same).

## Concurrency walk-through
A and B push overlapping histories concurrently. Distinct `pack_id`s, so no R2 key is shared; both `complete`. Both `/_do/push/index` routes are sync spans; `objects` rows for the same sha land under two `pack_id`s (legal, 2.3, `LIMIT 1` reader). Commit spans serialize; one `changes()=1`, the other `ng ... failed to update ref`; the loser's pack is live but unreferenced until `gc_consolidate`. Retried index post after a stub timeout: `DO NOTHING` on `(sha,pack_id)`, no-op. Retried `upload_part(n)`: replaces part n with identical bytes (S3 rule, unmeasured on R2), and `finish` checks `Object::size()` against the hashed byte count. No interleaving produces a live ref into a non-live pack.

## Interop check
The one place a wire byte could break is the zlib body of each stored entry, since fetch copies entries verbatim. `deflate::Write::flush` = `Finish`, so the adler32 trailer is present and `git index-pack` reaches `Z_STREAM_END`; header `78 9c` at level 6 is git's default. `Header::write_to` emits git's varint type/size byte layout; `header::encode(V2, n)` = `PACK\0\0\0\2` + count; trailer is SHA-1 over all bytes via `gix_hash::Hasher`. `decode_entry`'s `StreamEnd && n == out.len()` is byte-for-byte gix-pack's own corruption check (`decode/entry.rs:146`). Nothing else touches the wire. No breaking byte found for git 2.43-2.47 over v2.

## Blockers
- `Index::insert_pack` must be an upsert guarded by `state='ingesting' AND push_id=excluded.push_id` (or a separate `set_pack_meta`), otherwise `count/bytes/commit_lo/commit_hi` are never recorded under 2.4's first-post rule; section 7.4 commit-region reads and gc_consolidate then run on zeros.
- Signature write-backs to 1.2 conflict with two-phase-push and streaming-pack-parser (`create` arity, `append_entry` return type). Pick one and amend both siblings.
- Compile error: `finish` uses `self.count`/`self.expected` after `self.abort().await` moved `self` (E0382). Trivial, but the proof was not compiled.

## Caveats
- Store the multipart `upload_id` on the `packs` row so the Janitor can `abort` incomplete uploads of expired pushes; the R2 lifecycle rule is unverified.
- `Compress::new` allocates a full deflate state per entry ("should be done with care"); keep one `deflate::Write` and call `reset()` per object, or a 1,000,000-object push pays 1,000,000 allocations.
- `insert_objects` issues one `exec` per row (10,000 per span); a multi-row `INSERT ... VALUES (...),(...)` cuts it.
- Day-1 unverified: deflate on wasm32; 8 MiB equal parts and single sub-5 MiB part on real R2; same-number `upload_part` replacement; scenario 17 (duplicate object in a pack) on git 2.47.

## Verdict
lands-with-caveats. The mechanism is now the contract's pack model and every primitive it uses exists in the pinned crates; the first pass's five structural caveats are closed by shown code. Three small blockers (an upsert, a signature reconciliation, a moved-value fix) stand between it and compiling; none is a redesign.

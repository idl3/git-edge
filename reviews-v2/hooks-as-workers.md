# Second-pass review: Pre/post-receive hooks as Workers via service bindings

# Review v2: hooks-as-workers (idea #23)

## Scores
- Feasibility 4/5 (was 4). Every host call exists in `worker` 0.8.5 docs.rs: `Env::service(&str) -> Result<Fetcher>`, `Env::dynamic_dispatcher(&str) -> Result<DynamicDispatcher>`, `Fetcher::{fetch, fetch_request}`, `Fetch::{Request, Url}::send`, `Headers::set`, `Request::new_with_init` + `RequestInit::{with_method, with_headers, with_body}`, `worker::Delay`. `RequestInit` genuinely has no `signal` field, so the hook timeout is a `Delay` race that abandons rather than cancels; `send_with_signal` exists only on `Fetch`. Docked for: every `service:`/`dispatch:` call from inside a DO alarm context is unverified, dispatch namespaces are a Workers-for-Platforms paid add-on, and `fetch_request`'s `HttpResponse` is `worker::Response` only without the `http` feature (deviation 8).
- Reliability 4/5 (was 2). The first-pass alarm collision is gone structurally — the module contains no `set_alarm`; post-receive is a `jobs` row plus `hook_outbox` written inside the commit span, atomic with the ref flip (4.1, A3). The dedup race is closed by the commit-span `UPDATE jobs SET run_at` and the drain's re-SELECT per unit. Residual: a mid-slice isolate kill strands the `PostReceive` row in `running`, which dedup counts — section 4.2 has no running-timeout, so the kind wedges until manual repair; the same hole exists for `Janitor`/`GcMark`, so this is an inherited contract gap, not a new one. The timeout does not cancel the losing arm.
- Correctness 4/5 (was 3). Byte-exact hook stdin (`<old> <new> <ref>\n`), git's all-or-nothing decline mapped to `unpack ok` + `ng` + band-2 `remote:` lines, a real quarantine read path (`x-ge-push` + `lookup_or_pack` widening the 2.3 query), and post-receive covering accepted commands only — all inside the commit span, as git does. Dents: the HMAC the mechanism promises is never invoked (deviation 4); `pushes.result` is written as a bare string, not the per-ref array (deviation 2); and post-receive's `x-ge-push` is dead-on-arrival, so a post hook cannot read the repo it was notified about without `GE_READ_TOKEN`.
- Effort: weeks. The module code is days; the quarantine read path through `/_do/fetch`, the `wire` write-backs, the WfP namespace (or unsigned-webhook fallback), and the harness sink are the rest.

## Contract compliance
Matches: A9 REGISTRY block (tables `hooks`/`hook_outbox`, `JobKind::PostReceive`, routes `/_do/hooks/set` + `/_do/push/reject`, header `x-ge-push`, edge `PUT /<owner>/<repo>/hooks`, module `src/hooks.rs`); section 3 ordering preserved by running the gate in the edge between `ingest::run` and `/_do/push/commit`, so `commit_push` keeps "Awaits inside: none" (1.3); decline -> `/_do/push/reject` -> `pushes.state='rejected'` -> Janitor 5.2 kills the `ingesting` pack and 5.3 deletes both keys after GRACE — the cleanup path exists verbatim; no `set_alarm` in the module (4.1); backoff is the 4.4 formula `min(30 s * 2^attempts, 1 h)` capped at 12 (~5 h) with dead-letter retained GRACE; `JobKind` registration per 4.5; `x-ge-depth > 1` refused `Forbidden` before the body is parsed (section 10 pre-header mapping -> 403); `budget.charge(1)` on every hook subrequest exceeds 7.1 (they are neither `Bucket` nor stub calls); DTOs in `wire::http` (A8); hook stdin bounded by the 1 MiB command cap (6.3) to ~1.2 MB.
Deviations (each also in the structured list):
1. `d.q(...)`, `d.meta_str(...)`, `to_array::<N>()`/`IdRow` are called from `src/jobs/post_receive.rs` (lines 189-196, 204), but the siblings declare `fn q`, `fn meta` (named `meta`, not `meta_str`) and private `struct N`/`IdRow` (repo-do-ref-authority lines 36, 76-84; two-phase-push line 149). The write-back list names only `RepoDo.env` `pub(crate)`; `q`/`meta`/`N`/`IdRow` need the same treatment. Mechanical visibility + rename drift.
2. `push_reject` writes `pushes.result` as `serde_json::to_string(&b.reason)` — a bare JSON string (lines 147-148); every other writer stores the per-ref `[(name, Option<reason>)]` array (`finish_push`, repo-do-ref-authority lines 157-158). A5's "a rejected push writes `pushes.result`" is met, but the shape drifts from its own schema; anything auditing `result` must handle two formats.
3. Literal: the mechanism claims `unpack error pre-receive hook unreachable` (line 9); section 10's after-header rule is `unpack <message>`, and the `Error::Storage` message yields `unpack pre-receive hook unreachable`. Same class as two-phase-push deviation 8; not wire-breaking.
4. HMAC is claimed and absent: line 9 says an `https://` target is "HMAC-signed when `hooks.secret` is set" and `platform::hmac_sha256` is listed as a primitive, but `hooks::call` (lines 75-99) takes no secret parameter, `run_post_receive` selects `h.target` without `h.secret` (line 194), and nothing signs the body. The column is stored and never read. The fix is small (join the column, sign, add a header); as written the mechanism overclaims.
5. `UPDATE jobs SET run_at=? WHERE kind='PostReceive' AND state='queued' AND run_at>?` (line 169): the module writes the dispatcher's own table to pull a backoff-parked job forward. It works and it is inside the commit span, but it is not one of section 4's interfaces (`enqueue`) and it is not listed in the REGISTRY block.
6. The claimed "route's post-span `jobs::rearm` (A3, already needed for step 7's GcMark)" (line 13) does not exist in the sibling: `repo-do-ref-authority`'s `fetch` ends at `crate::edge::respond(out)` (lines 45-60) and never re-arms after `/_do/push/commit`, which enqueues `GcMark` in the same span. A3 requires it. Until added, `PostReceive` and `GcMark` rows wait for the next armed alarm (<= the Janitor's 15-min cadence if its row is armed) or the next DO event — the proof's own boot-rearm write-back covers it on the next request. One line; it belongs in this proof's write-back list or the sibling's code.
7. `with_body(Some(stdin.into()))` (line 84): `Vec<u8>` has no `Into<JsValue>`; a byte body needs `js_sys::Uint8Array::from(&stdin[..]).into()`. Mechanical.
8. `call` and `run_post_receive` consume `fetch_request`'s `HttpResponse` with `.status_code()`/`.text()` (lines 87, 94-95) — that alias is `worker::Response` only when the `http` feature is off; with it the return is `http::Response<worker::Body>` and neither method exists. The crate-wide feature flag is decided elsewhere ("`http` only for the stateless Worker", memo section 4); this needs an adapter or a stated assumption.

## First-pass blockers
1. Single-alarm collision with two-phase-push's janitor: **resolved**. The module holds no `set_alarm` (CI grep, 4.1); delivery is `jobs::enqueue(PostReceive)` inside the commit span plus the post-span `rearm` (A3), and `rearm`'s `MIN(run_at)` covers janitor, gc and `PostReceive` rows on the one measured alarm (platform-facts #5). Caveat: the resolution leans on the commit-route rearm that the sibling does not show — deviation 6.
2. `\n` in the rejection reason corrupting report-status: **resolved** by construction. The `ng` reason is the `&'static str` `pre-receive hook declined` — `RefResult::Ng` makes hook text in the pkt stream unrepresentable — and the hook body travels as band-2 `remote:` lines, 200 lines x 200 chars each under `MAX_BAND_DATA` (rules 2 and 4; write-back `write_report_status_remote`).
3. Upload-pack serving not-yet-committed objects under a `pushId` token undesigned: **resolved**. `x-ge-push` is the unguessable `PushId`; `/_do/fetch` validates `pushes.state='open'` in one sync span and `Index::lookup_or_pack` widens the 2.3 reader query to the push's `ingesting` pack (`GIT_QUARANTINE_PATH` equivalent); the token dies at commit, reject, or `PUSH_TIMEOUT`.
Caveats from the first pass: "register a Worker" needs WfP -> **partially resolved** — restated honestly (`service:` deploy-time, `dispatch:` verified-but-paid, `https:` the only dynamic target), and the `https:` path's HMAC is claimed but unimplemented (deviation 4). Commands in a 16 KB-capped header -> **resolved** — commands ride in the body, which is git's stdin anyway. ~8.5 min retry then drop -> **resolved** — the 4.4 formula over 12 attempts (~5 h) then `dead` retained GRACE. Missing `update`/push-options/quarantine-env -> **partially resolved** — quarantine is real (blocker 3); push-options are provably impossible (`push-options` not advertised, rule 5); `update`/`post-update`/`proc-receive` remain unmodelled, stated. Crash case A (isolate dies before `setAlarm`) -> **resolved** — `enqueue` is inside the span; only `rearm` is post-span, and the boot-rearm write-back closes the window. Crash case C (janitor alarm silently cancelled) -> **resolved** — same root as blocker 1. `hooks` table read at two times -> **resolved** — documented begin-snapshot vs as-of-commit semantics, matching git. `x-git-edge-depth` asserted, never enforced -> **resolved** — `receive_pack` refuses `x-ge-depth > 1` with 403 before any body byte; advisory, stated. Sideband wrapping / `report-status-v2` option lines -> **resolved by dependency** — framing is `wire`'s (rule 4); v2 without option lines is allowed by section 12. Non-fast-forward checks costing R2 reads per commit -> **resolved** — moved into the hook Worker as one `fetch --filter=blob:none`, bounded by section 9's fetch cap and off the push path.

## Crash walk-through
Edge killed during the pre-receive await, or after a decline but before `/_do/push/reject`: the `pushes` row stays `open`, the pack stays `ingesting`; Janitor 5.1 expires it at `began_at + PUSH_TIMEOUT` (1 h), 5.2 marks the pack `dead` next slice, 5.3 deletes `pending/<push>` and `packs/<pack>` after GRACE — about 2 h of retained garbage, identical to two-phase-push's ingest crash. The hook may already have run; a declined push can still have fired hook side effects, which git shares. DO killed inside `push_reject` or `commit_push`: the span has no awaits, so uncommitted writes are discarded wholesale (throw-rollback per memo section 1; `PanicError` rollback unverified — scenario 15) — an outbox row without the ref flip, or vice versa, is impossible by construction. Isolate killed between the commit span and the post-span `rearm`: outbox rows and the `PostReceive` job row are durable, the alarm is unarmed; the next armed alarm (worst case the Janitor's <= 15-min cadence) or the next DO event (boot-rearm write-back) fires the drain — delayed, never lost, assuming deviation 6 is fixed. Isolate killed mid-`run_post_receive` during a hook await: the job row stays `running`; section 4.2 applies the outcome only after the slice returns and nothing times a stale `running` row out, while `enqueue` dedups on queued-or-running — so no later commit can replace it and the kind is wedged for the repo until manual repair. Janitor and `GcMark` share the hole; it is a section-4 defect this module inherits. A kill after the hook returned but before the row `DELETE` redelivers an identical payload — at-least-once as claimed, dedupe key `x-ge-push` + `hook` in the payload. `hooks_set` killed mid-span is old-set-or-new-set; replace-all is one sync span.

## Concurrency walk-through
Pushes A and B both in the gate: each holds only an `open` pushes row — no lock is taken — so both hooks may approve against the same advertised `old`; the commits serialize and the loser's `changes()=0` yields `ng <ref> failed to update ref`, git's ref-lock race with the gate correctly outside the lock. A commit during a running `PostReceive` drain: `enqueue` dedups (`running` counts), the drain's loop re-SELECTs after every hook await and the new row's `next_at` is the committing span's `now` — due — so the same job delivers it; a commit inside the drain's tail span cannot interleave (no awaits); a commit after it finds the job consumed and enqueues fresh. The bridge between `run_slice` returning and `dispatch` applying the outcome — "a ready future's `.await` does not yield" (lines 217-218, 232) — is plausible microtask semantics but unmeasured; the safe shape is one more SELECT inside the outcome span. `hooks_set` mid-push: pre-receive reads the begin snapshot, post-receive reads as-of-commit; `hooks.id` is `AUTOINCREMENT`, so a replaced set can never alias an outbox `hook_id` — the LEFT JOIN yields NULL and the row is dropped, which is the right semantic. An `x-ge-push` fetch racing the commit: `push_scope` validates and resolves in one span; a validated fetch keeps working after commit because the pack is now `live` and the OR clause still resolves it; a fetch arriving after reject or expire gets `Forbidden`. Note the token widens auth: any write-capable principal mints a `push_id` at `push_begin` that reads all live objects for the open window — a write->read widening of section 12's two-token model, registered under A9 but worth stating.

## Interop check
Real git 2.4x on the decline path sees HTTP 200, `unpack ok`, `ng <ref> pre-receive hook declined` — `! [remote rejected] main -> main (pre-receive hook declined)` — plus the hook's body as `remote:` lines on band 2 under `side-band-64k`, dropped without it: byte-parity with git's hook-stderr behaviour. The unreachable path lands `unpack <msg>` + `ng ... unpack failed` (deviation 3's literal). Hook stdin is byte-exact; zero oids arrive as the 40-zero strings `CmdDto` already carries. The hook Worker sees a POST with `text/plain` body and ~200 B of `x-ge-*` headers, far under the 16 KB cap. Two honesty checks survive contact: a hook Worker cannot spawn `git`, so "the hook runs a real `git fetch`" (line 234) means a Wasm/JS v2 client that does not exist yet — the server side is real, the client is bring-your-own; and an `https://` target receives a live `x-ge-push` bearer over public TLS, unsigned (deviation 4). Added scenarios A and B fit the two-scenario budget (section 11); A's `pushes.state='rejected'` and dead-pack assertions match 5.2, and B's backoff/identical-payload assertions match the 4.4 schedule.

## Blockers
- None. Every remaining defect is mechanical (deviations 1-3, 5-8), an inherited contract gap (the `running`-job wedge), or a documented platform limit (WfP paywall, uncancelled timeout).

## Caveats
- `hooks::call`'s `Declined` arm does `r.text().await` outside the `Delay` race (lines 94-96): the 10 s cap covers the status code only; the body is then read unbounded in both time and size — a slow or huge hook response stalls the gate and buffers into the 128 MB isolate.
- 32 sequential hooks at up to 10 s each sum past `ReqBudget.max_ms` 240 s (7.1): the tail hooks are never consulted and the push reports a `Budget` decline; worst case is unstated.
- Post-receive's `x-ge-push` is dead-on-arrival (token dies at commit): a post hook that wants the objects needs `GE_READ_TOKEN` — the canonical CI-shaped hook has no read access unless the operator hands it the platform credential. Pre-receive gets repo-read; post-receive gets nothing.
- A malformed `payload` JSON in `hook_outbox` errors the whole slice (line 203); the same row is re-SELECTed every slice (`ORDER BY id LIMIT 1`), retrying the job to `dead` while every later outbox row waits behind it. Dead-letter the row instead.
- `Depends on: gc-and-repack-alarm` names a slug with no `proofs-v2/` file; the machinery relied on (`jobs::dispatch`, `MIN(run_at)`, `gc_epoch`) is contract sections 4/5 via two-phase-push and repo-do-ref-authority.
- `hooks_set` bounds count (32) but not `target`/`secret` length; only the stub body size applies.
- Unverified, day-1 list stands: `env.service`/`dynamic_dispatcher().get()` from a DO alarm context, `Request::new_with_init` at runtime, `worker::Delay` in a DO, `platform::hmac_sha256` (currently uncalled), DO subrequest cap on a deployed Worker (platform-facts #7). Contract-internal nit: `rearm` is `rearm(sql, storage)` in 4.1 but `jobs::rearm(&self).await` in A3 — pick one.

## Verdict
lands-with-caveats. All three first-pass blockers are closed structurally rather than by a check: the alarm collision cannot recur because there is no second `set_alarm` in the design, hook text cannot corrupt report-status because `RefResult::Ng` is `&'static str`, and the quarantine read path is real and token-scoped. Reliability 2->4, correctness 3->4. What remains is mechanical or inherited: the HMAC the mechanism advertises is never invoked, the commit route's post-span `rearm` is asserted but absent from the sibling, a handful of rename/visibility/literal drifts, and a section-4 `running`-job wedge this module shares with Janitor and GC.

# Second-pass review: Rate-limited, token-scoped remote URLs

# Review v2: scoped-token-remotes (idea #28)

## Scores
- Feasibility 4/5 (was 4). Every host surface is real: `Env::secret(&str) -> Result<Secret>` with `Secret: Display` is docs-listed in `worker` 0.8.5 (unverified at runtime, as auth-and-multitenancy), `Request::url().query_pairs`, `BodyReader::{new, fill, buffered, consume}` and `wire::parse_receive_header` are contract signatures (1.1, 6). `hmac` 0.12 `Mac::{new_from_slice, update, verify_slice}` and `base64` 0.22 `URL_SAFE_NO_PAD.decode` are API-correct and pure Rust (no `getrandom`), but neither crate is in the pinned list or the spike — unverified on wasm32. The code does not compile against its siblings as written (`receive_pack_body` does not exist; the two `RepoRoute::parse` definitions conflict) — mechanical.
- Reliability 4/5 (was 3). The spent-token-on-crash class is gone by construction: the debit is inside `commit_push`'s sync span under `any_ok`, so a kill anywhere in ingest leaves `token_usage` untouched (no row is even created). Expiry and revoke ride the existing Janitor span — no second `setAlarm` (4.1, A3; measured #5). Residual: the out-of-scope `drain` reads a zone-cap-sized body to EOF before answering, and a push that started before `exp` can lazily re-create a `token_usage` row the Janitor already deleted (harmless — the edge re-checks `exp` on every new request).
- Correctness 4/5 (was 3). Does what the idea says: HMAC scope at the edge before any stub, per-command `ng` at the edge and again per ref inside the CAS, `del` gates deletes, counters debit only moved refs. Deductions: scenario (a)'s `ng ... rate limit` depends on a post-header error arm nothing implements (the `token_precheck` `Conflict` becomes HTTP 409); scenario 4's `token cannot delete` string is unreachable for a lone delete; the mechanism's "every failure is Forbidden" is wrong — malformed `/t/` tails are 404 (line 89).
- Effort: weeks. This file is days; a tokened push needs `receive_pack` split at the header boundary, the `BeginDto`/`CommitRequest`/`apply_one` write-backs, and the sibling post-header error arm that two-phase-push's review already flagged.

## Contract compliance
Matches: `verify_token` is a sync `fn` like `authenticate` (1.4); 403-never-401 (section 10 `Forbidden`); `shallow` consumed by `parse_receive_header` (1.1) so only `RefCommand`s are scope-checked; one `BodyReader` per request with the PACK handed off through `remainder()` (6.1, 6.3); `changes()` never read as a token oracle (gate re-`SELECT`s); all DO additions inside existing sync spans with `Err`-out-of-`fetch` for `Storage`/`Internal` (A2); no `JobKind`, no `set_alarm` — the `token_usage` sweep folds into the Janitor slice (4.1, A4); REGISTRY block lists routes, table, secrets, DTOs (A9); `ReqBudget` 9,000/240 s (7.1); two added scenarios, within the section 11 cap; full rule-5 advertisement via the sibling's `info_refs`.
Deviations (each also in the structured list):
1. `receive::receive_pack_body(body, hdr, env, repo, who, token, budget)` (line 131) is a 7-arg function no sibling defines. `repo-do-ref-authority` defines `receive_pack(req, env, who, repo)` — 4 args (its line 165); `info-refs-endpoint` calls it as `receive_pack(req, &env, &repo, &who, &mut budget)` — 5 args, different order (its line 151). This proof needs a third form, split so the header parse happens before the scope check. Declared as a write-back (lines 128-131) but the crate does not compile until it lands.
2. `token_precheck` in `push_begin` returns `Error::Conflict` ("token revoked", "rate limit", lines 145-146) after the receive header is parsed; A2 requires HTTP 200 + report-status there. The proof asserts "the edge turns it into 200 + `ng` for every command" (line 141) but nothing shown does: `respond`/`finish` maps `Conflict` to 409 and remote-curl discards the body. This is the same gap as repo-do-ref-authority's deviation 3 and two-phase-push's blocker — here it sits on the headline denial path: scenario (a)'s immediate retry prints `error: RPC failed; HTTP 409`, not `ng ... rate limit`.
3. Write-backs into `repo-do-ref-authority` beyond the registered DTO fields: `apply_one` gains a `token: Option<&TokenDto>` parameter and `push_begin` gains a first-statement precheck (lines 167-172); DO `fetch` needs a `/_do/token/revoke` arm. REGISTRY lists `BeginDto.token`, `CommitRequest.token` and the route, but not the `apply_one`/`push_begin` signature changes or the `RevokeDto`/`UseRow` DTOs the comment locates in `wire::http`.
4. `TokenDto` is declared under the `// ---- src/auth/token.rs` listing header (line 70) but annotated "wire::http (A8)". If it lived in `auth`, `repo_do` could not reach it — section 1 gives `repo_do` no `auth` edge — and `repo_do/push.rs` would need the import the shared `use` block lacks. Must be `wire::http`. Mechanical.
5. `RepoRoute::parse` itself drifts between the two dependencies this proof needs: `info-refs-endpoint` returns `Option<(RepoRoute, &str)>` (used here, line 92) while `auth-and-multitenancy` returns `Result<(RepoRoute, String), Error>`; `repo.name()` (line 93) exists only in the latter (`info-refs-endpoint` inlines the `format!` in `stub()`). One definition must win; the fix is mechanical either way.
6. Mechanism overclaim: "every failure is `Forbidden` (403, never 401)" — `pre` returns `NotFound` for `/t/` tails that don't split or don't parse (line 89). Still pre-DO and leaks nothing, but the text is wrong.
7. Scenario 4's asserted string is unreachable for a lone delete: the edge `in_scope` test (line 122) treats a `del:false` delete as out-of-scope, so a delete-only push is answered with `ng <ref> token scope forbids this ref` (line 125) before any DO call; `token cannot delete` (line 172) is produced only when another command is in scope. Rejection semantics hold; the assertion's literal message differs.

## First-pass blockers
1. `rest`'s pull calls `body.getReader()` per pull; multi-chunk PACKs die on a locked reader: **resolved**. Structural — one `BodyReader` per request drives `parse_receive_header`, `drain` and ingest, with the PACK returned through `PktReader::remainder()` pushed back into the same reader (6.1, 6.3; lines 120-121, 189). There is no second stream to lock.
2. `shallow <oid>` pkt-lines parsed as a command with `ref: undefined` -> `ng undefined`: **resolved by dependency**. `parse_receive_header` consumes `shallow` lines into `ReceiveHeader.shallow` before commands (1.1; lines 27, 117-118), so `in_scope` iterates only `RefCommand`s. Scenario (a) covers the depth-1 CI case.
Caveats from the first pass: reserve-then-ingest burns budget on failure -> debit moved inside `commit_push`'s span under `any_ok`, `token_precheck` is read-only (lines 142-175): resolved. Chunked pushes debit `bytes=0` -> gate reads `packs.bytes`, the DO's own normalized count (lines 159-164): resolved, with the wire-vs-stored semantic shift documented in Known limits. Scoped-ref-only advertisement inflates first pushes -> `/t/` `info/refs` forwards to the full rule-5 advertisement (line 106): resolved (ref disclosure accepted as a limit). Early response cancels the stream -> `drain` reads to EOF before the `ng` report (lines 83-85, 124): resolved on the scope-denial path; the pre-auth and wrong-suffix POST paths still drain only 1 MiB (lines 98, 109), so a >1 MiB body on a stale token keeps the curl-92 risk — narrow, since an expired token fails at the GET. `delete-refs` advertised to a no-delete token -> `del: bool` default false, checked at edge and DO (lines 52, 122, 172): resolved. `revoke` rows immortal -> real `exp_ms` kept, Janitor deletes `exp_ms < now` on revoked and unrevoked rows (lines 178-185): resolved. Token in URL / no `kid` -> unchanged limit; `_PREV` two-key rotation window added (lines 60-63): partially resolved (`kid` still not built). Body cap -> documented at 6.2: resolved. Minting hand-waved -> `/_do/token/revoke` is now real, but minting is still a named dependency on `auth-and-multitenancy`, whose second pass explicitly does **not** build HMAC tokens — the mint endpoint has no owner in v2: partially resolved.

## Crash walk-through
`verify_token` and `pre` are sync — no kill point. Killed during `read_receive_header` or `drain`: nothing durable, no `pushes` row, no `token_usage` row (it is created lazily inside the commit span), client retry is clean. Killed after `push_begin` returned, mid-ingest: `pushes` row `open`, `pending/<push>.pack` parts or key orphaned; Janitor at `began_at + 1 h` expires the push (5.1), kills the `ingesting` pack (5.2), deletes keys after `GRACE` (5.3); incomplete multipart parts wait for the bucket lifecycle rule (unverified, storage cost only). The token is unspent — the first-pass "reserve, crash, token burned" case is gone. Killed inside `commit_push`: impossible mid-span (no awaits); a panic is all-or-nothing per A3 — rollback on `PanicError` stays unverified (scenario 15), and if it holds, a panic after the debit UPDATE discards the debit and the ref moves together. Killed after commit returned: ref moved and token debited, both durable — correct. `Gate::Deny` path: `finish_push("rejected")` commits in-span; the pack stays `ingesting` and the Janitor kills it at the next slice. `token_revoke` is one sync statement — durable or absent. The Janitor's `DELETE FROM token_usage` sits in the first (pre-await) sync span of the slice, so a slice kill either applied it with 5.1/5.2 or did not; next firing in <= 15 min.

## Concurrency walk-through
Two pushes on one `maxPushes=1` token: both verify at their edges; both `token_precheck`s may pass (advisory, non-debiting); both ingest distinct pack ids; the `commit_push` spans serialize on the one DO (platform-facts #4). Winner: gate `INSERT`s the row, `Admit`, CAS succeeds, `any_ok` debits `pushes=1`. Loser: gate sees `pushes=1 >= 1`, `Deny` **before** step 3 — its pack never goes `live`, Janitor sweeps it. Exactly one commits (scenario 6); the loser still paid full ingest, which Known limits admits. `token_revoke` racing an in-flight commit: the spans serialize; whichever runs second sees the truth — commit after revoke gets `Deny("token revoked")`. Edge case: Janitor deletes a row at `exp_ms`, then a push that started before `exp` commits — the lazy `INSERT` resurrects the row with `revoked=0`. Harmless: no new request can pass the edge `exp` check, and the row dies at the next sweep; the commit itself is the documented "exp checked once" limit. No token-path span contains an await, so the input gate never opens inside one; the only slice await (the R2 delete) runs after the `token_usage` DELETE.

## Interop check
Push is v0 `receive-pack` regardless of `protocol.version=2`; `Git-Protocol` is ignored (rule 8). The token rides as a path segment, which remote-curl carries verbatim through `info/refs` and `git-receive-pack` — no credential helper involved; a 403 is terminal and never prompts (git prints `The requested URL returned error: 403` once). Every emitted byte is a contract byte: the rule-5 advertisement in full, rule-4 `report-status`; the `ng` reasons are free text to end-of-line, spaces legal. `remote-curl`'s flush-only `probe_rpc` parses as zero commands, hits the `!any(in_scope)` arm, and gets `200 unpack ok` — exactly what it needs before streaming a chunked body. A shallow CI push's `shallow` lines land in `ReceiveHeader.shallow`, not the command list (scenario 11). The wire-visible breakage is deviation 2: the exhausted-token retry — the common case `token_precheck` exists for — yields HTTP 409 with an `ERR` pkt body that remote-curl discards, so git prints `RPC failed; HTTP 409` and `the remote end hung up unexpectedly` instead of `ng ... rate limit`. Also: a valid token for a repo that has never existed boots its DO and creates `meta` on `info/refs` — minted tokens carry repo-creation authority (same trust model as `GE_WRITE_TOKEN`, but worth stating). Malformed-header POSTs get a 400 without a drain — the sibling's shared gap.

## Blockers
- `receive_pack_body` does not exist in any sibling and the three `receive_pack` signatures across `repo-do-ref-authority`/`info-refs-endpoint`/this proof disagree (4, 5, and 7 args); `RepoRoute::parse` is defined twice with different return types across the two dependencies. The crate does not compile until one wins — mechanical, but it must be reconciled, not assumed.
- A2 post-header mapping is unmet for the `Conflict` this module adds at `push_begin`: nothing emits the 200 + `ng` report, and scenario (a) asserts that exact output. Same gap as two-phase-push's blocker and repo-do-ref-authority's deviation 3 — now load-bearing on the token path's most common denial.

## Caveats
- HMAC is computed over the *decoded* payload bytes (line 63), not the encoded segment as the first pass did — non-canonical base64url encodings of one payload all verify (malleability, not forgery).
- `maxPushes` and `maxBytes` have no `#[serde(default)]`; a payload missing either fails deserialize -> 403, so "unlimited" cannot be expressed except as a huge literal.
- Tokened `info/refs` discloses every ref name and oid to a push-only credential (documented as a limit; the alternative the first pass shipped was worse).
- The 1 MiB pre-error drain bound (lines 98, 109) leaves the HTTP/2 RST path open for large POST bodies rejected before routing — narrow, since `exp`/HMAC failures normally end at the GET.
- Minting and the admin edge route remain unowned: `auth-and-multitenancy` v2 builds only the two-token Basic path, so this proof's Depends-on does not deliver them.
- Unverified at runtime: `hmac`/`sha2`/`base64` on wasm32, `Env::secret` Display, `RequestInit` stub bodies, panic rollback (scenario 15), the `receive_pack_body` write-back itself.
- `d.q` from `jobs::janitor` needs `RepoDo::q` at `pub(crate)` — the same helper-visibility write-back other proofs already require.

## Verdict
lands-with-caveats. Both first-pass blockers are closed structurally rather than by check — one `BodyReader`, and `shallow` handled by the contract parser — and the debit-inside-the-CAS-span fix turns the worst crash outcome from "token spent, nothing moved" into "nothing spent, nothing moved". What remains is a cluster of mechanical reconciliations (the `receive_pack_body` split, the token fields, the parse-form conflict), one error arm the token path now depends on for its headline denial, and a scenario string the edge answers earlier with different text. Reliability 3->4, correctness 3->4.

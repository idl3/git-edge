# Second-pass review: Signed refs by default with append-only DO reflog

# Review v2: signed-reflog (idea #19)

## Scores
- Feasibility 4/5 (was 4). Every host call exists in `worker` 0.8.5: sync `SqlStorage::exec` (memo 1), `Stub::fetch_with_request` + `Request::new_with_init` (unverified at runtime, as every sibling), `worker::Bucket::{get,put}` (memo 1 — `get` returns `GetOptionsBuilder`, so `store::Bucket::get` must `.execute()` internally; mechanical). The four new crates are outside the memo 3 CI list and the contract's pin line but are pure Rust: `sha2`/`hmac`/`base64` are trivial on wasm32; `ed25519-dalek` 2 pulls `curve25519-dalek` 4, which selects its 32-bit serial backend on `wasm32-unknown-unknown` and compiles there routinely. `from_bytes`/`sign`/`verify`/`Signature::from_slice` need no RNG, so `getrandom` stays out provided `rand_core` is never feature-enabled (dalek 2's defaults do not include it); minting the seed via `platform::random32` instead of `SigningKey::generate` is exactly the right avoidance. Size is a non-issue on the memo's own numbers: the spike Worker measured 605 KB wasm-opt'd (corrections 5), these four add on the order of +200–300 KB post-opt (curve25519 `precomputed-tables` dominate), and the only remaining limit is 64 MiB uncompressed — the old 3/10 MB compressed caps no longer exist (memo 1). Cold-start delta over the measured 20–30 ms local instantiate is trivial. The genuinely unverified pieces are `BEFORE UPDATE|DELETE ... RAISE(ABORT)` triggers through worker's `exec` at runtime (disclosed) and `random32`'s return width, pinned nowhere (deviation 6).
- Reliability 4/5 (was 2). The first pass's fatal shape cannot recur: `sign_and_log` runs inside `commit_push`'s existing sync span after `changes()==1` with no await anywhere (lines 74-84), so the measured gate-opening pattern (platform-facts #4) is excluded by construction, and `UNIQUE(prev_hash)` turns any residual fork into `Err`-out-of-`fetch` with full span rollback (A2). The enqueue is an in-span row write, so a crash after commit leaves a `queued` anchor the next firing picks up (bounded by the Janitor's 15-min cycle, 4.2). Residuals: `enqueue` dedups on `queued OR running` (4.5), so a commit landing during a running `reflog_anchor`'s `bucket.get` await loses its re-arm — newest rows stay unanchored until the next push, and no queued row exists for the Janitor bound to cover; an isolate kill mid-slice leaves the job row `running` forever (nothing in section 4 requeues `running`, and dedup then blocks every later anchor permanently — a foundation gap this module inherits); `reflog_broken` once set has no clearing path, so the repo is bricked including on a false-positive `head.json` rewind.
- Correctness 3/5 (was 3). The server-attested half is right: the canonical entry binds name/old/new/push/principal/at/prev (line 79), the signature covers the hash-chain link, `verify_entry` repeats the same math, and the ref CAS + signed row are atomic in the span. The wire half is designed correctly — cert pkt-lines before `push-cert-end`/shallow/flush/PACK, commands from the cert body per `queue_commands_from_cert` — but as written `git push --signed` still cannot pass the proof's own scenario (a): `commands_from_cert` returns `Err(Protocol("cert command"))` on the trailing `""` after the last command line of every real cert (lines 144-152), and `verify_cert`'s `arm` slice includes the `-----BEGIN SSH SIGNATURE-----` marker line itself, so `STANDARD.decode` rejects `-` on every SSHSIG cert (lines 159-161). Both are one-line mechanical fixes; together they mean the client half of the idea fails end to end, in `Err` rather than even reaching `ng`.
- Effort: weeks. The module itself is days of code plus the day-1 wasm32 build; it lands on repo-do-ref-authority, two-phase-push, refs-sqlite-objects-r2, info-refs-endpoint and auth-and-multitenancy.

## Contract compliance
Matches: signing inside the section-3 span after `changes()==1` (measured #1); `Err`-out-of-`fetch` for `Storage`/`Internal` (A2); `enqueue` in-span + `rearm` after (4.5, A3); REGISTRY block covering tables, triggers, routes, the `JobKind` arm and R2 prefixes (A9); `ReflogDto` in `wire::http` (A8); budget-carrying `Bucket::{get,put}` through `SliceBudget.req` (A1, bundle-uri's write-back); identity from `meta`/`bucket.repo`, never `ctx.id.name` (8.2); `unpack ok` + per-ref `ng` after-header shape for cert rejection (10, A2); paginated `/_do/reflog` as an awaits-none route (1.3); at most two added scenarios (11); no `set_alarm`, no `rows_written`.
Deviations (each also in the structured list):
1. Rule 5's "Advertised receive caps, exactly:" gains `push-cert=<nonce>`, and `write_advertisement_v0` gains a nonce parameter (REGISTRY, line 41). Required by the feature, but capabilities are outside A9's enumeration (routes, `JobKind` variants, tables, R2 key prefixes); this wants a contract amendment line, and the signature change propagates into info-refs-endpoint's advertisement path.
2. `ReceiveHeader` gains `push_cert: Option<PushCert>` and `parse_receive_header`'s documented order (1.1: shallow lines, then command lines) changes — for a signed push the cert block comes first and commands come from its body (lines 40, 140-152). Registered; rewrites a 1.1 signature.
3. Dependency direction (1.1: `edge -> wire`, never the reverse; `wire` imports only gix crates): `PushCert` and `commands_from_cert` are declared in `src/edge/pushcert.rs` (lines 25, 142-152), but `ReceiveHeader.push_cert` lives in `wire`, which cannot name an `edge` type, and "hdr.commands are already the cert's commands" requires the extraction to run inside `parse_receive_header`. Mechanical: both move into `wire` (the `oid` helper becomes gix-hash direct, already allowed there).
4. Contract tables modified, not added: `reflog` gains four columns + `UNIQUE(prev_hash)` + two triggers (section 3 schema); `pushes` gains `push_cert`; `CommitRequest` gains `push_cert`; `push_begin`'s body-out gains `cert_keys` (1.3); `store::Bucket` gains `get`/`put` (1.2). All registered in the REGISTRY/write-back lists; flagged because A9's text covers additions.
5. `GE_NONCE_SEED` is a new deployment secret (line 128). Contract 12 names exactly two secrets; neither the REGISTRY block nor the write-back list (line 247) mentions it. Unregistered.
6. Signature drift: `cert_gate(..., allowed: &[Vec<u8>])` (line 185) vs the `push_begin` response's `cert_keys: Vec<String>` (line 42); the commented call site (line 193) passes `&begin.cert_keys` where `&[Vec<u8>]` is expected — a base64 decode of each OpenSSH blob is missing between them. `platform::random32`'s return type is pinned in no sibling: if it returns the 16 bytes behind section 8.2's 32-hex ids, `SigningKey::from_bytes(&seed)` needs `[u8;32]` and will not compile. `exec()`, `meta_opt()`, `bucket()`, `d.q()`, `now_ms()` are used as repo-do helpers (line 54) but `meta_opt`/`bucket` are actually bundle-uri's write-back and `exec` is shown nowhere; all need `pub(crate)` (wasm-git-core flags the same list).
7. `ReflogDto{ref,after,limit}` in REGISTRY (line 35) vs `b.ref_name` in code (line 92): `ref` is a keyword; the DTO needs `#[serde(rename = "ref")]`. Trivial.
8. Error shape: the `Err` paths inside cert handling — `commands_from_cert`'s `Protocol` errors, the nonce timestamp `parse` failure (line 132), `verify_cert`'s decode/`ssh_str` errors — propagate out of `receive_pack` as bare `Err` and map to 400/`ERR`, not the after-header 200 + `ng` A2 mandates; only the `Ok(Some(r))` arm reaches `report` (line 194). A malformed cert with no enumerable commands arguably cannot produce per-ref `ng` (git dies the same way), but a well-formed cert with an unparsable timestamp should be `ng`.

## First-pass blockers
1. "CAS and head read outside `transactionSync` across non-storage awaits: lost update on `refs` and forked hash chain under concurrent pushes.": **resolved**. There is no await on the sign path at all now — `sign_and_log` is synchronous inside `commit_push`'s span after the per-ref `changes()` (lines 74-84); the WebCrypto path is gone, and `UNIQUE(prev_hash)` (the first review's own suggestion) backstops the chain. Platform-facts #4 is cited correctly and applies.
2. "Signed-push command parsing: commands live inside the `push-cert` block, not in a leading command line; as described, `--signed` pushes are rejected.": **resolved** at the design level — `commands_from_cert` reads the cert body per `queue_commands_from_cert`, `parse_receive_header` accepts the `push-cert` block in send-pack's order, and the advertisement gains `push-cert=<nonce>` — but the implementation reintroduces rejection by bug rather than design: every real cert errors on the trailing empty line and every SSH armor fails base64 decode (Blockers).
Caveats from the first pass: `verifyPushCert` undefined -> **partially resolved**: SSHSIG implemented end to end but broken by the decode bug; GPG/RSA/ECDSA and an empty key list remain stored-only, disclosed. Key beside the log / append-only vs app code / overwritable anchors -> **partially resolved**: `head.json` now carries `pub` and a mismatch sets `reflog_broken`, failing later commits closed; the seed still lives in DO storage and anchors remain overwritable — detection, not prevention; the versioned bucket stays the r2-versioned-snapshots dependency. Alarm arming outside the transaction -> **resolved**: `enqueue` is an in-span row write (4.5), `rearm` after per A3; a new dedup-swallow residual is noted below. `/reflog` unpaginated, `nonce()` writes per advertisement, no key-id column -> **resolved**: `after`/`limit` pagination capped at 1,000, stateless HMAC nonce with no storage write, `key_id` on every row. The 32 MB RPC ceiling -> **resolved**: paginated JSON over `Stub::fetch_with_request`, ~0.5 MB pages, no typed RPC. Crash-after-commit anchoring -> **partially resolved**: the queued row is atomic with the commit and the Janitor cycle bounds the wait, but an enqueue racing a `running` anchor dedups to nothing, leaving a next-push-bounded tail. Silent key regen on DO wipe -> **resolved**: `pub` mismatch -> `reflog_broken` -> commits fail closed; wipe-before-first-anchor stays silent (admitted). Concurrent `meta`-row nonces -> **resolved** by the stateless nonce. O(refs) async WebCrypto before the transaction -> **resolved**: O(refs) *sync* signs inside the span; the CPU cost is disclosed.

## Crash walk-through
Kill inside `commit_push`'s span (mid-`sign_and_log`): the whole span is discarded (section 3 atomicity; panic rollback itself is scenario-15 unverified). No ref moved, no half-signed row, the push stays `open` and the Janitor expires it at +1 h. Clean. Kill after the span returns but before `jobs::rearm` (A3): the `ReflogAnchor` row exists atomically with the commit; if no alarm is armed the row waits for the next firing — the Janitor's 15-min self-cycle bounds it (4.2). The client saw a 500 on a committed push; a retry gets `ng failed to update ref`. Kill inside `reflog_anchor` between the two `put`s (lines 121-122): `anchor/<seq>.json` written, `head.json` stale — idempotent, self-heals on retry — but the job row is stuck `running`: section 4 requeues only on `Err`, never on isolate death, and `enqueue` dedups on `queued OR running`, so every later anchor is silently skipped until an operator deletes the row. Foundation-level gap; here it converts "detection lags" into "detection stops". Kill at the edge mid-`/_do/reflog`: read-only, nothing durable. DO storage wiped after anchors exist: the next push mints a new seed in-span; the next anchor firing sees `head.json.pub` != new pub (line 115) -> `reflog_broken` -> every later commit fails in `signing_key`, and since the `Err` discards the span the `refs` CAS rolls back with it — the log genuinely cannot move. Wipe before the first-ever anchor remains silent (admitted, line 243). False positive: an operator rewind or re-put of an old `head.json` bricks the repo with no documented recovery.

## Concurrency walk-through
P1 and P2 racing the same ref: commit spans serialize (no await inside); the loser's CAS reports `changes()==0` -> `ng failed to update ref`; the chain stays linear, and `UNIQUE(prev_hash)` would make any residual fork an `Err`+rollback rather than a fork — scenario (b) asserts the GROUP BY emptiness the structure already guarantees. Two `info/refs` advertisements racing: each mints an independent HMAC nonce, both verify — the first-pass `meta` race is gone. Commit C landing during `reflog_anchor`'s `bucket.get` await (the slice's gate-opening point): the anchor writes `anchor/<h.id>` + `head.json` for the head it read pre-await — stale but valid, `pub` unchanged — while C's `enqueue` dedups against the `running` row (4.5) and inserts nothing; C's rows stay unanchored until a later commit enqueues again. Next-push-bounded, not Janitor-bounded as line 216 claims. `/_do/reflog` reads vs a commit: separate DO-serialized spans; `next_after` is `id`-based so a row committed mid-pagination simply appears in the next page — consistent.

## Interop check
Push is v0 receive-pack regardless of `protocol.version` (section 7). For `--signed`, send-pack.c emits `push-cert\0<caps>`, the cert pkt-lines, `push-cert-end`, then shallow lines, flush, PACK — no leading command line; the proof's order matches and `parse_receive_header` is amended to consume it. `push-cert=<nonce>` as one more space-separated cap on the first ref line is protocol-legal, and advertising it is mandatory — git errors client-side if `--signed` is requested against an advertisement without it. Cert grammar: headers (`certificate version 0.1`, `pusher`, `pushee`, `nonce`, `push-option`), blank, `<old> <new> <ref>` lines, armor — `commands_from_cert` implements this but dies on the trailing `""` element where git's own loop stops at the armor's `-` (one-line fix, hard bug: every signed push `Err`s today). The SSHSIG framing is right — `SSHSIG` magic plus five SSH strings, signed message `SSHSIG` || string("git") || string("") || string("sha512") || string(SHA-512(body up to armor)), armor `-----BEGIN SSH SIGNATURE-----`, OpenSSH pubkey blob compare — but the decoded `arm` includes the marker line, so `STANDARD.decode` errors on `-` before any of it runs (lines 159-161). Whether `raw[..a]` including its trailing newline is byte-identical to git's `verify_signed_buffer` region needs scenario (a) to confirm. Rejection shape on the `Ok(false)`/bad-nonce paths is correct: `unpack ok` + `ng <ref> <reason>` (`&'static str` reasons fit `RefResult::Ng`, rule 4/section 10). `Err` paths bypass it (deviation 8). The early `return report(...)` in cert-gate does not drain the request body: scoped-token-remotes learned an early response before body EOF is cancelled under HTTP/2 — the same drain-before-`ng` applies here or the client may see a reset instead of the report. `GET /<o>/<r>/reflog` returns rows plus `pub`; the offline verifier's math is self-consistent (signature over the hex of `entry_hash`), but only the current key's `pub` is returned — rows under rotated `key_id`s cannot verify (admitted).

## Blockers
- `verify_cert` armor slice (lines 159-161): `arm` begins at `raw.find("-----BEGIN SSH SIGNATURE-----")`, i.e., includes the marker line; `STANDARD.decode` rejects `-`, so every SSH-signed push with a configured key list exits `Err(Protocol)` — and note `allowed.is_empty()` is checked before the slice (line 158), so the bug bites exactly when verification is on, which is the only case that matters. Mechanical fix (start the decode after the marker line's newline), but scenario (a) cannot pass as written.
- `commands_from_cert` (lines 144-152): `body.split('\n')` yields a trailing `""` after the last command on every real cert (the body ends `"...<ref>\n"`); the empty check only applies pre-blank-line, so the tail hits `Err(Protocol("cert command"))`. Every signed push fails inside `parse_receive_header` — the first pass's blocker 2 reintroduced by bug. Mechanical (skip empty lines or `trim_end` the body).
- The pieces do not compile as written: `PushCert`/`commands_from_cert` in `edge/pushcert.rs` cannot be named by `wire`'s `ReceiveHeader`/`parse_receive_header` (deviation 3); `cert_gate`'s `&[Vec<u8>]` vs `cert_keys: Vec<String>` (deviation 6); `platform::random32` width unpinned. Same class as two-phase-push's cross-proof drift — one pass of reconciliation is required before the crate builds.

## Caveats
- `enqueue` dedup during a `running` ReflogAnchor drops the re-arm; last-push rows can sit unanchored until the next push — the Janitor bound (line 216) covers only the queued-row case.
- A `running` job row orphaned by an isolate kill is never requeued (section 4 has no rule for it); dedup then blocks ReflogAnchor permanently. Inherited foundation hole, worst-consequence here.
- `reflog_broken` has no clearing path: the repo bricks permanently once set, including on a `head.json` rewind false positive; section 12 puts admin APIs out of scope, but an operator procedure (or a `/_do` route) is needed before this can ship.
- The four crates: pin `default-features` deliberately — `ed25519-dalek` must not gain `rand_core`/`getrandom` (which would drag in the `wasm_js` cfg dance of memo 3); defaults keep it out today. Estimated +200–300 KB post-wasm-opt over the 605 KB measured baseline; immaterial against the 64 MiB limit.
- Migration mechanics: `prev_hash`/`entry_hash`/`sig` are `NOT NULL` without `DEFAULT` and `UNIQUE(prev_hash)` — `ALTER TABLE` cannot add either on a populated `reflog`; a rebuild or defaults are needed. Greenfield-fine; the schema_version bump text doesn't say which.
- `cert_gate` runs after `push_begin`, so a cert-rejected push leaves its `pushes` row `open` until `PUSH_TIMEOUT` and writes no `pushes.result` (A5); a `/_do/push/reject` call as in hooks-as-workers would close both. Also: no body drain before the early report (Interop).
- `nonce_ok` is inconsistent on malformed input: a nonce without `-` -> `Ok(false)` (per-ref `ng`), an unparsable timestamp -> `Err(Protocol)` (request 400). One behavior, two surfaces (line 131-133).
- `raw.get(a..).and_then(|s| s.split("-----END SSH SIGNATURE-----").next())` can never yield `None` — the `armor` error arm is dead code (line 159).
- `key_id` is hardcoded `1` and `pub` exposes only the current key; rotation machinery remains out of scope (admitted).
- Unverified, day-1 (mostly disclosed): the four crates on wasm32; triggers through `exec` at runtime; `RequestInit` JSON path; `web_sys::Crypto` binding behind `platform::random32`; the GET-query -> `ReflogDto` parse; the deployed DO subrequest cap (platform-facts #7); a lifecycle rule for expired anchors.
- HMAC tag compared with `==` on hex strings rather than constant-time — a nonce forgery needs the secret anyway; cosmetic.
- `verify_cert` signs `raw[..a]` — the body up to the armor, trailing newline included; byte-exactness against git's `verify_signed_buffer` region is for scenario (a) to prove.

## Verdict
lands-with-caveats. Both first-pass blockers are closed at the design level — the sign path is fully synchronous inside the existing commit span, so the measured lost-update pattern cannot recur, and the wire parse follows send-pack's real order. What remains is implementation-tier: two one-line parse bugs that keep every `push --signed` from working (both caught by the proof's own added scenario on day 1), one dependency-direction move, an unregistered env secret, and a rule-5 amendment. Reliability 2->4; correctness holds at 3 because the client half of the idea still cannot succeed as written.

# Second-pass review: Wasm git core (gitoxide/libgit2) for delta resolution and merge

# Review v2: wasm-git-core (idea #25)

## Scores
- Feasibility 4/5 (was 4). The hybrid is gone and what remains is one crate where every API either exists or is a flagged rename: `Find::try_find(&self, &oid, &mut Vec<u8>) -> Option<Data>` with `Data{kind, data: &[u8]}`, `CommitRef::parents() -> Iterator<Item = ObjectId>`, `ObjectId::{null, is_null, as_slice, from_hex}` all verified against gix-object 0.64.1 / gix-hash 0.26.2 docs. But four calls do not compile as written against the pinned versions — `CommitRef::from_bytes` and `TreeRefIter::from_bytes` each take a hash-kind second argument, `EntryMode::as_bytes` takes a `&mut [u8; 6]` backing buffer, and `imara_diff::diff` does not exist in 0.2.0 at all (the all-items list has only `sources::{byte_lines, lines}`; the path is `Diff::compute(Algorithm, &input)`). The proof itself marks these unverified; I verified them wrong. All mechanical, none structural. The vendored-driver decision is memo-sanctioned (section 3: `gix-merge` is not in the wasm CI list and `blob::Platform` needs `gix_worktree`/`gix_filter`).
- Reliability 4/5 (was 3). All three first-pass stall/leak classes are gone by construction: no FFI (no linear-memory leak), no `pending_deltas` drain (no terminal stall, no alarm collision — `jobs::rearm` is the only `set_alarm` caller and this module registers no `JobKind`). Span discipline is right: epoch pinned, `push_begin`/`push_index`/`commit_push` each a sync span, `rearm().await` after (A3). Residuals: a kill between `PackWriter::finish` and `push_index` leaves a completed `packs/<id>.pack` with no row and no cleanup path (the sibling posts the `ingesting` row first, deviation 5); the `?` error paths skip `w.abort()`; and `MEM_CAP` (64 MiB) + `MERGE_OUT` (64 MiB) + 8 MiB part buffer can jointly exceed the 128 MiB isolate — worst case an OOM panic (500), not `Error::Limit`.
- Correctness 3/5 (was 3). Delta resolution is inherited and measured (correction 5); the merge machinery is git's trivial-merge table plus a git-compatible text driver, and a merge is a real section-3 push with CAS and `gc_epoch` guards. But the code as written fails its own scenario (a): `merge_base` can return a base commit it never loaded (the `other.contains` early return at line 71 precedes `try_find`), and `tree_of(&mem, &base)` at line 239 maps the miss to `Error::NotFound` — HTTP 404 on the canonical diverged-by-one-commit merge. Nested conflict/changed paths are emitted without `/` separators; a file-vs-directory change on both sides gets 400 instead of a conflict; the scenario asserts 409 where the code returns 200. Fixable line by line, but they are real.
- Effort: weeks. This file is days of code — ~150 lines of tree merge, a 926-line vendored driver, two routes — on top of a foundation that must land first; the vendoring, the write-backs, and the conformance additions are the work.

## Contract compliance
Matches: REGISTRY block per A9 (two edge routes, two `/_do` routes with awaits declared, no `JobKind`/tables/R2 prefixes); section 9 shape — `want` is the async loader, `merge_base`/`merge_trees`/`tree_changes`/`unified` are `fn`s over `MemFind`, `Load::Need` rounds are the contract's loop and terminate (every `Need` is non-empty, `want` either loads or returns `NotFound`); section 3 ordering finish -> `push_index` -> `commit_push` with `changes()` as the only oracle and `jobs::enqueue` inside the span, `rearm().await` after (A3); `gc_epoch` pinned in span 1 and re-guarded in span 2 and commit step 2; A7's 16 MiB cap on merged blobs/trees, 10,000-row index cap (1.3), budget charging on every stub/R2 call (7.1); no `set_alarm`, no `transactionSync`, no `Reflect` (4.1, A3, A8); `push-options` not used (12); merge gated on `who.can_write` and `m.principal` is overwritten from `who.name`, never trusted from the body.
Deviations (each also in the structured list):
1. `merge_base` (line 71) returns `Done(Some(id))` before `try_find`, so the base commit can be absent from `mem`; `tree_of` (lines 189-193) then returns `NotFound` and `api_merge` (line 239) 404s a symmetric-depth merge — exactly the shape scenario (a) exercises. Fix is one `want(&mut mem, &[base], budget)` (or route `tree_of` misses through `Load`); as written the flagship path fails.
2. Path separator missing twice: `p.push_str(name)` (line 119) in `Tm::dir` and `q.push_str(name)` (line 178) in `tree_changes` concatenate without `/`, so nested conflict paths and changed-path lists come out mangled (`"srcmain.rs"`).
3. `Tm::dir` never checks the base entry's kind: the tree-tree arm passes `be.oid` to `dir` unconditionally (line 125), so a file->dir change on both sides hits `tree_list`'s `Error::Protocol("not a tree")` -> HTTP 400 instead of a conflict; the blob arm passes whatever `be.oid` names (tree, symlink, gitlink) to `merge_blobs` as the text base (line 131), and the NUL binary check covers `ob`/`tb` but never `bb` (line 132). git reports these as conflicts.
4. Verified-wrong entry points (the proof flags them unverified; docs.rs settles them): `imara_diff::diff(Algorithm::Myers, &input)` at line 165 does not exist in 0.2.0 — it is `imara_diff::Diff::compute(Algorithm::Myers, &input)`; `CommitRef::from_bytes` is `(data, object_hash)` — one arg at lines 75 and 192; `TreeRefIter::from_bytes` is `(data, hash_kind)` — one arg at line 91; `EntryMode::as_bytes(&mut [u8; 6])` needs a backing buffer — none at line 142. All mechanical; the file does not compile as written.
5. Lifecycle ordering regresses the sibling's invariant: `push_index` — the only place a `packs` row is created — runs after `PackWriter::finish` (lines 266-269), so a kill in that window leaves a complete `packs/<id>.pack` that nothing deletes (5.3 needs a `dead` row; the abort-incomplete-multipart rule does not apply to a completed upload). two-phase-push posts `PackMeta::EMPTY` before `create` precisely to close this (its line 64).
6. Added scenario (a) (line 334) asserts the conflicted call "returns 409 with `{"conflicts":[<path>]}`"; the code returns `wire::http::json` (HTTP 200) for both conflict and unrelated-history results (lines 235, 244) — 409 arises only from `Error::Conflict` (CAS failure / gc epoch). The scenario contradicts the code.
7. Signature drift inherited from the dependency set, plus this proof picks a side: `commit_push`/`CommitRequest`/`CommitResponse` exist in two incompatible sibling definitions — repo-do-ref-authority (`commands: Vec<CmdDto>`, `pack_id: Option<String>`, `results: Vec<(String, Option<&'static str>)>`) and refs-sqlite-objects-r2 (`commands: Vec<RefCommand>`, `pack_id: Option<PackId>`, `results: Vec<RefResult>`). The `(_, Some(ng))` match at line 275 compiles only against the first. `PackWriter::create` here uses the A1 four-arg form `(bucket, key: &str, expected: u32, budget)` while two-phase-push's call site has three args and a `String` key (its line 65); `append_entry` is `Result`-returning here (A1) but tuple-returning in streaming-pack-parser (its line 176 has no `?`). One definition each must win before the crate builds.
8. `Hunk` is declared in `core` (line 161) with no `Serialize` derive while the write-backs assign `Hunk` to `wire::http` (line 333); `json!({"hunks": unified(..)?})` (line 215) needs whichever type `unified` returns to be serializable. Mechanical, inconsistent as written.
9. `boot_meta()` (line 256) exists in no sibling — `boot(&RepoHeaders) -> Meta` does. Listed under write-backs, but it is a new helper, not a visibility change; either `boot` is reused with the route headers or the helper is added.
10. The merge commit bypasses both new-object caps: it is built by `compute_hash` + `objects.push` (lines 248-249), not `new_obj`, so `req.message` — an unbounded JSON string, body cap is the zone's 100 MB — mints a commit that can exceed A7's 16 MiB per-object cap and pushes `objects` past `MERGE_OUT` unaccounted.

## First-pass blockers
1. ofs-delta base resolution inconsistent with the parser it depends on: **resolved by dependency**. The first-pass `pending_deltas`/`loadBase`/`objects/<sha>` machinery is gone; contract 2.4 + A10 persist the raw pack at `pending/<push>.pack` and `resolve_at` walks chains by recorded offset in offset order with `verified_base_pack_offset` and `MAX_DEPTH` guards, resolved bytes hashed by `compute_hash` — a bad chain cannot mint a plausible sha. Measured on workerd (correction 5: two OFS deltas, ids match `git verify-pack`). This module adds nothing to ingest, which is the right amount.
2. Terminal-stall paths (missing base, missing `pending/` key looping forever): **resolved**. There is no drain loop; a missing base is `Error::Unpack` from pass B and reaches the client as HTTP 200 + `unpack <msg>` + `ng` per ref (A2, section 10). Nothing re-arms.
3. Linear-memory leak (no `free`/`reset`): **resolved**. There is no FFI; the whole crate is the module (section 1). Object memory is `MemFind` + `Vec<u8>` under the Rust allocator, dropped at request end, bounded by `MEM_CAP`/`MERGE_OUT`/A7 — though the joint bound is unenforced (deviation/Reliability note).
Caveats from the first pass: alarm collision with the janitor -> **resolved** (no `JobKind`; `jobs::rearm` is the sole `set_alarm` caller, second `setAlarm` cancels the first — measured #5). Wasm only on the parked path -> **resolved** (delta resolution is now the only ingest path, 2.4). `gix-merge` on wasm32 unverified -> **resolved by decision** (vendored 926-line text driver, memo section 3; the vendored file is claimed, not shown — a build check is day-1). Free-plan 3 MB cap -> **resolved** (limit gone, memo section 1; foundation measured 605 KB / 262 KB gzip, correction 5). CPU 64x40MB slices -> **resolved** (in-request under `cpu_ms = 300000` and `ReqBudget.max_ms` 240 s; byte budgets replace the row-count budget). Wasm boundary design + interop (1) chain bug -> **resolved by dependency** (section 9 is the same host-loads-then-compute rule; 2.4 owns chains). Interop (2) byte-identity claim -> **carried honestly** (Known limits: imara-Myers, conflict detection equivalent, marker text may differ, no byte-identity claim). Crash `!` panic loop -> **resolved** (the machinery it lived in is deleted; see crash walk-through for what replaced it).

## Crash walk-through
Kill inside a `want` await during the merge rounds: no writes exist yet — the first write is `push_begin` in span 2 — so nothing is durable; a retry is clean. Kill inside span 2 (epoch check + `INSERT INTO pushes`): the span is uncommitted, so either nothing or a lone `open` pushes row persists, which Janitor 5.1 expires at +`PUSH_TIMEOUT` (1 h); no `packs` row, no `objects` rows. Kill during `PackWriter::{create, flush_if_full, finish}` awaits: `open` pushes row plus an incomplete multipart upload with no packs row — the parts wait for the bucket's abort-incomplete-multipart lifecycle rule (not in the memo; storage cost only, same as the sibling). Error paths here (`append_entry?`, `flush_if_full?`, `finish?`) propagate without `w.abort()` — the sibling calls `out.abort().await` on pass-B failure; this module never does, same orphan class. Kill between `finish` and `push_index`: a complete `packs/<id>.pack` (up to 64 MiB) with no row — nothing ever deletes it (deviation 5). Kill between `push_index` and `commit_push`: `open` push + `ingesting` pack + `objects` rows — Janitor 5.1 expires the push, 5.2 kills the pack and deletes rows, 5.3 deletes the R2 key and the `packs` row after `GRACE` (2 h total). Clean. Kill inside `commit_push`: the span is atomic — either ref moved + `committed`, or nothing; after commit, the ref is live and a client retry sees `ng failed to update ref` -> 409, correct. Kill between the commit response and `jobs::rearm().await`: the `GcMark` row is queued but the alarm may be unarmed only in a vacuum — in steady state the Janitor's self-enqueued 15-min chain keeps a pending alarm, so the job fires at the next dispatch. Clean.

## Concurrency walk-through
Two `POST /merge` calls on the same `into`: both pin `ours` in span 1, both compute merge commits in parallel rounds (the input gate opens on every `want` await — the merge holds no locks, which is the design), both reach `commit_push`. Step 3 flips both packs `live` (each its own fresh `PackId`), step 4's `UPDATE refs SET target=? WHERE name=? AND target=ours` admits exactly one (`changes()` 1/0 measured, #1); the loser gets `ng failed to update ref` -> `Error::Conflict` -> 409, and its pack stays `live`-but-unreferenced until the next GC marks it absent — wasted bytes, no corruption. Merge vs a pushed update to `into`: identical CAS race, same outcome. Merge vs `GcSweep` during the rounds: the sweep bumps `gc_epoch` in its own span; span 2's recheck catches it -> `Conflict` -> the caller retries; a sweep between span 2 and commit is caught by `commit_push` step 2 -> `ng "gc ran during push, retry"` -> `Conflict` -> 409. Merge vs Janitor: the merge's `pushes` row is seconds old (< `max_ms` 240 s against `PUSH_TIMEOUT` 1 h) and its pack/pending keys are never `dead`/not-`open` older than `GRACE`, so 5.1/5.3 cannot touch it mid-request. `/_do/diff` racing any writer: `Index::lookup` is sync and sees before-or-after, never mid-span (#4). A no-op merge (`base == theirs`) still CASes `ours -> ours` (changes()=1), writes a reflog row and bumps `refs_version` — noise, and it can abort an in-flight `GcSweep`; harmless, mildly wasteful.

## Interop check
A real git client never sees these routes — they are authenticated JSON over the same `/:owner/:repo` namespace, and `diff`/`merge` path suffixes collide with no git endpoint (`info/refs`, `git-upload-pack`, `git-receive-pack`). What git does see is the merge commit on the next `git fetch`: the object written is `tree <root>\nparent <ours>\nparent <theirs>\nauthor ...\ncommitter ...\n\n<msg>` — byte-valid, ours-first parent order matching git's merge convention; `cat-file -p` shows two parents and `fsck` is clean *provided* `req.principal` is well-behaved — it is interpolated into the `author`/`committer` header lines unvalidated (line 246), and `Principal.name` is the Basic-auth `write:<username>` label (auth proof line 50), so a `\n` in the username produces a malformed commit object `fsck` rejects. Tree objects are canonical (`mode SP name NUL raw-oid`, `sort_key` implements git's dir-sorts-as-`name/` rule) once `as_bytes` gets its backing buffer. Merge semantics are honestly weakened: trivial-merge table + vendored imara-Myers text driver — conflict detection equivalent to git, marker text and slider placement may differ from xdiff, no rename detection, one BFS base. `theirs` must be a full commit oid (tree/tag -> `Protocol` -> 400 via `merge_base`'s kind check); `into` must exist (404, no unborn-branch merge in v1). Both added scenarios have problems: (a) fails twice — the canonical merge 404s (deviation 1) and the conflicted call is 200 not 409 (deviation 6); (b) asserts hunk-range equality with `git diff --unified=0`, but `unified` never calls `diff.postprocess_lines(&input)` — imara's raw hunks can place equal-cost sliders differently than git's indent-heuristic output, so the assertion needs postprocessing or a looser check.

## Blockers
- `merge_base` can return an unloaded base and `api_merge` 404s the canonical symmetric merge — the proof's own scenario (a). One-line fix (load `base` before `tree_of`, or route it through `Load`), but the headline route does not work without it (deviation 1).
- A kill between `PackWriter::finish` and `push_index` leaves a completed `packs/<id>.pack` that no mechanism deletes; the sibling's row-before-upload ordering (`PackMeta::EMPTY` before `create`) is the fix (deviation 5).
- `commit_push`/`CommitRequest`/`CommitResponse` are defined incompatibly across two sibling proofs this one depends on; the code compiles only against repo-do-ref-authority's version — one definition must win before the crate builds (deviation 7).
- Four calls do not compile against the pinned crates — `imara_diff::diff` (does not exist; `Diff::compute`), `CommitRef::from_bytes` arity, `TreeRefIter::from_bytes` arity, `EntryMode::as_bytes` backing buffer (deviation 4). Mechanical, but real.

## Caveats
- Nested conflict and changed paths are mangled by missing `/` separators (deviation 2); the base entry's kind is unchecked, turning both-sides file<->dir changes into a 400 or a garbage blob base (deviation 3). Both mechanical; both ship wrong API output if unfixed.
- `req.message` is unbounded and the merge commit bypasses `MAX_OBJ`/`MERGE_OUT` accounting (deviation 10) — a giant message mints a >16 MiB commit object, violating A7.
- `MEM_CAP` + `MERGE_OUT` + 8 MiB part buffer exceed the 128 MiB isolate at the bounds; the joint bound is unenforced — worst case an OOM panic (500), not `Limit`. Same admitted class as the two-phase-push review.
- `merge_trees`/`merge_base`/`tree_changes` recompute from scratch on every `Need` round — wasted but bounded by `MEM_CAP` and `ReqBudget`.
- `Hunk` sits in `core` without `Serialize` while write-backs put it in `wire::http` (deviation 8); `boot_meta` is a new helper, not a visibility change (deviation 9); `push_begin`/`push_index` return `Response`s that are discarded — works, but they are route handlers being used as functions.
- The `/_do/diff` and `/_do/merge` dispatch arms are not shown: they must be early-return await arms ahead of the sibling's sync-span match (like `/_do/fetch`), and a DO-side `ReqBudget` must be constructed for the `budget` parameter. Mechanical write-back.
- Scenario (b)'s byte-exact hunk assertion needs `postprocess_lines` or a looser check; scenario (a) contradicts the code's 200-for-conflicts (deviation 6).
- Unverified per memo/platform-facts: `RequestInit`/`new_with_init` JSON body path, `Error::from_do_response`, real-R2 multipart and subrequest enforcement (#6, #7), deployed size and cold start (still-open #3 — +100-200 KB is an estimate), `TransactionSync` absent so panic rollback is scenario 15.
- No-op merges write a reflog row and bump `refs_version`; a >64-deep tree is `Limit`; `diff` accepts only full oids and only commit/blob pairs; duplicate subtrees are appended to the merge pack un-deduplicated (legal per 2.3, redundant bytes).
- `server-side-rebase` writes its own three-way tree merge over `MemFind` (`merge_trees(mem, Option<E>, Option<E>, Option<E>, ...)`) — two proofs now carry parallel tree-merge implementations with different types and no shared `core` module; they will drift.

## Verdict
lands-with-caveats. The collapse the contract forces — the whole crate is the wasm git core — deletes the first pass's entire failure surface (FFI leak, alarm stall/collision, parked-delta consistency), and the surviving feature is a real section-3 push with correct span discipline. What remains is localized: the `merge_base` unloaded-base bug that 404s the flagship merge, a row-ordering regression that orphans a completed pack, four verified-wrong API calls, and a sibling signature that needs one winner. Correctness stays 3/5 because the merge route as written fails its own conformance scenario; reliability improves 3->4 on structural grounds.
